# INS-001 — The CLI installer

## What this delivers

```
php artisan sanitube:install
```

Seven idempotent stages — preflight, environment, application key, database,
migrations, owner, verify — plus `docs/deployment/installation.md`.

The module is `Installer`, which `config/sanitube.php` has reserved since
ARCH-001. It registers through the existing module loader; no bootstrap change
was needed.

## The service is the installer, not the command

INS-002 puts a web form in front of exactly this. A web installer that
reimplemented the stages would be a second installer — one that gets a fix the
other does not — so `InstallationService` owns the stages, their order and
their idempotence, and `InstallCommand` is a terminal in front of it.

What belongs in the command is the conversation: asking for the owner's details,
reading the password without echoing it, and reporting each stage as it
finishes so a run that fails at stage six says which six ran.

## Idempotence, and no rollback

Every stage is safe to re-run, because re-running is what an operator does when
the first attempt failed at stage six. A stage with nothing to do reports
**SKIPPED with the reason** — "an application key is already set, it was left
alone" is a more useful answer than a silent success.

There is deliberately **no rollback**. Undoing a successful migration because a
later stage failed would turn a recoverable situation into a lost database. The
first five stages stay done and the next attempt starts from the sixth.

## What it refuses to do

| Refusal | Why |
| --- | --- |
| Overwrite an existing `.env` | "the installer replaced my configuration" is not recoverable from a message |
| Replace an existing `APP_KEY` | it decrypts existing sessions and any encrypted column; replacing it logs everyone out and makes encrypted data unreadable |
| Modify `.env` without a backup beside it | the operator running the installer is frequently doing so *because* something is already wrong |
| Accept a password as an option | options land in shell history and in every process listing on the machine |
| Print any secret | these strings go to a terminal and, in INS-002, to a browser |

The backup is taken **once per run**, not per write — the useful copy is the
state before the installer touched anything — and is chmod `0600`, because it
holds every credential the original does and group-readable is how a shared
host leaks it to the account next door.

The rewrite is line-based rather than parse-and-serialise. A round trip would
normalise the file: comments dropped, ordering changed, quoting rewritten. An
operator who opens `.env` afterwards and finds their annotations gone learns not
to trust the installer with the file — and those comments are frequently the
only record of why a value is what it is. A value containing a space or a `#`
is quoted, because every dotenv parser truncates it otherwise and database
passwords contain both.

## Three defects found by building it

**1. Preflight would have refused every first install.** The `scheduler`
capability reports unavailable until a cron entry has fired at least once,
which on a machine being installed for the first time it never has. The first
smoke run refused with *"This environment cannot run SaniTube yet: Database,
Scheduler."*

The fix is in the installer, not the detector — the detector is right that a
scheduler which never ran is a real finding for a *running* installation. What
was wrong was preflight treating a fact about the installation's history as a
prerequisite. Two capabilities are now excluded by name with their reasons, and
the list is short on purpose: a preflight that skips checks stops meaning
anything.

**2. `--skip-owner` always exited non-zero.** Verify correctly reported the
installation incomplete, which made the flag useless to the deployment script
it exists for. `verify(ownerRequired: false)` now reports success once
everything else is in place and says plainly that the account still has to be
created.

**3. `.gitignore` did not cover the installer's own backups.** It has
`.env.backup`; the installer writes `.env.backup-<timestamp>`, which that
pattern does not match. A file containing every credential on the installation
was addable to git. Fixed, with the reason in the file so the next person does
not "tidy" the two patterns into one.

## A test that was defective, and how that was found

The mutation removing the overwrite guard from `EnvironmentFile::createFromExample()`
**stayed green**. The service checks `exists()` before it ever calls that
method, so the service-level test passed with the inner guard gone.

That guard matters: INS-002's web installer will reach the method without the
outer check. A test exercising `EnvironmentFile` directly was added, and the
same mutation now turns it red.

This is precisely what the mutation discipline is for — the test was covering
the behaviour at one level and reading as though it covered it at two.

## Guardrails proven

Six regressions injected; **five turned a test red immediately, one exposed a
defective test** which was then fixed and re-proved:

| Injected regression | Caught by |
| --- | --- |
| writes without a backup | 3 tests |
| the backup is world-readable | the backup is not readable by the rest of a shared host |
| an existing `.env` overwritten from the example | **survived** → new test added → now caught |
| an existing `APP_KEY` regenerated | an existing application key is never replaced |
| an unknown counts as installed | an unknown is never treated as installed |
| a second owner created on re-run | a second run does not create a second owner |

## Unknown is not false

`InstallationStatus` carries nullable fields, and `isComplete()` requires all
four to be **definitely** true. An installer that read "I could not reach the
database" as installed would consider itself finished and lock itself out of the
machine it was supposed to set up. "There are no tables" and "I could not look"
lead to opposite next steps.

Status is derived from the installation itself rather than from a marker file.
A `installed.lock` says somebody once ran the installer; it says nothing about
whether the database still has tables, whether an owner still exists, or whether
the file arrived with the rest of a deployment copied from another server.

## Tests

21 new tests. **880 PHP tests / 3734 assertions**, 1 skipped (the real ffprobe
run), plus 16 component tests. PHPStan level 6 clean, no baseline. Pint clean.
vue-tsc clean.

Every test works against a **temporary `.env` in its own directory**. A test
pointed at the repository's real environment file would rewrite the machine it
runs on — and the guarantee this class exists for, that a backup precedes any
modification, is exactly the one you cannot verify by destroying the evidence.

## Shared hosting stays the baseline

No root, no Docker, no Redis, no Supervisor, no persistent worker. The
documentation gives the cron line for the scheduler and the
`--stop-when-empty --max-time=55` cron form of the queue worker for hosts that
will not run a long-lived process, and says to point the document root at
`public/` — because everything above it, `.env` included, is readable over HTTP
otherwise.

## Architecture amendment

**None.** No migration, no new table, no invariant touched. One new module in
the slot already reserved for it.

## Review

Not `REVIEW_REQUIRED` under the standing policy: installer and deployment
tooling. It creates the first OWNER through the same `forceFill` path SEC-001
established, changes no authorization semantics, and every write it makes to
`.env` is preceded by a backup.
