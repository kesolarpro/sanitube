# ENR-001 — asking a model for a shape instead of hoping for one

## The rule

**Never parse free-form prose when a schema can be required.**

AI-001 shipped `AiPrompt::$expectsJson`, which sends OpenAI `response_format:
{type: "json_object"}` and sends Anthropic nothing at all. That guarantees the
answer parses and **nothing about what is in it**: the model picks the keys,
and a model that picks different keys next month is a silent data-quality
change nobody gets told about. On the Anthropic side it guaranteed nothing
whatsoever — the request was "please answer in JSON", in prose, and hoped.

Both vendors can be *made* to answer in a named schema. This ticket makes them.

## Researched, not recalled

Per the standing rule, both contracts were read from official sources before
any code was written.

**OpenAI** — the official `openai/openai-openapi` specification,
`ResponseFormatJsonSchema`:

```
response_format: {
  type: "json_schema",
  json_schema: { name, description, schema, strict }
}
```

`name` is required and documented as a-z, A-Z, 0-9, underscores and dashes to a
maximum of 64. `strict` defaults to false; when true, "the model will always
follow the exact schema defined in the `schema` field" and only a subset of
JSON Schema is supported.

**Anthropic** — the official tool-use documentation. There is no
`response_format` on the Messages API, and its absence is the vendor's design
rather than a gap in the adapter. The shape is a tool:

```
tools: [{ name, description, input_schema, strict: true }]
tool_choice: { "type": "tool", "name": "…" }
```

`name` must match `^[a-zA-Z0-9_-]{1,64}$` — the same constraint OpenAI states in
prose, arrived at independently, so `AiSchema` enforces it once rather than
letting whichever vendor is configured discover it as a 400. The answer arrives
as a `tool_use` content block whose `input` **is** the object, with
`stop_reason: "tool_use"`. `tool_choice` has exactly four forms — `auto`, `any`,
`tool`, `none` — and only `tool` forces a particular one.

Two documented caveats recorded but not relied on: with *manual* extended
thinking (`thinking: {type: "enabled"}`), `any` and `tool` are unsupported and
return an error; and combining `tool_choice: {"type":"any"}` with `strict: true`
guarantees both that a tool is called and that its input matches. This adapter
enables no thinking and forces a single named tool, so neither applies today —
but a later ticket that turns thinking on needs to know.

## One schema in, one object out

`AiSchema` is a name, a description and a JSON Schema. A caller writes it once
and never learns which vendor answered:

- OpenAI gets a `response_format`.
- Anthropic gets a one-tool request, and the tool's `input` is re-encoded to
  JSON so `AiCompletion::json()` decodes both the same way.

The description is **required**, not optional. Anthropic's guidance is blunt
that it is the single largest factor in whether a schema gets filled in
correctly, and a schema named `track_metadata` with nothing else attached is one
the model has to guess the purpose of.

The Anthropic tool block is matched **by name**. An account with a server tool
enabled can return a tool block this request never asked for, and taking the
first one would read an unrelated call's arguments as a suggestion about a
recording.

## Malformed output is a failure, never partial data

Enforced once, in `RunPrompt`, so it holds for every provider including ones
written later.

The tempting alternative is to salvage — pull the object out of a fenced code
block, take the first `{`, regex the fields that did arrive. Every one of those
turns a model that ignored the contract into a suggestion somebody accepts
without knowing it was reconstructed. **A schema that is enforced most of the
time is not enforced.**

The model's text is not carried into the failure message: it is output over this
installation's catalogue data, and a failure message reaches a screen. And the
call is recorded in the ledger as *failed*, because "why did nothing get
suggested last night" only has an answer if it says so.

## A security inconsistency, closed

`HttpAiProvider` put the vendor's **response body** into the failure message,
redacted. TRN-002 had already settled that question for transcription and
reached the opposite conclusion, so the two halves of the platform disagreed.

Redaction masks the credential this installation is configured with. It cannot
mask the *prompt*, and a vendor's error routinely quotes the request back — on
these endpoints that means catalogue data, on a failure message that reaches a
browser. The status code is what an operator acts on: 401 is a key, 429 is a
rate limit, 5xx is theirs. So the code is kept and the body is dropped.

`a_failure_message_never_carries_the_api_key` was updated rather than deleted,
to the stronger claim, with its own note saying what changed and why.

### E5 found a defective test, and a trap worth writing down

`Http::fake()` called twice for the same URL **does not replace the first
stub.** The first registered one keeps answering; a later `fake()` for the same
URL is dead code. Verified directly rather than assumed:

```
Http::fake(['https://example.test/x' => Http::response(['n' => 'first'])]);
Http::fake(['https://example.test/x' => Http::response(['n' => 'second'])]);
Http::get('https://example.test/x')->body();   // {"n":"first"}
```

So a `foreach` that re-fakes the same endpoint per iteration tests its **first**
case N times and reports N passes. My refusal test was written exactly that way
and looked thorough. `Http::fakeSequence()` is the correct tool, and the tests
now assert `Http::assertSentCount()` so a silently-collapsed loop shows up.

**The same defect was already merged in TRN-002.**
`a_response_without_usable_text_is_a_refusal_rather_than_an_empty_transcript`
looped over three broken payloads and only ever exercised the first. Corrected
here rather than left looking like coverage it never had, and a repo-wide scan
found one further looped `Http::fake` — in this ticket's own vendor-body test,
where it is safe because the two stubs match *different* endpoints and an
unmatched stub falls through. That one carries a comment saying so, and E14/E15
are the empirical proof both iterations really run.

- **E18** found a real gap: `withModel()` rebuilds the prompt field by field,
  which is precisely the constructor that silently loses whatever was added to
  it last. A dropped schema is not a visible break — the call succeeds, the
  model answers in prose, and the refusal surfaces somewhere else entirely.

## Who calls this in production?

Nothing yet, and deliberately. `AiSchema` is a capability, not a feature: the
first caller is the enrichment task that turns a transcript into suggested
metadata, and that is ENR-002. What this ticket proves is that the capability
reaches both real vendors in the shape each of them documents — the OpenAI and
Anthropic tests substitute no provider and assert the exact request body that
leaves.

Wiring an enrichment task here would have meant shipping the prompt, the storage
and the review semantics in the same change as the transport, and the transport
is the part with two vendor contracts to get right.
