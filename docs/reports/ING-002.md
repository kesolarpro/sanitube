# ING-002 — Starting an Import Without a Terminal

**Status:** delivered
**Base:** `01920c6` (main, after CAT-002)
**Branch:** `claude/ing-002-start-import`

---

## What this ticket is actually about

`sanitube:import` remains the right tool for the initial catalogue. Nine
hundred files are a manifest and a long afternoon, and a browser tab is the
wrong place to keep either.

What was missing is the ordinary case afterwards: a label that dropped twenty
new masters in a folder and had to be given SSH to bring them in.

**Nothing is imported inside the request.** `StartIngestionBatch` creates the
batch and queues the work; the queue does the rest and survives the tab being
closed. A controller that fetched, hashed and verified inline would half-run
whenever somebody navigated away — the exact shape ING-001 was designed not to
have, and the test asserts the jobs are *pushed* rather than run.

The person is recorded on the batch. An import is where several hundred things
enter the platform at once, and "who started this" is the first question asked
when one of them turns out to be wrong. The API cannot answer it — it
authenticates a shared token, not a person — so this is the first path that
does.

## Three refusals that were not distinguishable

The screen needed to tell a person *which* thing was wrong, and the domain
could not say.

### `IngestionException` had one code where it needed several

`failureCode` is a **persisted** column: it describes why an *item* failed to
import and a retry policy branches on it. Several distinct *request* refusals
share `UNSUPPORTED_SOURCE` there — a blank prefix, a managed prefix, a manifest
supplied alongside a prefix. Fine for a retry policy, useless on a screen,
where they need three different sentences.

So `IngestionException` gained a `reason`, separate from the failure code and
defaulting to it. Adding cases to a populated enum would have been a migration
for the sake of a label.

### "Nothing selected" reported a path nobody gave

An empty request answered `Nothing to import under [(no references)]`. The
message reads almost like "nothing found under the prefix you gave", and the
fixes are opposite: one is a typo in a path, the other is a form submitted
empty. It now answers `NOTHING_SELECTED`.

### A folder and a list silently dropped the list

`StartIngestionBatch` documented it — *"explicit object keys; ignored when a
prefix is given"* — and a manifest beside a prefix was already refused for
exactly this ambiguity. The two were answered differently only because nobody
had put the fields on one screen next to each other yet, and the person who
typed the list would never have learned it was ignored. Now
`AMBIGUOUS_SELECTION`.

## Two pre-existing tests got stronger

`IngestionPipelineTest` asserted on English substrings — `'SaniTube manages'`,
`'Importing an entire store'`. They assert on codes now. Strictly stronger in
both directions: the old versions went green on a reworded message and red on
a translated one.

The empty-selection test also covers both shapes now — a blank prefix *and*
nothing supplied at all — which is what turned up the wrong refusal above.

## The stylesheet was built from a runtime cache

`resources/css/app.css` declared:

```css
@source '../../storage/framework/views/*.php';
```

That is the **compiled Blade cache**. It made the production stylesheet depend
on whether the application had happened to render anything before
`npm run build` ran: a fresh clone produced 34.7 kB and a warmed machine 50.8
kB, from the same commit, the difference being compiled vendor Blade the
interface never renders.

The size was not the problem. An asset pipeline that reads a runtime cache is
one whose output nobody can reproduce — CI builds one stylesheet, a developer
builds another, and neither is wrong.

Replaced with `@source '../../src/**/*.blade.php'`, which covers what the
cache was accidentally providing: module views live beside their module rather
than in `resources/`, and `src/Identity/Resources/views/login.blade.php` is the
sign-in page — the one screen a person sees before the Vue application loads at
all. A glob rooted at `resources/` never reached it.

Verified by diffing a cold-cache build before and against after: **no selector
dropped, none added.** What changed is that the build no longer varies.

Both properties are now asserted by `ViteEntrypointTest`, which is where this
codebase keeps its "the build wiring is still wired" checks.

## Mutation pass — 7 injected, 7 killed

| # | Mutation | Result |
|---|---|---|
| M1 | An empty selection reports the wrong refusal again | killed |
| M2 | A folder and a list silently drop the list again | killed |
| M3 | The batch stops recording who started it | killed |
| M4 | The refusal travels as the domain's English | killed |
| M5 | Every refusal collapses to one reason again | killed |
| M6 | The import route loses its role guard | killed |
| M7 | The stylesheet is built from the view cache again | killed |

**M6 survived the first pass, and the reason is the more interesting finding
of this ticket.** The mutation removes `can.role:catalogue` from the route
group, and the test that posts past the interface as a MEMBER still got a 403
and stayed green.

The cause was a leftover `bootstrap/cache/routes-v7.php`, written by
`DeploymentTest` running `sanitube:deploy` earlier in the session. The suite was
matching against the *cached* route table, which still carried the middleware
the source no longer had. Clearing it and re-running `route:list` showed the
guard genuinely gone.

So the stale-cache defect CAT-002 fixed does not only make a config value read
as null. **It can make a removed authorization guard look enforced, with the
test suite agreeing.** With CAT-002 merged into this branch, M6 dies.

## Authorization

The route sits behind `can.role:catalogue`, the guard candidate review and the
studio writes use. A MEMBER may watch imports and start none — asserted both
ways: the form is absent from the payload, *and* a MEMBER posting past the
missing form gets a 403.
