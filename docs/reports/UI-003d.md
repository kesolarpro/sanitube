# UI-003d — Catalogue: assets and the signed preview

The last catalogue resource, and the only one that creates a credential.

**REVIEW_REQUIRED.** This ticket introduces a new capability: handing out
time-limited access to stored objects, including masters. The policy it
implements was arbitrated in advance and is followed exactly, but the code that
enforces it should be read by somebody other than its author before it merges.

## What a preview actually is

A signed URL is a **bearer credential**. Whoever holds it can fetch the object
until it expires, with no further check. Three consequences shape the design.

**It is minted on request, never on a page load.** `AssetDetailQuery` carries no
URL at all — the payload says whether a preview *could* be minted, and why not
when it could not. Rendering a detail page for an asset somebody merely clicked
on must not create a credential.

**It is a POST, not a GET.** A GET that minted one would be prefetched by
browsers, followed by link checkers, cached, and replayed from history — each
producing a live credential nobody asked for.

**It is never persisted and never logged in full.** Storing one would turn a
fifteen-minute credential into a permanent one sitting in every backup. What is
logged is the audit fact — which asset, by whom, expiring when — with no URL, no
path and no disk.

## The policy, in one place

`AssetPreviewPolicy` is a class rather than a few `if`s in a controller because
it is the boundary that protects the masters, and it should be auditable in one
reading.

- **An allow-list of kinds**, not a deny-list. A kind added to the domain later
  is refused until somebody decides otherwise — the safe direction for a list
  governing access to audio. Licence documents and distribution exports are not
  preview material.
- **A master must be VERIFIED.** Playing an unverified master hands out bytes
  nobody has confirmed are the bytes we meant.
- **Masters and stems additionally require the ability to write the catalogue.**
  Reading that a master exists is ordinary catalogue work; *listening to it* is
  closer to holding it, and MEMBER is a role that browses without being trusted
  with the material. **This is the one judgement call in the ticket that was not
  pre-arbitrated, and it is the thing most worth disagreeing with.**
- **If the provider cannot issue an expiring URL, the answer is "preview
  unavailable".** Never a permanent URL, never a public object.

The TTL is **clamped in code** to 300–900 seconds, default 900. A misconfigured
environment must not be able to mint day-long credentials with nothing looking
wrong.

## A defect this ticket found in its own tests

The first run refused every preview, including the ones that should have
succeeded. The cause: the default `local` storage provider cannot issue expiring
URLs on a plain filesystem disk.

That is worth stating plainly, because of what it meant for the test suite:
**the negative test — "a provider without temporary URLs gets preview
unavailable" — was passing for the wrong reason.** It would have passed against
a policy that never checked anything, because the environment refused
everything anyway. Every positive assertion would have been dead.

Fixed by registering `InMemoryStorageProvider`, which can both sign and refuse
on demand, so both paths are exercised deliberately rather than by accident.

## Guardrails proven

Five regressions injected; **six tests went red** before any was trusted:

| Injected regression | Caught by |
| --- | --- |
| signed URL added to the detail payload | detail never carries a signed URL; opening the page mints nothing |
| VERIFIED requirement removed | an unverified master is never previewable |
| role check removed | a member may see a master exists but not hear it |
| kind allow-list removed | a document is not preview material |
| TTL clamp removed | the TTL is clamped rather than trusted |

## The list

Ordered by `(created_at, uuid)`. Assets have no title, and the two fields that
would read like one — `original_filename` and `path` — are exactly what must not
be exposed. Ordering by either would publish them inside the cursor, which
travels in the URL.

`no_payload_reveals_where_an_asset_lives` asserts both the forbidden key *names*
and the actual path *value* are absent from the list and the detail alike.

## Tests

**16 new tests. 708 PHP tests / 2774 assertions**, 1 skipped (the real ffprobe
run), plus 16 component tests.

## Localisation

All new strings in en / fr / es / it / pt / de, including asset kinds and the
five preview refusal reasons. Refusals travel as **reason codes**, translated in
the browser — the server never sends a sentence, and the codes are coarse so a
refusal is not a probe for finding assets in interesting states.

## Review corrections C1–C3

**C1 — storage provenance is canonical. This was a real defect and the review
was right to catch it.**

Both the policy and the minting service resolved `StorageManager::defaultName()`.
That is wrong for any asset whose bytes live on a different configured backend,
and it fails in three distinct ways: a broken link when the default cannot serve
the path; a *working* link to somebody else's object when two backends share a
path; and every historical asset silently "moving" the moment
`storage.default` changes.

`Asset.disk` records the SaniTube provider name at the moment the bytes were
written and is immutable from then on — it is listed in
`Asset::IMMUTABLE_ONCE_STORED`. Both call sites now resolve `provider($asset->disk)`.

No new abstraction was needed inside Storage, and none was added to Ui:
`StorageManager::provider($name)` already *is* the mapping boundary, and the
interface passes it a name the asset recorded. Ui holds no knowledge of disks or
drivers.

The failure path is total. An unknown provider — one removed from configuration
— and an unreachable one both mean **preview unavailable**. There is no fallback
to the default, because the tempting fallback is precisely the bug.

**C2 — a dedicated budget for minting.** 60/minute, keyed on the authenticated
user rather than the address: an office behind one IP must not share a quota,
and one compromised session must not spend everybody else's. An IP-keyed
fallback of 10/minute exists for a request with no user — which `auth` should
already have refused, so it is there only so the limiter cannot be bypassed if
that ever stops being true. Ordinary catalogue GETs are untouched, and a test
asserts seventy consecutive detail reads still succeed.

**C3 — the credential response is never written down.** `Cache-Control: private,
no-store, max-age=0` and `Pragma: no-cache` on success *and* on refusal.
`no-store` rather than `no-cache`: the latter permits writing the response down
on a promise to revalidate later, which for a bearer credential is the whole
problem. `Pragma` is for HTTP/1.0 intermediaries, which some corporate proxies
still are. The refusal is uncacheable too, because whether a person may preview
an asset depends on their role and the asset's status, and a cached "no" would
survive either changing.

### Mutation testing

All three corrections were injected in their broken form and **seven tests went
red** before any was trusted:

| Injected regression | Tests that caught it |
| --- | --- |
| `defaultName()` instead of `$asset->disk` | signed by the recorded provider; changing the default moves nothing; identical path on two backends |
| throttle removed from the route | minting is rate limited; one person's quota is not another's |
| cache headers removed | preview response may never be written down; a refusal is uncacheable |

**One honest limitation of that exercise**, worth recording rather than glossing:
the two *refusal* tests — unknown provider, and a backend that cannot sign — did
**not** go red under the `defaultName()` regression. With the manager's default
resolving to the filesystem `local` provider, which cannot sign anyway, they
were refused for the right outcome by the wrong route. They remain valid for
what they claim (an unknown or unsigning backend is refused), but they are not
the tests that defend provenance. The three provenance tests are.

### Verification

10 new tests. **718 PHP tests / 2928 assertions**, 1 skipped (the real ffprobe
run), plus 16 component tests.

Everything the review asked to keep is kept: POST only, authenticated and
active, kind allow-list, `canWriteCatalogue()` for masters and stems, VERIFIED
for restricted kinds, 403 for known-but-forbidden, TTL clamped 300–900 with a
default of 900, never persisted, never logged in full, no path or disk in any
response, and no public URL fallback.

## Architecture amendment

**None.** No invariant, migration, column or relation is modified. One config
key added (`assets.preview.ttl_seconds`).

## What a reviewer should push on

1. **Masters and stems require `canWriteCatalogue()`.** Is that the right line?
   It is defensible and it is conservative, but it is mine, not arbitrated.
2. **403 rather than 404 on a refused preview.** The asset's existence is
   already known to anyone who reached its detail page; hiding it further would
   be theatre. Worth confirming.
3. **The audit log line** records asset UUID, kind, user UUID and expiry. That
   is deliberately not the full audit-log ticket, which comes later.
