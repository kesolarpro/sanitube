# ART-004 — un appel payant obtient un plafond avant d'obtenir un bouton

## Le problème

ART-003 a mesuré si la génération de pochettes était possible sur une
installation et l'a dit — puis **s'est délibérément arrêté avant de câbler un
déclencheur**. `GenerateArtwork` n'avait aucun enregistrement, rien ne comptait
ses requêtes, et donc aucun plafond ne pouvait exister. Brancher un générateur
payant sur un bouton sans plafond aurait été la seule chose que les règles de
coût interdisent.

## Sécurité opérationnelle, pas finance

Cela compte des **requêtes**, parce que les requêtes sont ce que la plateforme
peut observer. Il n'y a ni prix, ni devise, ni solde, ni facture nulle part.
Un test le vérifie en balayant le code source des cinq fichiers concernés,
commentaires retirés — ces fichiers *parlent* d'argent pour dire qu'ils n'en
détiennent pas, et un garde incapable de distinguer la prose du code aurait
chassé cette discussion hors du dépôt.

`estimated_cost_hint` est une **chaîne**, délibérément : une note qu'un
fournisseur peut renvoyer sur son propre palier tarifaire, enregistrée parce
qu'un opérateur comparant deux fournisseurs la veut — et typée de sorte que
rien ne puisse être tenté de l'additionner.

## La table est le registre

`artwork_generations` ne s'accompagne d'aucun compteur ailleurs, pour la raison
que `GenerationSpendGuard` donne à propos de la musique : `submitted_at` est
écrit exactement au moment où une requête quitte ce serveur pour un
fournisseur. Un total parallèle serait une seconde source de vérité et
divergerait la première fois qu'une ligne serait supprimée à la main.

**La revendication centrale du ticket : une requête refusée avant soumission
n'a pas de `submitted_at`, et ne compte donc jamais contre le plafond qui l'a
produite.** Compter par résultat se tromperait dans le sens où quelqu'un paie :
un plafond qui compterait ses propres refus verrouillerait une installation
définitivement après un mauvais après-midi.

## Deux moments, délibérément séparés

`RequestArtworkGeneration` enregistre une intention et ne coûte rien.
`SubmitArtworkGeneration` est l'endroit où une requête quitte le serveur, et
**re-pose toutes les questions** — parce qu'une file peut l'exécuter des heures
plus tard avec cent frères devant elle, et que le plafond qui compte est celui
lu au moment où la requête partirait réellement.

Demander aussi à l'entrée n'est pas redondant : c'est ce qui permet de dire
« non » immédiatement à quelqu'un qui clique, dans sa langue, plutôt que de le
laisser regarder une ligne échouer silencieusement dans une file.

## Les garde-fous

| | |
|---|---|
| Plafonds | fenêtres glissantes 24 h / 168 h / 720 h, zéro = pas de plafond (défaut livré) |
| Disjoncteur | échecs consécutifs par fournisseur, avec temps de refroidissement |
| Interrupteur dédié | `artwork.generation_enabled` |
| Arrêt global | OPS-002 `BackgroundWork`, honoré **en plus** de l'interrupteur |
| Réclamation atomique | `UPDATE` gardé, expirable — une redélivrance ne dépense pas deux fois |
| Limiteur de débit | 6/minute par utilisateur sur la route |
| `tries` du job | **1**, délibérément |

Les fenêtres sont glissantes et non calendaires : un mois calendaire exige un
fuseau horaire pour avoir un sens et une remise à zéro dont il faut se souvenir,
et il se contourne en lançant une série à 23 h 55.

Le plafond est le budget ; le limiteur est le robinet. Ils répondent à deux
questions différentes : combien cette installation accepte de dépenser, et à
quelle vitesse quiconque peut le dépenser.

## Ce qu'une pochette générée n'est pas

**Générer n'est pas choisir.** Une image terminée devient un `Asset` ordinaire,
vérifié et mesuré par ART-001 comme n'importe quel autre, et doit encore être
sélectionnée comme pochette via le sélecteur existant. Un test l'asserte : après
une génération réussie, `cover_asset_id` de la release est toujours nul.

Aucune URL de fournisseur ni secret temporaire n'est stocké comme média
canonique — les octets sont écrits dans un fichier temporaire puis stockés, et
le temporaire est supprimé dans un `finally`.

## Mutations — 10 posées, 1 survivante corrigée

| | Mutation | Résultat |
|---|---|---|
| M1 | le plafond compte par `created_at` au lieu de `submitted_at` | **survivante → test ajouté → tuée** |
| M2 | le plafond n'est pas relu au moment du départ | tuée |
| M3 | la réclamation n'est plus atomique | tuée |
| M4 | `submitted_at` écrit après l'appel plutôt qu'avant | tuée |
| M5 | le disjoncteur ignore le refroidissement | tuée |
| M6 | un succès ne referme plus le disjoncteur | tuée |
| M7 | la pause globale est ignorée | tuée |
| M8 | le contrôleur ne met plus le travail en file | tuée |
| M9 | une pochette générée devient automatiquement la couverture | tuée |
| M10 | la route sort de `can.role:catalogue` | tuée |

**M1 visait exactement la revendication centrale du ticket, et mon test ne
l'attrapait pas.** Le test « un refus ne compte jamais » utilisait un
fournisseur indisponible — cas où `RequestArtworkGeneration` refuse **avant de
créer la ligne**. Sans ligne, compter par `created_at` donne aussi zéro : le
test passait pour la mauvaise raison.

Le cas qui distingue les deux est celui des requêtes **enregistrées, mises en
file, puis refusées au moment de partir** : elles existent comme lignes et ne
coûtent rien. Un test les crée explicitement, sans `submitted_at`, et vérifie
que le plafond n'en tient pas compte.

*(Ce test a d'abord échoué en ouvrant le disjoncteur — cinq échecs d'affilée,
seuil par défaut cinq. Correct de la part du code ; le disjoncteur est désormais
désactivé dans ce test pour isoler la revendication mesurée.)*
