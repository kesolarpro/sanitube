# ENR-003 — how much this installation is willing to spend, and when it stops

## Operational safety, and deliberately not finance

Everything in this ticket counts **calls**, because calls are what the platform
can actually observe. There is no price, no currency, no balance and no invoice
anywhere in it, and it is not a step towards any of those. The question it
answers is "should we keep going", which is an operations question, and the
answer is a number of requests.

SaniTube's scope excludes finance outright, and a spend guard is exactly where
that boundary erodes: one currency column, then a rate, then a balance.
`nothing_here_holds_money` asserts the boundary rather than trusting it to a
reviewer's memory — it strips comments and scans the remaining code for
`currency`, `price`, `balance`, `invoice` and their neighbours.

*(That test failed the first time it ran, on the docblock sentence promising
there was no currency. It now reads code rather than prose, which is what it
should have done to begin with.)*

## The gap this closes

The failure is specific, and this platform's design has walked up to it twice.

A backfill over four thousand masters enqueues four thousand jobs. OPS-002's
backlog ceiling bounds **how many of those sit on a queue at once** — and bounds
nothing whatsoever about how many reach a vendor over the following week. A
queue that drains steadily spends steadily. The first sign of it is an invoice.

`ALREADY_WAITING`, the pause switch and the backlog ceiling all bound *work
queued*. None of them bounds *calls made*. That was the honest gap ENR-002's
report ended on, and this is it closed.

## `attempted` is not `succeeded`

The single design decision everything else follows from.

The ledger deliberately records calls that never happened — an installation with
no key, a request a ceiling refused — because "why did nothing get suggested
last night" is answerable only if the non-events are written down. That makes
`succeeded` the wrong column to count spending by, **in both directions**:

- a refused-before-sending row cost nothing and would inflate a quota;
- a vendor call that returned a 500 cost a request and would be missed.

So attempt and outcome are two columns. `AiCompletion` gains `attempted`, false
for the three refusals that never leave this server (no key, quota exhausted,
circuit open) and true otherwise.

The consequence that matters most: **a refusal does not count against the
ceiling that produced it.** A quota that counted its own refusals would latch
shut and never reopen, because every attempt to check would push the count
further past the line. That is asserted directly.

Existing rows backfill to `true`. Every one was an attempt or an
unavailable-provider refusal, and the conservative reading of an unknown row is
that it cost something — a quota that under-counts history is a quota that lets
an installation past a ceiling it had already reached.

## Rolling windows

Daily, weekly and monthly, as **rolling** windows rather than calendar ones. A
calendar month needs a time zone to be meaningful and a reset somebody has to
remember, and both go wrong quietly. "The last 24 hours" needs neither, and
cannot be gamed by starting a sweep at 23:55.

The **longest** exhausted window is the one reported, because "you have run out"
and "you have run out until the 3rd" are different instructions and the longer
one is still true tomorrow.

Counted from the ledger rather than from a counter this platform keeps, for the
reason `BacklogGuard` gives about queue depth: a counter is a second source of
truth and drifts the first time a row is removed by hand.

`0` means no ceiling and is the shipped default. A platform whose first
experience of an AI feature is a refusal is a platform nobody turns the feature
on twice.

## The circuit breaker

A vendor having an outage answers every request identically and immediately, and
a queue worker holding two thousand enrichment jobs will discover that two
thousand times — each one possibly billed, all of them in the minutes before
anybody notices.

**Derived from the ledger, with no state of its own.** The alternative is a row
or a cache key holding "the circuit is open", and both drift from what actually
happened and need something to reset them. Reading the last few invocations
answers the question directly and cannot disagree with the record.

It is **half-open for free**: once the cooldown passes, the next call goes
through, and if that one fails it becomes the newest failure and the window
starts again. There is no separate probe state to get wrong.

Three details each earned their own test:

- **Per provider.** An OpenAI outage is not a reason to stop asking Anthropic.
- **Only attempted calls count.** A run of "no key configured" rows is a
  statement about this installation, not about whether the vendor is answering.
- **The cooldown is checked on the newest failure.** Without it the breaker
  latches permanently the first time a provider has a bad afternoon and is then
  left unused — and nothing would ever reopen it.

## Order, and refusals that are not exceptions

The ceiling is asked **before** the breaker: the operator's own decision
outranks a measurement, and "you have reached your ceiling" is the more
actionable of the two.

Both produce a **completion**, never an exception. AI in SaniTube assists a
person who could do the job without it, and a feature that threw when a ceiling
was reached would break the workflow it exists to help.

Both gates live in `RunPrompt`, the one place every call already passes through,
so a caller that resolved a provider for itself cannot bypass them.

## Max retry

The brief asks for one; the platform's answer is **one attempt**, stated on the
two jobs that spend money rather than left to a framework default somebody can
change without ever seeing them. A retried job is a second billed call, and
deciding whether to pay twice is a person's decision rather than a queue
worker's — the same reasoning `HttpAiProvider` already gives for not retrying at
the transport.

## Cost estimate

**Not implemented, deliberately.** §13 lists it as optional, and the honest
version of it needs per-model prices that change without notice, a currency, and
a token-to-price mapping this installation cannot verify. A wrong estimate on a
screen is worse than no estimate, because somebody plans against it.

What is reported instead is calls remaining per window, which is a number this
platform actually knows. `null` for an unconfigured window, rather than a very
large number, so "no ceiling" reads as no ceiling.

## Who calls this in production?

Everything that asks a model anything, because `RunPrompt` is the only way to.
The transcription path is **not** covered by these ceilings and the report says
so plainly: `TranscribeAsset` calls a `TranscriptionProvider` directly rather
than going through the AI ledger, so its spend is bounded by
`SANITUBE_TRANSCRIPTION_AUTOMATIC` being off, by the backlog ceiling and by
`sanitube:transcription:backlog --limit`, and not by a call quota.

Unifying the two ledgers is a real ticket and not a small one — a transcription
is billed by audio minute and a completion by token, so a single "calls" number
would flatten two different things. It is recorded here rather than quietly left
looking covered.
