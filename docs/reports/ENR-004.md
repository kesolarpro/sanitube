# ENR-004 — a person answering what a model proposed

## Where the boundary actually is

ADR-0016 says canonical catalogue fields are never silently overwritten by AI.
Every ticket so far has honoured that by **storing opinions and stopping**.
This is the ticket where the boundary is enforced against a click rather than in
a docblock: it is the only path by which something a model said becomes
catalogue data.

## Acceptance is not a copy

`DecideSuggestion` writes no catalogue column. It calls `SetTrackMetadata` — a
new service in **Catalog**, not in Enrichment — which applies the catalogue's own
validation and produces the catalogue's own refusals.

That placement is the whole design. A path that wrote `tracks.title` from an
enrichment row would be a second, weaker editor with a model on the end of it,
and it would drift from the real one the first time a rule changed. So the
service that accepts a suggestion and the service a person uses to edit a track
directly are **the same service**, and `the_catalogue_refuses_what_it_would_
refuse_from_a_person` is the test that says so: a released track cannot be
rewritten by an accepted suggestion, because its metadata is what a distributor
was given.

The refusal happens **inside the transaction**, so a rejected write leaves the
suggestion undecided rather than marked accepted with nothing written.

### What `SetTrackMetadata` will write

`title`, `language_code`, `genre_primary`, `genre_secondary`. A closed list, and
short. Everything on it is editorial — something a person decides — and
`duration_ms` and `bpm` are deliberately absent because Media measured them from
the file, and a person typing over a measurement is a bug rather than a feature.

`language_code` is validated as a code, never a word, because it is read by the
distribution export where a word instead of a key is a rejected delivery. A
cleared genre becomes `null` rather than `''`, because an empty string in a
nullable column reads as "set to nothing" in some queries and "unset" in others.

## Edit-before-accept is the ordinary case

A model's title is right about half the time and *nearly* right rather often. A
queue offering only accept-or-reject would train people to accept nearly-right,
which is the failure mode that puts a wrong title in front of a distributor.

So every field on the accept request is optional: sending none accepts what the
model proposed, sending one replaces it. The distinction between an **absent**
field and a **present empty** one is preserved deliberately — collapsing them
would either make clearing a field impossible, or make every acceptance blank
the fields the form did not show.

**The stored suggestion is not rewritten to match.** The row keeps what the
model actually said, because "what did the model propose" and "what did the
person accept" are different questions, and a row that answered only the second
would make a bad prompt version invisible.

That is also why the audit line carries an `edited` boolean: a prompt version
whose answers are *always* corrected before acceptance is a prompt version that
is not working, and that is invisible from acceptance counts alone.

## Three acts, three routes

Accepting, rejecting and regenerating are separate routes because they are
separate acts.

**Regeneration is not "reject, then request".** A rejection is a person saying
the model was wrong, and it is counted — a run of them against one prompt
version is how a bad prompt announces itself. Recording a rejection nobody made
would corrupt the only signal the platform has about prompt quality. So
regeneration marks the waiting suggestion `SUPERSEDED`, which is what actually
happened to it.

Regeneration is allowed past `ALREADY_WAITING` and past **nothing else**. It is
still a paid call: a trashed asset is not described because a reviewer pressed a
button twice, and an operator who paused the platform an hour ago and forgot
must not have it spent for them. It is keyed by the asset rather than by the
suggestion, for the reason trashing is — what is being asked for is a new
suggestion about this recording, and tying it to the row that prompted it would
make the same recording un-regenerable from anywhere else.

All three are behind `can.role:catalogue`, on the route, so a future action
cannot acquire the surface without the guard.

## Refusals, and their order

| Code | Why |
|---|---|
| `SUGGESTION_ALREADY_DECIDED` | Somebody has answered this one. |
| `SUGGESTION_NO_TRACK` | The asset is not the master of any track. |
| `SUGGESTION_NOTHING_TO_ACCEPT` | An acceptance carrying nothing is a rejection somebody mislabelled. |
| `TRACK_RELEASED`, `TRACK_TITLE_REQUIRED`, `TRACK_LANGUAGE_NOT_A_CODE` | The catalogue's own, unchanged. |

`NO_TRACK` is **not a gap to be filled by creating one.** A track is a catalogue
entry with a lineage, a status and a promotion decision behind it; letting an
accepted suggestion conjure one would make a model the author of catalogue
entries, which is precisely the boundary this ticket exists to hold.

The **order** is load-bearing, and a mutation proved it. Checked last, an
already-decided suggestion on a track-less asset would come back
`SUGGESTION_NO_TRACK` — a true statement about the asset and an entirely wrong
instruction to the reviewer, who would go looking for a track to create instead
of noticing a colleague had already answered.

## Two reviewers at once

Both the accept and reject paths claim the row with a **guarded UPDATE** rather
than reading the status and then writing it. A guarded UPDATE is atomic on every
engine in the matrix; read-then-write is not, and the loser of that race would
apply a suggestion on top of whatever the winner had just written.

The race is tested by holding a **stale in-memory row** — which is exactly what
the loser of a race has: its own copy says `PROPOSED` and the database says
otherwise. Without that test the guard was invisible, because the early status
check answered every case a fresh model could produce.

The four survivors:

- **H5 and H10** exposed that the guarded UPDATE was invisible to the tests: the
  early status check answered every case a fresh model could produce. The stale-row
  tests reach the race guard directly.
- **H10b** looked like a redundant fast path and is not one — it is what makes an
  already-decided suggestion report the *right* refusal code.
- **H20** — regeneration was not asking the pause switch in any test, on a route
  that spends money.
- **H25** — nothing proved a suggestion could not be applied to **somebody
  else's track**. Matching on any track instead of `master_asset_id` would
  rewrite an unrelated catalogue entry with a model's opinion of a different
  file, and it would look entirely correct afterwards, because the row it wrote
  is a plausible one. That was the most serious thing this ticket's mutations
  found.

## A finding: the audit context silently drops lists

`the_audit_line_names_the_fields_and_not_the_values` failed on first run with an
empty array where four field names should have been.

`Redaction::scrub()` keeps only keys matching `^[a-z][a-z0-9_]{0,39}$`. A PHP
**list** has integer keys, so every element is dropped and the context arrives
as `[]` — silently, with no error anywhere. That is deliberate on the audit
module's side (an audit line is not a payload) and completely silent on the
caller's.

Both new audit contexts now join their field names into a string, with a comment
saying why, so nobody re-introduces the list. Worth knowing repo-wide: **any
audit context carrying a list is being thrown away right now**, and a caller
would never find out.

## Still not done

There is no Vue screen. Everything a reviewer needs to *do* exists, is reachable
over HTTP, and is tested at that boundary — the screen that shows canonical
beside measured beside proposed beside suggested, with the four buttons wired to
these routes, is ENR-005.

`SuggestionStatus::Superseded` rows accumulate and nothing prunes them. That is
correct for now — they are the record of what earlier prompt versions said — but
an installation running enrichment for a year will want a retention policy, and
it does not have one.
