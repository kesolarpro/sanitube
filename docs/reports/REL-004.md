# REL-004 — préparer le package depuis l'écran de release

## Le problème

REL-003 a construit `PackageRelease` — la seule description d'une sortie qui
franchit la frontière vers un distributeur — et ne lui a donné **aucun
appelant**. Avant ce ticket, la seule façon de voir un package était d'écrire un
test : personne assemblant une sortie ne pouvait découvrir ce qu'une plateforme
recevrait avant qu'une plateforme l'ait reçu.

C'est le motif « construit mais pas câblé » que l'audit du parcours produit
(#91) cherchait, et l'item 3 du chemin critique qu'il nomme.

## Le défaut réel, plus large qu'un bouton manquant

Les exigences d'identifiants — un UPC sur la sortie, un ISRC sur chaque piste —
vivaient à l'intérieur de `ValidateDelivery`, qui n'est **jamais interrogé
qu'à propos d'une destination**.

Sur une installation sans distributeur configuré — le défaut livré, et l'état
dans lequel toute installation démarre — une sortie sans le moindre ISRC :

1. passait `ValidateRelease` sans une seule erreur ;
2. était marquée `READY` ;
3. et ne disait rien.

La première nouvelle serait arrivée d'une plateforme de streaming.

Ces exigences ne dépendent d'aucun distributeur. Une plateforme identifie un
produit par son UPC et un enregistrement par son ISRC ; toutes le font. Elles
sont donc répondables sans destination, et REL-004 les pose depuis l'écran de
release.

## Ce que fait ce changement

**`ValidateReleaseIdentifiers`** — extrait de `ValidateDelivery` sans
modification. `ValidateDelivery` le compose ; ce n'est pas une seconde copie, et
la mutation P9 le vérifie.

**`ReleasePackageQuery`** — trois réponses gardées séparées, parce qu'une sortie
peut être bloquée par l'une pendant que les deux autres vont bien :

| | |
|---|---|
| `package` / `refusal` | le contenu assemblé, ou un code |
| `blocking_identifiers` | UPC et ISRC — bloquent **toute** livraison |
| `destinations_configured` | zéro ⇒ un package parfait ne va nulle part |

**`prepared` ne veut pas dire « livrable »**, et l'écran ne le laisse jamais
entendre. Le packaging interroge le validateur de REL-001 ; la livraison
interroge en plus les identifiants et le distributeur lui-même.

**`GET /releases/{release}/package`** — un GET parce qu'il ne crée rien : un
« laisse-moi regarder » qui laisserait une livraison DRAFT derrière lui
deviendrait un enregistrement que quelqu'un relirait plus tard comme une
intention. Même raison que le préflight distributeur.

**Derrière `can.role:catalogue`**, pas seulement derrière l'authentification :
le package porte les noms **légaux** des contributeurs — ceux sur lesquels les
sociétés de gestion font correspondre — qu'aucun autre écran de release
n'affiche.

## Preuves

**A. PREUVE COMPOSANT** — `tests/Feature/Releases/PackageFromTheReleaseScreenTest.php`,
12 tests / 53 assertions, toutes à travers la route HTTP.

**B. PREUVE CHEMIN DE PRODUCTION** — *qui appelle ceci en production ?*
`resources/js/Pages/Releases/Show.vue`, bouton « Préparer le package » →
`GET /releases/{uuid}/package`. Avant ce ticket, `PackageRelease` n'avait aucun
appelant hors tests ; c'est vérifiable par `grep`.

## Mutations

Neuf posées, **zéro survivante**.

| | Mutation | Résultat |
|---|---|---|
| P1 | `destinations()` compte aussi `none` | tuée |
| P2 | filtre `active_marker` retiré (un UPC révoqué identifie) | tuée |
| P3 | un refus rapporté comme `prepared` | tuée |
| P4 | la route sort de `can.role:catalogue` | tuée |
| P5 | l'exigence d'ISRC supprimée | tuée |
| P6 | `getMessage()` ajouté au payload | tuée |
| P7 | `refusal_context` vidé | tuée |
| P8 | `blocking_identifiers` vidé | tuée |
| P9 | `ValidateDelivery` cesse de composer le service extrait | tuée |

### Un défaut dans le harnais de mutation lui-même

Les trois premiers passages ont rapporté **P1, P6 et P7 survivantes**. Elles ne
l'étaient pas : le script `python3 -c "..."` passait par une double couche de
quoting shell, `$name` et `$exception` étaient mangés par bash, et
`str.replace` ne trouvait rien — la mutation n'était jamais appliquée, les
tests passaient, et le harnais lisait ce succès comme une survivante.

Un harnais qui rapporte SURVIVED sur une mutation jamais appliquée est pire
qu'aucun harnais : il envoie écrire des tests pour un trou qui n'existe pas, et
il rate ceux qui existent. Corrigé en passant par des fichiers heredoc et en
**assertant que le fichier a changé** avant de lancer la suite :

```python
b = s
s = s.replace(...)
assert s != b, 'P6 no-op'
```

C'est la même famille que la règle §21 du mandat sur les codes de sortie : le
signal doit venir du mécanisme, jamais d'une correspondance textuelle qui peut
échouer silencieusement.

## Ce que cela ne fait pas

Aucune livraison n'est simulée. `destinations_configured` compte des
distributeurs configurés, pas des distributeurs qui fonctionnent — et sur cette
installation le seul livré est `fake`, en sandbox, qui le dit. Le blocage
externe `DIST-002` (aucun contrat de distributeur publié accessible) reste
entier : ce ticket rend visible ce qui bloque, il ne débloque rien.
