# MED-001 — Audio Technical Analysis

**Status:** delivered
**Base:** `8ff35e4` (main, after ING-001)
**Branch:** `claude/med-001-audio-analysis`

---

## What this ticket is actually about

Not "measure the audio". The hard requirement is that a server which **cannot**
measure the audio keeps working.

SaniTube's primary deployment target is cPanel shared hosting, where FFmpeg is
frequently absent and the account cannot install it. If analysis were a
dependency rather than a capability, every candidate on such a host would sit
unpromotable for ever and nothing would reach the catalogue — the platform would
be bricked by a binary it was told to treat as optional.

So almost everything below is about one distinction: **a missing capability is
not a bad file.**

```
TrackCandidate (PENDING)
   → AnalyzeAudioAssetJob
       → AnalyzeAsset      — object → temp file → probe → AudioAnalysis row
       → SettleCandidate…  — READY | NEEDS_REVIEW | WAITING_CAPABILITY
```

## The analyser is a contract, not ffprobe

`AudioAnalyzer` has four methods: `name()`, `version()`, `isAvailable()`,
`analyze(string $localPath)`. Three implementations ship:

| Implementation | Role |
| --- | --- |
| `FfprobeAudioAnalyzer` | the real one |
| `UnavailableAudioAnalyzer` | what a host with no FFmpeg gets |
| `Testing\FakeAudioAnalyzer` | a second real implementation, so the contract describes *analysis* and not ffprobe |

`MediaServiceProvider` binds `AudioAnalyzer` by asking the server what it can
do, once, at resolution time. Nothing downstream branches on FFmpeg's presence.

`UnavailableAudioAnalyzer` never reports failure about a file. Failure would
mean the *recording* was wrong, and blaming a master for the host's missing
binary is how a perfectly good file ends up quarantined.

## `ffprobe`, not `ffmpeg`

`ffprobe` reads headers and reports; `ffmpeg` decodes. For duration, codec,
sample rate and channel count the decode is wasted work, and on a shared host
with 900 files to get through, wasted work is the difference between a nightly
job that finishes and one that is killed.

Every field is nullable. A WAV has bit depth and no meaningful bitrate; an MP3
the reverse. A missing field is a fact about the format, not a failure —
substituting zero would put a number in the catalogue that nothing measured.

`parse()` is **public**, and that is deliberate. Parsing is where the mistakes
live, and a parser tested only where the binary happens to be installed is a
parser tested almost nowhere — three of the ten CI jobs would silently skip it.
Nine tests run captured ffprobe JSON through it on every engine and every PHP
version. One further test runs the real binary against a WAV it generates in
PHP, and skips when ffprobe is absent; it exists to catch the day ffprobe
changes its output, not to prove the parser.

No binary fixture is committed. A WAV in Git is a file nobody can review and
every clone carries for ever; `silentWav()` builds a real 44-byte-header PCM
file in nine lines.

## The object/file problem

A probe needs a **file**. The platform holds **objects**. On a local disk those
are the same thing; on object storage they are not, and an analyser handed a
storage key would work in development and fail in production — the worst
possible place to find out.

`AnalyzeAsset` streams the object to a temporary file, probes it, and unlinks
it in a `finally`. Every provider, one code path. That copy is the price of
provider independence and it is bounded: once per asset per analyser version,
in a queued job, never in a request. Two tests hold the line — one asserts the
analyser saw the actual bytes, one asserts the temporary file is gone
afterwards. 900 masters at 500 MB would exhaust a hosting quota otherwise.

Only `VERIFIED` assets are analysed. Analysing bytes nobody has confirmed would
describe an object the catalogue does not yet claim is the one it means.

## Three outcomes

| Outcome | When | Promotable |
| --- | --- | --- |
| `READY` | analysed, or analysis not required on a host that cannot | yes |
| `NEEDS_REVIEW` | the analyser **ran** and could not make sense of the file | no |
| `WAITING_CAPABILITY` | no analyser **and** the operator requires one | no, and non-terminal |

`SANITUBE_MEDIA_ANALYSIS_REQUIRED` defaults to **false**, and that default is
the cPanel question. False means an absent analyser yields `READY` with the
analysis columns null — honest about what was measured: nothing. An operator
whose distributor rejects masters below a loudness floor sets it true and
accepts that their host must provide FFmpeg.

The setting makes the *measurement* optional. It must never make the *finding*
optional, so an analyser that ran and failed produces `NEEDS_REVIEW` either
way. A test asserts exactly that, because a config flag that suppresses bad
news is the kind of thing that gets added by accident.

`WAITING_CAPABILITY` is deliberately non-terminal, and
`sanitube:media:analyze` is what makes that mean something. Without a command,
the only way to analyse 900 already-imported files after installing FFmpeg
would be to import them again — duplicating the entire catalogue. The pass is
bounded (`--limit`, default 200) so it finishes inside a cron window, and it
prints what it left behind: a truncated pass that reads like a complete one is
worse than no pass. With no analyser it warns and exits **0**, because a
nightly cron that mails an error on a supported configuration trains its reader
to ignore the mail.

## Analyses are never overwritten

`UNIQUE (asset_id, analyzer, analyzer_version)`. A recording analysed in 2026
and again in 2028 has two rows, and the older stays readable — otherwise "why
did this track's duration change?" has no answer. `FfprobeAudioAnalyzer::VERSION`
is bumped when the *meaning* of the output changes, not when the code is
edited, so a later, better version can be re-run over exactly the rows that
need it.

Re-running at the same version re-probes nothing; a test asserts the analyser
was not called a second time.

`loudness_lufs` and `peak_dbfs` are `decimal(6,2)`, not float. Loudness is
compared against delivery specifications, and a value that changes when it
round-trips is a value nobody can reconcile.

## Declared change to ING-001

Not silent, and pre-announced in ING-001's own report under *Decisions worth
challenging* — but stated here in full because it changes observable behaviour
of a merged ticket.

**Original decision (ING-001).** A candidate is created `READY` on successful
verification, because at the time nothing else had to happen first.

**Change.** `ProcessIngestionItem` now creates it `PENDING`.
`SettleCandidateAfterAnalysis` moves it to `READY`, `NEEDS_REVIEW` or
`WAITING_CAPABILITY`. Duplicates are still born `DUPLICATE` — that case is
already settled, since the duplicate points at an asset the platform analysed
before.

**Why.** Publishing a candidate as review-ready before its duration and
loudness are known means reviewing it without the numbers the review exists to
consider.

**Compatibility and data migration.** No schema change; `PENDING` and
`WAITING_CAPABILITY` were already declared in `TrackCandidateStatus` in
ING-001, specifically so MED-001 would extend rather than rewrite. No column,
index or relation is altered. Rows imported before this change are already
`READY` and stay so; they are not walked backwards, because a terminal
candidate is left alone.

**Rollback.** Reverting MED-001 leaves any `PENDING` or `WAITING_CAPABILITY`
candidates unpromotable until they are set to `READY` — a one-line update, not
a data loss.

**Tests.** `a_pending_candidate_becomes_ready_once_it_has_been_analysed`, and
`IngestionApiTest::candidates_can_be_filtered_by_status` now filters on
`PENDING`.

## Deliberately out of scope

**The analysis is not exposed on the candidate API.** CAT-001 is the candidate
review surface and is the very next ticket; building that read model twice is
waste. Today the analysis is reachable through `sanitube:media:analyze --json`
and through the candidate's `status`, which already moves on what analysis
found.

**Loudness and true peak are not measured yet.** `ffprobe -show_streams` does
not compute them; they need an `ffmpeg -af ebur128` pass, which decodes. The
columns exist, the result object carries them, and the analyser version is what
will let that be added and back-filled over exactly the rows that lack it.

## No architecture amendment

Nothing here changes a decision from ARCH-001/002/003 or AST-001. The schema is
additive: one new table, no column altered, no invariant relaxed. The one change
to ING-001 is set out in full above.
