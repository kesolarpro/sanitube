# A11Y-001 — the label that pointed at nothing

## The finding

`FormField` was written correctly. It generates an `id`, an `aria-describedby`
and an invalid flag, and its own docblock explains why each matters. It exposed
all three as **slot props**.

**Sixty-one of the platform's sixty-five fields never bound them.**

```vue
<FormField :label="trans('ui.releases.release_title')" :error="detailsForm.errors.title">
    <TextInput v-model="detailsForm.title" />
</FormField>
```

That renders `<label for="v-0">` beside an `<input>` with no id, no
`aria-describedby` and no `aria-invalid`. Every release form, every candidate
review form, every filter on every list, the settings screen, the studio.

## Why it went unnoticed for eleven tickets

**The failure is silent.** The screen looks right. The label is beside the
control, the error is visible in red, the form works with a mouse. Nothing in
CI complains, because nothing renders these together and asserts the
association. The only person who finds out is somebody using a screen reader,
who tabs into the field and hears *"edit text, blank"* — and then again for the
next field, and the one after.

It is also not sixty-one careless authors. It is one mechanism that was **opt-in
for something that must never be forgotten**, and an opt-in that is right by
default in four cases out of sixty-five is not a mechanism, it is a convention
nobody was told about.

## The fix

The field **provides** its wiring; the controls take it.

- `FormField` calls `provideField({ id, describedBy, invalid })`.
- `TextInput`, `SelectInput` and `TextareaInput` inject it and apply it.
- An explicitly passed prop still wins, so one label describing two controls
  stays expressible.
- A control outside a field keeps working exactly as before — a search box in a
  toolbar is not a mistake.
- The slot props stay, for the handful of screens that place things by hand.

All sixty-five call sites are fixed without touching one of them, and the
sixty-sixth cannot get it wrong.

## A second bug, found while fixing the first

The first implementation resolved the flag as:

```ts
const fieldInvalid = computed(() => props.invalid ?? field?.invalid.value ?? false);
```

**Vue casts an absent Boolean prop to `false`, not `undefined`.** `??` therefore
never falls through, and `aria-invalid` would have been silently absent on every
erroring control in the platform — the exact bug just fixed, reintroduced one
layer down, and equally invisible.

Caught by `points aria-describedby at the error when there is one`, which
asserts `aria-invalid` alongside the description precisely because colour is not
the only signal an error is allowed to have.

Now `||`: either source saying "invalid" is enough, which is also the behaviour
worth having — a field carrying an error is invalid whatever its control was
told.

## The tests

`tests/js/form-field.spec.ts`, six cases, and they assert the *resulting
behaviour* rather than the mechanism:

- a text input, a select and a textarea each associate with their label **with
  nothing bound by hand** — so writing a new field the ordinary way stays
  correct;
- `aria-describedby` points at the error element and `aria-invalid` is set;
- **nothing** is described when there is nothing to describe, because pointing
  at a non-existent element makes some screen readers announce nothing at all;
- an explicit id still wins;
- a control outside a field is untouched.

## What this audit did not cover

Stated plainly rather than implied by omission. Checked and clean:

- **No `v-html` anywhere** in the application — zero occurrences.
- **No icon-only controls without an accessible name.** `ToggleInput` is a real
  `<button role="switch">` carrying its own `aria-label`; navigation items pair
  their icon with text.
- Modal and drawer focus trapping, Escape handling, focus restoration and
  counted scroll locking were built and tested in UI-001 (`useModalSurface`,
  nine tests) and are unchanged.

**Not covered**, and not claimed:

- Per-screen keyboard walkthroughs on real assistive technology. Nothing here
  substitutes for that, and `docs/production-readiness.md` still records
  "Screen-reader semantics — NOT_READY".
- Responsive behaviour at the four breakpoints, and long-content/RTL overflow
  across six locales. Both need a rendered browser rather than jsdom.

Those remain open. What changed is that the single largest defect standing
between this platform and a screen-reader user is gone, and cannot come back
quietly.
