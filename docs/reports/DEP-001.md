# DEP-001 — The deploy script

Bringing a **running** installation up to new code.

## A deploy is not an install

Almost the whole ticket is that distinction. An install runs once against an
empty machine and may create things. A deploy runs against a machine with a
live catalogue on it and **creates nothing**:

| Missing | What a deploy does | Why not create it |
|---|---|---|
| `.env` | refuses | A deployment updates an installation; it does not create one. |
| application key | refuses | Generating one makes every existing encrypted value and every signed URL unreadable. |
| database | refuses | Creating one silently turns "you ran the wrong command" into a second, empty installation nobody notices. |

Each requirement carries its *reason*, not just its name, and a test asserts
the reasons are reasons rather than labels. An operator on shared hosting who
reads "database: missing" learns nothing they can act on.

## Two halves, and why

`bin/deploy.sh` runs `composer install`, `npm ci`, `npm run build`.
`php artisan sanitube:deploy` migrates, rebuilds caches, links storage and
restarts workers.

The split is not tidiness: **PHP cannot safely rewrite its own autoloader
mid-request.** A deploy command that ran `composer install` on itself would
finish half on the old code and half on the new.

## Decisions worth recording

**The script never runs `git pull`.** Which revision is deployed belongs to
whoever is deploying. A script that decides is a script that deploys the wrong
branch one day.

**Migrations before caches.** A config cache rebuilt before a migration that
adds a setting is a cache that must be rebuilt again, and nobody does it twice.

**Caches cleared, then rebuilt.** A stale cached config on a machine whose
`.env` just changed is the failure mode where somebody edits a credential,
restarts, and nothing happens. If the rebuild fails after the clear, the
installation is left *uncached* rather than wrongly cached — slower, and
correct, which is the right way round to fail.

**The storage link and the queue restart cannot fail a deploy.** A host that
forbids symlinks and an installation with no queue worker are both legitimate.
Failing a release over either teaches people to ignore the exit code.

**`queue:restart` is included at all** because without it a deploy leaves
workers running the *previous* version until somebody happens to restart them —
and the symptom is a job behaving like last week's code.

**Maintenance mode is released from a shell trap**, so a failure at any later
step still brings the site back up.

**`--dry-run` is a first-class mode.** It reports what every stage would do and
changes nothing — the cheapest way to find out a host is not deployable.

## Mutation pass — 13 injected, 13 killed

| # | Regression injected | Killed by |
|---|---|---|
| M1 | a missing key is generated rather than refused | deploying without a key is refused |
| M2 | a dry run migrates anyway | a dry run applies no migration |
| M3 | a dry run rebuilds caches anyway | a dry run rebuilds no cache |
| M4 | nothing pending reported as a successful migration | nothing pending says so |
| M5 | a failed queue restart fails the deploy | a restart that throws is not a failure |
| M6 | a host forbidding symlinks fails the deploy | a forbidden symlink is a note |
| M7 | the deploy carries on past a failed preflight | stops at the first failing stage |
| M8 | the requirements lose their reasons | reasons say why, not only what |
| M9 | the script pulls a revision of its own choosing | never decides which revision |
| M10 | the script installs development dependencies | installs without dev dependencies |
| M11 | the script leaves the site down on failure | brings the site back up |
| M12 | the script carries on after an error | stops on the first error |
| M13 | `--skip-migrations` silently migrates | says it was asked for |

**Three survived the first run, and all three were defective tests.**

- **M5 and M6** — the tests only asserted the *happy* path did not fail, so the
  `catch` branches they were supposedly about never ran. Both now use a
  deployment whose every artisan call throws, and the symlink test removes and
  restores `public/storage` because the stage short-circuits on an existing
  link.
- **M10** — the test looked for `--no-dev` *anywhere in the file* and was
  satisfied by the **comment explaining the flag**. Removing it from the actual
  command changed nothing. Now asserted against the `composer install` line
  itself.

A fourth near-miss is worth recording: the "never destructive" test reads the
script as text, and the original comment disowning `migrate:fresh` tripped it.
The comment was reworded rather than the guard weakened — the same call
ARCH-003's `PortabilityTest` forced earlier in the project.

## Not in this ticket

**DEP-002 / DEP-003** — cPanel and VPS deployment documentation, which describe
how to *run* this on each kind of host. `docs/deployment/deploying.md` is the
host-independent half.

**No deployment has been run against a real host.** Everything here is exercised
locally and in CI. The stages that only misbehave on shared hosting — a
forbidden symlink, a missing `npm` — are handled by construction and tested with
a stubbed kernel, not observed.
