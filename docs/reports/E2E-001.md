# E2E-001 — The V1 Acceptance Walk

**Status:** delivered
**Base:** `1d2f527` (main, after REL-002)
**Branch:** `claude/e2e-001-acceptance-walk`

---

## What this ticket is actually about

Every other test in the suite asks whether a *part* works. This one asks
whether the parts are still connected to each other, which is a different
question and the one nobody notices going wrong.

The V1 brief lists what an installation must be able to do. Until now that list
lived in a document, which means it was checked by a person reading prose and
deciding whether it sounded true. `AcceptanceWalkTest` turns it into a walk, in
the order an operator actually performs it: import a library, review it, build a
release, validate it, hand it to a distributor, watch it go live, back it up,
lose everything, and restore.

It found two real defects on its first run. That is the argument for it.

## Finding 1 — a restore could not restore

**Severity: the backup system did not work.**

`DatabaseDumper` wrote tables in alphabetical order, and `RestoreBackup`
replayed the file in that order inside one transaction. Alphabetically,
`distribution_attempts` comes before `distribution_deliveries`, so the restore
inserted attempt rows pointing at deliveries that did not exist yet:

```
SQLSTATE[23000]: Integrity constraint violation: 19 FOREIGN KEY constraint failed
(insert into "distribution_attempts" ... "delivery_id" 1 ...)
```

The delete pass had the mirror problem: emptying `releases` while
`distribution_deliveries` still referenced them is refused for the same reason.

Every OPS-001 restore test passed because they all used `users` — a table
nothing points at. A dump order that could not be replayed satisfied all of
them.

### Why turning the constraints off is not the whole fix

It is the usual answer, and it is done here too. But **SQLite ignores
`PRAGMA foreign_keys` inside a transaction**, and a restore runs inside one. A
fix that leaned on the pragma alone would be green on MySQL and MariaDB and
broken on the platform's smallest supported database — which, on the shared
cPanel hosting SaniTube targets, is also its most common one.

So the ordering is the fix and the pragma is the fallback:

- **`DatabaseDumper::tables()`** now returns a dependency order — Kahn's
  algorithm over the schema's foreign keys, alphabetical among the ready set so
  the order stays deterministic and a dump checksum still means something. A
  table is written after everything it points at.
- **`RestoreBackup`** empties every table the dump names in **reverse** file
  order before inserting anything, then streams the inserts in file order.
  Emptying is a separate pass because the whole table list is not known until
  the file has been read once, and a table emptied halfway through the stream
  would drop rows a child had already been given.
- `withoutForeignKeyConstraints` wraps both passes, for cycles and for backups
  written before the dump was ordered.

A schema whose dependencies cannot be resolved — a cycle, or one the connection
will not describe — has its remaining tables appended rather than dropped. A
dump missing a table is a backup that silently loses data, which is far worse
than a restore that needs the escape hatch.

## Finding 2 — a track can be promoted but never made releasable

**Severity: the browser path to a deliverable release is broken.**

`PromoteTrackCandidate` creates a track in `DRAFT`. `Track::markReady()` is the
only route to `READY`, and I3 refuses it without a primary artist — both
correct. But:

- there is no route in `src/Ui/Routes/web.php` that marks a track ready;
- there is no route that gives a track its credits;
- the whole catalogue surface (`TrackDetailController`, `TrackIndexController`,
  and their artist, asset, composition and contributor siblings) is read-only.

So a label who imports a library through the interface can promote a candidate
and then stop. Every release built from those tracks fails validation with
`TRACK_NOT_RELEASABLE`, and the fix for that issue is not reachable from any
screen.

The walk reaches it through the domain, with the gap named in a comment at the
point it is worked around. **CAT-002 closes it**, and that block becomes the
browser path when it does. It is recorded in `project-status.json` as the next
blocking ticket rather than fixed here, because credits and a readiness action
are a UI surface of their own and not a line of this test.

## Two smaller things the walk showed

- **`Track::readinessProblems()` still answers in English sentences.** REL-002
  converted `Release`; `Track` was not in its scope and is now the only
  validation surface left that cannot be translated. Raised as REL-003.
- **Existing distribution fixtures build identifiers by hand**, bypassing
  `AssignExternalIdentifier`, and use a 13-digit value as a UPC — which the
  normaliser refuses, because a UPC is 12. Not a production bug: the browser
  and command paths both go through the service. The walk uses the service.

## What the walk covers

| Step | Capability |
|---|---|
| 1 | A library imports as candidates; the catalogue is untouched |
| 2 | A person reviews, and the queue does not empty itself |
| 3 | A promoted track has a public uuid and a verified master |
| 3b | …and is DRAFT, and cannot be made releasable from a browser *(finding 2)* |
| 4 | An EP is assembled, numbered by the builder |
| 5 | Validation answers early, in codes, all of which are translated |
| 6 | Credits, artwork, dates, copyright lines |
| 7 | READY, and no longer structurally editable |
| 8 | ISRCs and a UPC — supplied, never minted; refused twice until both exist |
| 9 | Delivered, once |
| 10 | And refused a second time |
| 11 | Synced to LIVE, with a history |
| — | An outage is retryable; a refusal is a verdict |
| — | A generated recording joins the same review queue and needs the same person |
| — | Backup, total loss, restore — catalogue *and* delivery record *(finding 1)* |
| — | Six locales cover every issue code the walk can produce |

### What it deliberately does not cover

- **Installation**, which cannot meaningfully run against the database the
  suite is already connected to. `InstallerTest` covers it.
- **The unknown-submission outcome**, which lives on PR #35 awaiting review.
- **Nine hundred files.** Twelve. The claim that the walk holds together is
  what is under test; the claim that it holds at nine hundred is about
  queueing, and `ImportCommandTest` asserts it where it belongs.

## Mutation pass — 5 injected, 5 killed, 1 withdrawn

| # | Mutation | Result |
|---|---|---|
| M1 | The dump goes back to alphabetical order | killed |
| M2 | The dependency scan ignores foreign keys entirely | killed |
| M3 | Tables are emptied in dump order rather than in reverse | killed |
| M4 | A draft track is treated as releasable | killed |
| M5 | Promotion puts a track straight into the catalogue as READY | killed |

**M3 survived the first pass**, and the reason is worth recording: both restore
tests cleared their rows by hand before restoring, so the delete pass never ran
against a populated database — which is the only situation a restore is ever
performed in. `a_restore_over_a_populated_database_empties_children_before_parents`
restores over the graph without removing anything first, and M3 dies.

**M6 was withdrawn, not killed.** It removed `SubmitDelivery`'s early
`isSubmittable()` check and nothing went red — correctly. That check is a fast
path; the guarantee is the conditional `UPDATE` that claims the delivery, which
still refuses the second submission and is already proved by `DistributionTest`.
A mutation that deletes a redundant guard while the real one holds is not a
risk, and keeping it would have meant writing a test to assert an implementation
detail.
