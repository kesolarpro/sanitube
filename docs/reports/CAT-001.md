# CAT-001 — Candidate Review & Promotion

**Status:** delivered
**Base:** MED-001 (`claude/med-001-audio-analysis`, PR #6)
**Branch:** `claude/cat-001-candidate-promotion`

---

## What this ticket is actually about

The door between a proposal and the source of truth.

Everything before this point was allowed to guess. ING-001 read a title off a
filename at three in the morning. MED-001 measured what the server was capable
of measuring. Neither may write to the catalogue — that negative is the whole
architecture of the last two tickets. CAT-001 is the one place a Track comes
into existence from imported material, and it is narrow by construction.

Most of the code, and most of the tests, are about the ways it refuses.

```
TrackCandidate (READY)  ──promote──▶  Track (DRAFT)
                        ──reject───▶  REJECTED, reason recorded
                        ──patch────▶  suggestion corrected, nothing decided
```

## Promotion is not publication

The Track is created `DRAFT`, always, with no way to ask for anything else.
"This belongs in the catalogue" and "this is ready to release" are separate
decisions, and a promotion that could produce a releasable track is a route
from an unattended batch job to a distributor.

## The six refusals

| Reason | When |
| --- | --- |
| `NOT_PROMOTABLE` | not `READY`, and not a state a reviewer may overrule |
| `OVERRIDE_NEEDS_NOTE` | overruling the platform with no stated reason |
| `ALREADY_PROMOTED` | promotion happens once |
| `ALREADY_DECIDED` | revising or re-rejecting a settled candidate |
| `ASSET_NOT_VERIFIED` | the master's bytes were never confirmed |
| `MASTER_ALREADY_IN_CATALOGUE` | this recording is already a track |

Each is a 422 carrying a machine-readable `code`. A refusal with no reason is
what makes a reviewer guess, and a reviewer who guesses eventually works around
the check instead of addressing it.

### Overruling the machine

`NEEDS_REVIEW` and `DUPLICATE` are not ready — that is the point of them — but
a person who has listened to the file may legitimately disagree, and a platform
with no way to record that ends up with a spreadsheet beside it. So both are
promotable **with an explicit override and a written note**. The note is
required, not encouraged: an override nobody can account for six months later
is not an override, it is a gap.

`WAITING_CAPABILITY` and `PENDING` are deliberately **not** overridable, and
the distinction is the interesting one. There is no verdict there to disagree
with — the work has not happened. Letting a reviewer overrule it would promote
an unmeasured master on a host whose operator had explicitly said measurement
was required.

## Promotion happens once, under a race

The claim is a single guarded `UPDATE`:

```php
TrackCandidate::query()
    ->whereKey($candidate->id)
    ->whereNull('promoted_track_id')
    ->where('status', '!=', TrackCandidateStatus::Promoted->value)
    ->update(['status' => TrackCandidateStatus::Processing->value]);
```

Zero rows affected means someone else got there first. Reading the status and
then writing it would let two reviewers who both loaded the page while it was
`READY` each create a track; a conditional `UPDATE` is atomic on all four
engines. A test promotes from a deliberately stale model to prove it.

Backed in the schema by `UNIQUE (promoted_track_id)` — NULLs are distinct
inside a unique index everywhere in the matrix, so any number of unpromoted
candidates coexist while a track can be claimed by exactly one candidate.

## One recording, one track

The duplicate constraint, at the point where it would do real damage: the same
recording under two identifiers is what a distributor sees as two releases of
the same track.

**This was found by a failing test, and the first implementation was wrong.**
Checking `tracks.master_asset_id` against the candidate's asset id is not
enough, because AST-001 registers a duplicate as a *second* asset carrying
`duplicate_of_asset_id` rather than discarding it — the import happened, and an
import that disappears is one nobody can account for. So the second candidate
has a different asset id and sailed straight past the guard. The check now
follows the duplicate chain.

The same finding produced a second rule: when a duplicate *is* promoted by
override, the track points at the **original** master, not the copy. Pointing
at the copy would leave the original unreferenced while the account pays
storage for both.

**No unique index was added to `tracks.master_asset_id`**, and that is
deliberate restraint. `tracks` is ARCH-002's table, validated; tightening its
schema to enforce a rule this ticket introduced would be an architecture
amendment made in passing. The rule lives in the domain service, where it can
be overridden with a stated reason — because a genuine second recording sharing
a master is rare but not impossible.

## What promotion does not do

**It mints no identifier.** No ISRC is assigned. A new identifier for a master
that may already have been distributed is the one mistake that cannot be taken
back once a DSP has seen it, which is also why `already_distributed` exists:
the reviewer declares it, the track becomes `LEGACY_IMPORT`, and the platform
knows to preserve an existing ISRC rather than mint one. Only a person knows
this, so only a person can say it.

**It does not guess a language.** Nothing about an imported file says what
language it is in, so an unspecified language is recorded as `und`
(undetermined), never inferred. A wrong language code reaches DSPs.

**It does not edit an existing Track.** The catalogue remains read-only over
the API; this creates, it does not modify.

## Small things that matter

- **Instrumental and language are derived in both directions.** Ticking
  "instrumental" sets `zxx`; choosing `zxx` sets instrumental. `TrackObserver`
  enforces I8 and would otherwise throw an ISO 639-2 error at a reviewer who
  ticked a box.
- **The measured duration reaches the track without being retyped** — but a
  supplied duration wins, because a reviewer may be cataloguing an edit the
  master does not reflect. A host with no analyser leaves it null rather than
  zero: a zero is a number nothing measured.
- **Rejection keeps the row.** Deleting it means the next import of the same
  folder proposes the same file again as though nobody had ever looked, and
  across 900 files that is how a reviewer stops trusting the queue.
- **A PATCH merges metadata rather than replacing it.** What the importer read
  out of the file is as much a part of the record as what a reviewer adds, and
  it is the only copy.
- **A promoted candidate cannot be revised.** Editing the suggestion behind a
  decision would rewrite the history of a decision taken on the old value.

## The dependency direction

Media already listens to Ingestion, so `PromoteTrackCandidate` reading an
`AudioAnalysis` directly would close a cycle between two modules. The measured
duration is applied by `Media\Listeners\RecordMeasuredDurationOnTrack`,
listening for `TrackCandidatePromoted` — the module that holds the measurement
is the module that applies it. The event fires inside the promoting
transaction, so a failing listener takes the promotion with it rather than
leaving a half-catalogued track behind.

The candidate resource reads `AudioAnalysis` in the API layer for the same
reason: an analysis belongs to an *asset*, and a relation on `TrackCandidate`
would put Media's table in Ingestion's model.

## API

```
PATCH /api/v1/ingestion/candidates/{uuid}          revise a suggestion
POST  /api/v1/ingestion/candidates/{uuid}/promote  → 201, the Track
POST  /api/v1/ingestion/candidates/{uuid}/reject   reason required
```

`promote` is a POST to a named action rather than a PATCH of `status`. It runs
invariants, writes to the catalogue and is refusable six ways; a settable
status field would present all of that as an assignment.

`201` rather than the `202` that starts an import: unlike a batch, the thing
this request describes exists by the time it answers.

The candidate resource now carries `analysis` — deferred here from MED-001
because the measurement and the screen that reads it are separate concerns, and
building the read model in the ticket that produced the data would have meant
building it before knowing what the review needed. `raw` is excluded: it names
codecs, paths and tooling, and is kept for diagnosis rather than publication.

## Schema

One additive migration on `track_candidates`:

| Column | Why |
| --- | --- |
| `reviewed_at` | a decision with no timestamp is indistinguishable from something the platform did on its own |
| `reviewed_by` | nullable; Identity does not exist yet, declared now because backfilling provenance is guesswork |
| `review_note` | a rejection's reason, or an override's justification |

Plus `UNIQUE (promoted_track_id)`. `migrate → rollback → migrate` verified
locally on SQLite and by all four engines in CI.

`TrackCandidateStatus` gains `REJECTED`. Additive, and distinct from `FAILED`
on purpose: `FAILED` is the platform saying it could not, `REJECTED` is a
person saying no.

## Architecture amendment

**None to a validated ticket.** The `track_candidates` changes are additive
columns and one new unique index on a table introduced by ING-001; no column is
altered, no relation changed, no invariant relaxed. `tracks` — ARCH-002's
validated schema — is untouched, which is precisely why the one-master-one-track
rule is enforced in the domain rather than by an index.

MED-001's declared change to ING-001 (candidates born `PENDING`) is carried
forward from that ticket's report and is not restated as new.
