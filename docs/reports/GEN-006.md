# GEN-006 — asking a supplier what it does

**Capability discovery and provider selection.** No adapter, because there is
still nothing to adapt to: see `docs/research/music-generation-2026-08.md`,
delivered with this ticket.

---

## Why this and not an adapter

The research this ticket follows evaluated four candidate music generation
providers against ~22 axes. From this environment exactly **one** had a contract
that could be verified against primary sources — ACE-Step 1.5, read from its own
repository — and that contract turned out to be **synchronous**: `POST /generate`
blocks and returns a local filesystem path. No job id, no polling, no webhook,
no cancel.

`MusicGenerationProvider` was written on the opposite assumption. Its docblock
says so plainly: *"Generation is asynchronous by nature."*

One verified provider was enough to show the shape of the problem. The contract
had silently taken its first intended supplier's architecture as the definition
of what a music provider *is*, and any second supplier would have arrived either
as a lie (a synchronous provider pretending to poll) or as a fork of the
pipeline. So the platform stops assuming and asks.

WaveSpeedAI, HeartMuLa and Suno remain `BLOCKED_EXTERNAL_API_ACCESS` from this
environment — an environment limitation, recorded as one, and explicitly not a
judgement about those providers.

## What was built

| Piece | What it is |
| --- | --- |
| `GenerationCapability` | 13 named capabilities, the vocabulary |
| `DeclaresCapabilities` | optional contract — an adapter says what it read in the docs |
| `ProviderCapabilities` | discovery: structural + interfaces + declaration, minus what the operator withheld |
| `SelectGenerationProvider` | which supplier serves this request, and what else could |
| `StartMusicGeneration::requires()` | what a request needs, derived from the request |

### Three sources of evidence, ranked

1. **Structural** — implementing the interface proves `TEXT_TO_MUSIC` and
   nothing else. One capability, and the shortness is the point.
2. **Capability interfaces** — `instanceof SupportsExtend` is a method that
   exists and can be called. A provider cannot forget to mention a method it
   has, so these are read even for adapters that also declare a list.
3. **Declaration** — an adapter author saying what they read. Weaker than a
   method, far better than a guess.

`CANCEL` looks structural and is not. `cancelGeneration()` is on the base
contract and returning `false` for ever is a documented answer, so having the
method is not evidence. A synchronous provider has nothing to cancel. It must
be declared, and a test pins that.

### Configuration removes, never grants

`generation.providers.<name>.disabled_capabilities` switches off things the
adapter believes its supplier can do. A self-hosted deployment with no stem
model installed genuinely cannot separate stems however capable the software is,
and only the operator knows that.

There is deliberately no key that *grants* one. A capability granted in a config
file produces a failure at the supplier that looks like a bug in SaniTube, and
would let an installation overrule the one place that has actually read the
contract.

## WHO CALLS THIS IN PRODUCTION?

```
POST /studio/generations                     (src/Ui/Routes/web.php, can.role:catalogue)
  -> StudioActionController::startGeneration
    -> StartMusicGeneration::handle
      -> StartMusicGeneration::requires($lyrics, $instrumental)
      -> SelectGenerationProvider::select(required:, preferred:)
        -> ProviderCapabilities::missing
        -> GenerationCircuitBreaker::isOpenFor
```

and, read-only:

```
GET /studio -> StudioOverviewQuery::get -> ProviderCapabilities::for
            -> Studio/Index.vue renders ui.studio.capability.*
```

`the_studio_form_is_what_selects_a_provider_in_production` posts the real form
twice — once asking a text-only supplier to sing supplied lyrics, once not — and
asserts the refusal code, that no row was written, and that no job was queued.

## The sharpest edge

`config/generation.php` ships with `fake` in `providers`, because the fake is
what makes the Studio demonstrable without a supplier account. So "fall back to
anything configured" would mean a fresh installation — whose default is `none` —
answering a request for music with **synthetic audio**, and the operator would
have no reason to suspect it.

`SelectGenerationProvider::order()` therefore returns the preference list plus
the default, and nothing else. **A configured entry says a provider *can* be
selected; it does not say it *may* be used.** Falling back to a second supplier
is opt-in, via `generation.preference`, which is a sentence somebody wrote on
purpose.

This was caught by three existing tests failing, not by foresight.

## What moved

The circuit breaker moved from `StartMusicGeneration` into selection. GEN-005
made it *refuse*; with somewhere else to go the right answer is to *go there*.
A provider having an outage should cost the backlog a detour, not a stop — and
when there is nowhere to go, the refusal is unchanged (`PROVIDER_CIRCUIT_OPEN`).

Ceilings deliberately did **not** move. They are a property of the installation
rather than of a supplier, so no provider is more or less viable for having
reached one, and moving a request to a second provider to get past a ceiling
would defeat the ceiling. A test asserts that.

`candidates(required:, except:)` is the substrate for the mandate's requirement
that a provider failure must not lose a `ProductionSlot`: the caller holding the
work asks what else would do, naming what it has already tried. The re-routing
itself belongs with whatever bridges `WorkProductionSlot` to generation, which
does not exist yet.

## New refusal codes

| Code | Means |
| --- | --- |
| `PROVIDER_INCAPABLE` | this supplier does not do what the request needs — names the missing capabilities |
| `NO_CAPABLE_PROVIDER` | the search came back empty; nothing configured can serve it |

Distinct on purpose: one says change supplier, the other says configure one.
Both translated in six languages, along with `CEILING_REACHED` and
`PROVIDER_CIRCUIT_OPEN`, which reached the Studio's failure list only now.

## Verification

- **24 tests, 150 assertions** in `tests/Feature/MusicGeneration/ProviderCapabilityTest.php`
- Full suite: **1842 passed, 1 skipped, 23492 assertions**
- PHPStan level 6 clean, Pint clean, vue-tsc clean, Vitest 23 passed

### Mutation testing — 13 mutations, 13 killed

Two rounds. The first found **two survivors**:

- **M11** — reporting the *last* refusal instead of the most preferred
  provider's. Real gap: no test had two providers falling short for *different*
  reasons, so the documented claim that the operator is told about the supplier
  they meant to use was untested. Covered by
  `the_refusal_reported_is_the_one_from_the_supplier_that_was_preferred`.
- **M13** — a harness bug, not a survivor. `'capabilities' => [] ?: array_map(…)`
  evaluates to `array_map(…)`, so the mutation changed nothing. Re-run with the
  array actually replaced: killed.

Both re-run and killed. The harness verifies each mutation with md5 before/after,
judges by exit code, restores the file and verifies the restoration.

## State

`CODE READY`. Not `CONFIGURED`, not `CONNECTIVITY VERIFIED`, not
`PRODUCTION VERIFIED` — there is still no real music provider on this
installation, and this ticket does not pretend otherwise. What it changes is
that the day one arrives, the platform will ask it what it does.
