# CAT-002 — A Track Becomes Releasable

**Status:** delivered
**Base:** `c8c6869` (main, after E2E-001)
**Branch:** `claude/cat-002-track-releasable`

---

## What this ticket is actually about

E2E-001 found it: **the catalogue was read-only from a browser.**

- `PromoteTrackCandidate` creates a track in `DRAFT`.
- `Track::markReady()` is the only route to `READY`, and I3 refuses it without
  a primary artist.
- Nothing in `src/Ui` called `markReady()` on a track, and nothing set track
  credits.

Both of the first two are correct on their own. Together they left a track that
could be created and never finished. A label who imported a library through the
interface could promote a candidate and then stop: every release built from
those tracks failed validation with `TRACK_NOT_RELEASABLE`, and **the fix for
that issue was not reachable from any screen**.

Two routes close it.

## Credits

`SetTrackCredits` replaces the list rather than patching it, for the reason
`ReleaseBuilder` gives about release credits: **the order is part of the
credit**. "A feat. B" is not "B feat. A", and a per-row endpoint cannot express
a reordering without a moment where the recording is credited to nobody.

`track_artist` is unique on `(track, artist, role)`, which is deliberate — the
same person can legitimately be a PRIMARY and a REMIXER on one recording. So
credits are written one row per pair rather than through `sync()`, which is
keyed by the related model and would have kept only the last role given. A
performer who also remixed their own record would have lost a credit with
nothing refused.

The same person in the same role twice is deduplicated rather than allowed to
hit the unique index: it is a duplicated line in a form, not something worth a
500.

A `RELEASED` or `ARCHIVED` recording keeps the credits it was delivered with. A
store is serving it under the metadata it was given, and editing the local row
would only make the two disagree without changing anything a listener sees.

**Credit, not entitlement.** A name in `track_artist` says who performed on a
recording, which is what a store displays and what a distributor's metadata
requires. It says nothing about who is owed anything, and this does not become
a record of that.

## Readiness is earned, never assigned

`TrackActionController::markReady()` calls the domain and lets it refuse.
Neither action writes `status` — same rule the release actions follow, and for
the same reason: a controller that set `status = READY` would be skipping I3
while looking like it did the same thing.

The refusal carries a code. The problems are already in the payload the screen
renders, from the same `readinessProblems()` the domain throws on, so a second
copy in a flash message would be one that can disagree with it.

## Validation moved to Foundation

`Track::readinessProblems()` now answers in issues rather than English
sentences — REL-003, folded in here because without it the new screen would
render English into six locales.

That meant `Catalog` needing the value objects `Releases` owned. Rather than
point `Catalog` at `Releases` — `Releases` already depends on `Catalog`, so
that is a cycle between modules — `ReleaseValidationIssue` and
`ReleaseValidationResult` moved to `SaniTube\Foundation\Validation` as
`ValidationIssue` and `ValidationResult`. Every module already depends on
Foundation.

The translation table moved with them, from `ui.releases.issue.*` to
`ui.issue.*`: it holds track codes now, and the old key said otherwise.
`ValidationIssueTest` scans `src/Catalog` as well, so the six-locale gate covers
the new codes in both directions without anybody adding them to a list.

## Authorization

Both routes sit behind `can.role:catalogue`, the same guard candidate review
uses. A MEMBER may read the catalogue and may not credit or promote anything in
it. On the route rather than in the controller, so a future action cannot
acquire the surface without acquiring the guard.

The screen's `actions` block is presentation and is tested as such: a MEMBER is
offered nothing to press, *and* a MEMBER posting past the missing buttons gets
a 403.

## The stale-cache defect

Three times this session a test failed for a reason that had nothing to do with
what it asserted: `config('backup.*')` reading null, and a route answering 404
that plainly existed. The cause is the same each time.

**`DeploymentTest` runs `sanitube:deploy` against this checkout, which caches
the configuration and the route table and leaves them there.** The run that
creates the cache does not notice — the application is already booted — but the
*next* `php artisan test` reads a snapshot of `config/` and `routes/` as they
were. A config file added since reads as null; a route added since answers 404.
Neither looks like a stale cache. Both look like a broken feature, and the
failure lands in whichever test happens to touch it rather than at the cause.

Two halves:

- **`tests/bootstrap.php`** removes any cached config or route table before the
  suite runs. Removed rather than warned about: there is no situation in which
  running the suite against a stale snapshot is what somebody wanted.
- **`DeploymentTest::tearDown()`** runs `optimize:clear`, so the one thing in
  the suite that creates a cache cleans it up.

`php artisan test` twice in a row now gives the same answer, which it did not
before.

**M9 survived the first pass.** A PHPUnit bootstrap cannot be observed from
inside the run it precedes — by the time any assertion executes, the file is
gone either way. It is now exercised directly: a cache file is planted, the
bootstrap is required over it, and its absence is asserted. Requiring the file
again is safe because all it does besides the sweep is require the autoloader.

## A fixture that was quietly wrong

`TrackActionsTest` first used the `user()` helper the other UI tests use, which
`forceFill()`s a role without saving it. That is enough for a single
`actingAs()` and silently wrong the moment a test signs in twice: the second
call reads the row back with whatever the column defaulted to, and the request
is refused for a reason the test never intended to exercise. The helper here
persists.

person uses, so the walk covers the path an operator actually takes.
