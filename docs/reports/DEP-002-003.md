# DEP-002 / DEP-003 — Host guides

`docs/deployment/cpanel.md` and `docs/deployment/vps.md`, plus the tests that
stop them drifting from the code.

## The honesty banner is the first thing in both files

> Nothing in this file has been run against a real cPanel account / VPS.

Both guides are *derived* from the constraints those hosts impose, not observed
on one. Those constraints — no root, no long-running processes, cron through
the panel, a PHP version selector, symlinks sometimes forbidden — are stable
and well documented, so the guides are useful. They are not verified, and a
guide that reads as a verified procedure when it is a derivation is exactly the
confidence that leaves somebody stuck at two in the morning.

A test asserts the banner is present. Removing it fails the suite.

## What the guides carry

**Shared hosting is the baseline, not an afterthought.** A label with a back
catalogue and a £5 plan is who this platform is for. The cPanel guide names
Redis, Supervisor, Docker and root explicitly — as things SaniTube does *not*
need — because every design decision that looks over-careful elsewhere exists
because of that reader. A test asserts all four are addressed.

**The document root gets its own section.** With it one level too high, `.env`
— database password, storage credentials, application key — is served over HTTP
to anyone who asks. The guide says so, and a test requires a dedicated section
rather than a passing mention in the install steps.

**The scheduler is the step people skip, and skipping it is silent.** Retries
never retry, distribution status is never refreshed, the health snapshot goes
stale, and nothing anywhere says so — the Operations screen reporting a
scheduler that has never run is the only warning. Both guides carry the cron
line and a test requires it.

**The VPS guide explains why `Restart=always` matters.** `bin/deploy.sh`
signals workers to finish and exit so they pick up new code, and deliberately
does not start them again. Without a supervisor that does, the queue stops
after every deploy and nobody notices until an import hangs.

**Neither guide repeats the deploy stages.** Two copies of a procedure is one
copy that goes stale; both defer to `deploying.md`.

## Mutation pass — 7 injected, 7 killed

Two survived a first pass.

**M3 was a defective test.** The pattern required `Restart=always` *somewhere
after* `[Service]`, which reached past the unit file into the prose paragraph
explaining it — so breaking the unit file left the page still matching. Now
bounded to the unit's own block.

**M1 exposed a weak assertion.** The original test looked for `public/`
anywhere in the file and was satisfied by `public_html`, `public/build` and
`storage/app/public`. It now matches the instruction, and a new test requires
the dedicated section.

**One mutation was withdrawn rather than killed.** Removing the *install step*
that restates the document root, while the dedicated section stands, is not a
regression — the guide still says the thing that matters, in the place designed
to be read. Contorting a test to fail on it would have been fitting the test to
the mutation rather than to the risk.

## Still open

`OPS-001` — there is no backup command. The VPS guide says so plainly and tells
the reader what they are responsible for until it lands: the database, and
`storage/app` if storage is local. Off the machine, because a backup on the
same disk survives a mistake and not a failure.
