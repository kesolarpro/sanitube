# OPS-001 — Backup and restore

A backup command, a restore command, and a great many refusals.

## A restore is the most destructive operation in the platform

It is the only one that deliberately overwrites data somebody is still using,
and everything here is arranged so it fails **before** it writes rather than
during. The order is not negotiable:

1. **Is it a backup?** A manifest, readable, in a format this version knows.
2. **Is it complete?** Every entry it names is present.
3. **Is it intact?** Every checksum matches.
4. **Does it belong here?** The migration set must match, or the caller says
   explicitly that they know it does not.
5. **Was it asked for?** Explicitly.

`verify()` is steps one to four alone, so an operator can find out whether a
backup is restorable at a moment when the answer costs nothing. **A backup
nobody has ever tried to restore is a belief, not a backup**, and `--verify` is
the flag the documentation puts on a schedule.

## Decisions worth recording

**The manifest is written last.** Until it exists the directory is not a
backup: not listed, not restorable, not pruned. That is the whole crash-safety
story — there is no state in which a partial backup looks complete. Proved by a
test that fails the dump mid-run rather than by inspecting the order.

**A directory, not an archive.** `ZipArchive` and `PharData` are optional PHP
extensions and shared hosting is the baseline target; a backup that needed one
would be a backup that sometimes cannot be taken.

**Rows, not SQL. No `mysqldump`.** Shared hosting frequently has no shell, no
`exec()` and no client binaries. It is also portability: a SQL dump is written
in one engine's dialect, and a label moving from a shared host to a VPS is
moving engines. Rows travel as data; the schema comes from migrations, which
are already engine-neutral.

**Audio masters are excluded, loudly.** Several hundred are tens of gigabytes.
Copying them every run is not a backup strategy, and pretending otherwise is
how an operator discovers their nightly job has been failing on disk space for
a month. Every exclusion is recorded in the manifest *with its reason*.

**Schema drift is refused by default.** Restoring older rows into a newer
schema silently is how a catalogue is corrupted. `--allow-schema-drift` exists
and is never the default.

**`--force` is not implied by `--no-interaction`.** A deploy script that
acquired the power to restore by being non-interactive would be one stray line
away from replacing a live catalogue.

**Files and the database are not restored atomically, and nothing pretends
they are.** The database goes back inside a transaction; files are copied
afterwards. A file failure leaves a consistent database and a named count —
recoverable. The other order leaves a backup's covers beside a database that
never received it.

**Pruning is the only routine unattended destructive act**, so it never removes
an incomplete backup, never removes everything whatever `keep` says, and
`realpath`-checks before the one recursive delete in the platform.

## On the operations screen

Last backup, and how many are kept. A backup job that silently stopped is the
classic disaster — nothing looks wrong until the day something is — so a date
an operator walks past every week is what makes it visible.

**`taken_at: null` means never backed up**, and the screen says that in words.
Never backed up and backed up a long time ago are different problems.

Reading manifests is a directory listing, not a probe. It never verifies
checksums: that reads every byte and has no business running during a page
load. A destination that cannot be read reports itself rather than taking the
screen down — this is the page somebody opens when things are already wrong.

## Mutation pass — 16 injected, 16 killed, 1 withdrawn

Covered: the web-root check, missing entries, checksums, schema drift, manifest
format, confirmation, path traversal (POSIX and Windows-style), the pruning
floor, symlink escape during delete, replace-not-merge, ephemeral tables, the
recorded exclusions, the non-interactive guard, and manifest ordering.

**M16 exposed a missing test.** Writing the manifest early changed nothing,
because the real one overwrote it — the mutation staged no hazard. The actual
claim, *a crashed run leaves nothing that looks complete*, had no test. One was
added that fails the dump partway through; M16 and a stronger M17 both die on
it now.

**M10 was withdrawn.** Removing the manifest-existence check in `complete()`
leaves `manifestAt()` throwing and the surrounding `catch` doing the same job —
defence in depth, not a regression. Contorting a test to fail on a redundant
guard would be mutation theatre.

## A note on the config cache

The first test run failed because `config/backup.php` returned null: a stale
`bootstrap/cache/config.php` left by an earlier `sanitube:deploy`. That is
exactly the failure SET-001's settings screen exists to make visible, and it
found me before it found an operator.

## Not in this ticket

**Backups are not encrypted.** The documentation says so and says to treat the
directory as you would the database itself. Encryption needs a key-management
answer — where the key lives so that it survives the machine the backup is
protecting against — and that is a decision, not an implementation detail.

**Object-storage destinations.** The repository is a filesystem path today. The
manifest and checksum design is storage-agnostic, so this is an adapter rather
than a redesign.
