# UI-005b — Studio write actions

## What this delivers

The studio can now be used, not only watched. Four actions:

| Action | Route | Service |
| --- | --- | --- |
| Start a campaign | `POST studio/projects` | `CreateGenerationProject` **(new — extracted)** |
| Ask a supplier to make something | `POST studio/generations` | `StartMusicGeneration` |
| Stop a generation | `POST studio/generations/{uuid}/cancel` | `CancelMusicGeneration` **(new — extracted)** |
| Take a result into the review queue | `POST studio/results/{uuid}/select` | `SelectMusicGenerationResult` |

All behind `can.role:catalogue`, the same guard candidate review uses.

## The claim this ticket rests on

**Selecting a result never creates a Track.**

```
result → fetch audio → Asset → VERIFIED → TrackCandidate (GENERATED) → review queue
```

and it stops there. Generated audio is exactly the material that most needs a
person to listen before it enters the catalogue — it was produced by a machine
from a sentence — so it joins the same queue as an imported file, and UI-004b's
promotion is a separate decision on a separate screen.

A mutation makes that structural rather than aspirational: adding a
`Track::create()` beside the selection call turns
`selecting_a_result_produces_a_candidate_and_never_a_track` red. Without it, a
campaign could write nine hundred rows into the source of truth overnight.

The candidate lands `PENDING`, so MED-001 analyses it like any other file.
Generated audio gets no shortcut.

## Two extractions, and why they were necessary

Building this surface surfaced a real defect: **two behaviours the interface
needed lived inside API controllers, not services.**

- `MusicGenerationController::cancel()` held "ask the provider to stop, then
  write CANCELLED, unless it has already finished".
- `GenerationProjectController::store()` held "a campaign starts as a DRAFT".

Duplicating either into a second controller would have produced exactly the
thing the ticket forbids — a second, weaker copy of un-serviced logic, and the
copy that drifts is always the one nobody is looking at.

So both were **extracted into services and both surfaces now call them**. The
semantics are unchanged; all 49 pre-existing generation tests passed unmodified
immediately after the extraction, which is what makes it an extraction rather
than a rewrite.

`CancelMusicGeneration` also hardens one thing while moving it. The provider
call is now wrapped: a supplier that refuses, does not support cancellation, or
is simply unreachable must not stop SaniTube recording the intent. The previous
code would have propagated the throwable, which means a job stuck at a supplier
could never be closed locally and the operator would stare at PROCESSING
forever with no way to act. It is the one place in the module where swallowing
a throwable is right, and the comment says so.

## Money

Starting a generation is the one action in the interface that **spends the
operator's money at a supplier**. Three consequences, each tested:

- It **queues** the submission rather than making it inline. A browser that
  gives up mid-request must not leave a paid job nobody has a record of. The
  row exists before the provider is called, so a retry finds it.
- The dialog says so before the button does anything: *"Providers charge for
  generation, and the request cannot be un-sent once it reaches them."*
- A MEMBER cannot cause it. `a_member_may_watch_the_studio_and_spend_nothing`
  asserts all three write routes answer 403 and that nothing was queued.

Cancelling likewise says what it cannot undo: if the provider has already
finished, or already charged, stopping locally does not reverse that.

## Two reasons a button is missing, and the screen says which

`may_generate` is the conjunction of "this account may write the catalogue" and
"a provider is available", and the two fail for entirely different reasons with
entirely different fixes. Collapsing them into "unavailable" sends somebody to
the wrong place, so the overview prints the applicable one:

- *"No generation provider is configured, so there is nothing to send a request
  to."*
- *"Your account may watch the studio and may not send requests to a provider."*

Both are covered by tests, including one asserting that a MEMBER on an install
with a working provider sees `provider.available: true` and
`may_generate: false`.

## Honest values preserved

A new generation's `commercial_rights_status` is `UNKNOWN` — asserted at
creation, because that is exactly where an optimistic default would be
tempting.

An instrumental carries no lyrics however the form was filled in. The
contradiction is resolved in `StartMusicGeneration` rather than validated into
an error: somebody who ticks "instrumental" after typing a verse has changed
their mind, not made a mistake.

A campaign with no target records `null`, not `0`; an empty default style
prompt is stored as no default, because otherwise every generation in the
campaign inherits a style prompt of nothing.

## Guardrails proven

Six regressions injected; **every one turned a test red**:

| Injected regression | Caught by |
| --- | --- |
| role guard dropped from the studio writes | 2 tests |
| the submission made inline instead of queued | starting a generation queues the request |
| a finished generation becomes cancellable | 2 tests |
| `may_generate` ignores the provider | nobody may generate when no provider is configured |
| selection idempotence bypassed | selecting the same result twice creates one candidate and one asset |
| a selected result becomes a Track directly | selecting a result produces a candidate and never a track |

## A fixture that would have been a fake finding

The first run of `a_generation_cannot_be_started_when_no_provider_is_configured`
reported `UNKNOWN_PROVIDER` instead of `PROVIDER_UNAVAILABLE`. The cause was my
own fixture: it replaced `generation.providers` with only `fake`, dropping the
`none` entry that `config/generation.php` actually ships. The disabled provider
then became unresolvable rather than unavailable.

The fixture was corrected to mirror the real configuration. Left alone it would
have documented a defect that does not exist in any real install — and worse,
it would have hidden the genuine distinction the studio overview draws between
"unconfigured" and "named but unresolvable".

## Tests

23 new tests. **842 PHP tests / 3574 assertions**, 1 skipped (the real ffprobe
run), plus 16 component tests. PHPStan level 6 clean, no baseline. Pint clean.
vue-tsc clean. Frontend build clean. Strings in `en/fr/es/it/pt/de` with the
completeness gate passing both directions.

## No provider credential reaches the browser

Unchanged from UI-005 and re-asserted by the existing suite: no
`provider_job_id`, no `source_reference`, no `raw`. The new forms send a prompt
and read back a uuid.

## Architecture amendment

**None.** No migration, no new table, no invariant touched. Two services
extracted from controllers with their behaviour preserved, four routes, one
controller, two form requests, two read-model additions, two pages extended.

## Review

Not `REVIEW_REQUIRED` under the standing policy: UI over already-approved
domain services, consuming SEC-001's existing middleware. It activates no real
provider — GEN-002 remains `BLOCKED_EXTERNAL` — introduces no invariant, and
every action it exposes was already reachable through the API surface merged in
GEN-001. The two extractions preserve behaviour and are covered by the
pre-existing tests.
