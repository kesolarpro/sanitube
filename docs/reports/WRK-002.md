# WRK-002 — where media work runs, and who decides

SaniTube installs on a cPanel account with no FFmpeg and on a VPS with a full
toolchain. Both are supported deployments. Until now the platform had one answer
— run it here — and a shared host simply went without analysis, fingerprints and
therefore duplicate detection.

WRK-001 built a boundary that could carry any kind of work. This puts media on
it, **without migrating anything.**

---

## Three strategies, and the middle one is the interesting one

| `SANITUBE_MEDIA_EXECUTION` | Behaviour |
| --- | --- |
| `local` | this machine, always. A worker offering the capability is not an invitation |
| `remote_worker` | the worker, and **unavailable** when it cannot serve |
| `auto` | prefer the worker when it advertises, this machine otherwise (shipped default) |

`remote_worker` deliberately does **not** fall back. An operator who selected a
worker has usually done so for a reason — a shared host whose CPU limit ffprobe
trips, a licence that lives on one machine — and a silent fallback would defeat
it without telling anybody.

An unrecognised value is `auto` rather than a boot failure: a typo in a `.env`
on a shared host must not take an installation down.

## The rule that carries the ticket

**Availability is never inferred from configuration.** A worker URL and a token
prove somebody typed two settings; they prove nothing about whether a worker
answers or whether it does this particular work.

- remote is offered only when the handshake succeeds **and** advertises the
  capability;
- local only when the tool is actually executable.

Both are asked, and asking is cheap — the handshake is cached, the local check
is an executable lookup, and nothing runs a probe to find out whether it could.

## No caller knows which machine ran

`AnalyzeAsset` and `FingerprintAsset` are unchanged except that they now offer a
storage key when the chosen path can use one. A test asserts neither file
mentions `WorkerClient`, `WorkerCapability`, `RemoteAudio` or `ExecutionPlace` —
the property this ticket exists to establish, enforced mechanically because it
is a boundary that erodes by somebody adding one convenient check.

`name()` and `version()` answer for whichever machine did the work, and that
matters: they are persisted as evidence and decide whether an asset needs
re-analysing. A worker running a newer ffprobe than this host is a real
difference, and a row claiming otherwise would hide it. The version comes from
the worker's own handshake.

## The bytes never pass through Core

A worker is handed a **storage key** and reads the object from the storage both
sides share. Streaming it down to Core's disk only for a worker to stream it
back up would be twice the egress for no benefit — on a cPanel account talking
to R2, twice the bill.

Two new capability interfaces, `AnalyzesStoredObject` and
`FingerprintsStoredObject`, are how an implementation opts in. The same pattern
the generation contract uses: callers test for it rather than every
implementation answering a question most of them cannot.

## Doctor tells the truth

| Reported | Status |
| --- | --- |
| `LOCAL_AVAILABLE` | available |
| `REMOTE_WORKER_AVAILABLE` | available |
| `REMOTE_WORKER_UNAVAILABLE_LOCAL_AVAILABLE` | **degraded** |
| `UNAVAILABLE` | optional, never blocking |

The third is the one worth having. Real work is happening, on the machine the
operator did not choose, and a green tick there is how somebody spends an
afternoon wondering why a shared host is slow.

`UNAVAILABLE` is **optional, not blocking**: a cPanel account with no FFmpeg and
no worker still ingests, catalogues and releases. Marking it required would make
a supported deployment look broken.

## The mandate's seven proofs

| # | Proof | Test |
| --- | --- | --- |
| A | local-only installation still analyses | `a_local_only_installation_still_analyses` |
| B | remote configured and healthy → worker probes | `a_healthy_worker_that_advertises_the_capability_does_the_probing` |
| C | remote unavailable + `auto` → falls back | `auto_falls_back_to_this_machine_when_the_worker_cannot_be_reached` |
| D | `remote_worker` unavailable → refuses honestly | `an_explicitly_selected_worker_does_not_quietly_use_this_machine` |
| E | capability missing → job not dispatched | `a_worker_that_does_not_advertise_the_capability_is_not_sent_the_job` |
| F | malformed answer → structured failure | `a_worker_answering_in_an_unexpected_shape_fails_structurally` |
| G | core boots with no worker | `core_boots_and_analyses_nothing_with_no_tools_and_no_worker` |

B and E run through the **real** HTTP boundary: Core's outbound call lands on
this application's own worker route, so the real middleware, validation and
handler execute.

## What did not change

`ProbeRunner` and `ChromaprintFingerprinter` are untouched and remain the whole
answer on a capable VPS. Nothing was removed, and the existing media suite
passes unmodified — which is the evidence that the domain result did not change.

## Verification

- **15 tests, 58 assertions** in `tests/Feature/Media/MediaExecutionStrategyTest.php`
- Full suite: **1983 passed, 1 skipped, 25589 assertions**
- PHPStan level 6 clean, Pint clean, vue-tsc clean, Vitest 23 passed

### Mutation testing — 11 mutations, 11 killed

Killed: inferring availability from configuration (M1), falling back from an
explicit `remote_worker` (M2), ignoring `local` (M3), defaulting an unreadable
strategy to local (M4), reporting a fallback as green (M5), a remote analyser
claiming to be always available (M6), abandoning the stored-object path (M7), a
worker forwarding to another worker (M8), leaking the worker's temporary copy
(M9), not naming a missing object (M10), accepting a malformed fingerprint (M11).

**Five survivors across two rounds, and one produced a design change.** M6
survived because `MediaExecution` asked the worker's capability *and* the remote
implementation asked it again — the same knowledge in two places, where one
eventually stops being updated. `placeFor()` now takes both availabilities as
callables and knows nothing about capabilities at all; the duplication is gone
and M6 is load-bearing.

M3 was a real gap: nothing proved `local` stays local *while a healthy worker is
offering*, which is the only case where the setting means anything. M9, M10 and
M11 were untested worker-side behaviour — a leaked temp file per probe, a
missing object surfacing as an unreadable stream rather than a named
configuration fault, and a malformed fingerprint being stored as evidence of
nothing.
