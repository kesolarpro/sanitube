# SYS-001 — Operations, jobs and health

## What this delivers

Two screens behind `can.role:administer`:

| Screen | What it answers |
| --- | --- |
| `/system/operations` | Is the platform's outside world working, is cron running, what is this installation configured as |
| `/system/jobs` | What work is waiting, and what broke |

Plus one explicit action: `POST /system/operations/refresh`.

## A GET probes nothing

This is the rule the whole ticket is built around, and it matters more here
than it did on the dashboard where UI-002's review first settled it.

**An operations page is what somebody opens during an outage.** A page that
reaches storage and three providers to render itself is slow when everything is
healthy and unusable exactly when it is needed. So both GETs read the stored
`OperationalHealthSnapshot`, the scheduler heartbeat and the queue tables, and
nothing else.

A test makes the boundary structural rather than stated: it forgets the stored
snapshot, loads the page, and then asserts **the snapshot is still absent**.
Reading did not become writing. A page that probed to fill the gap would have
left one behind.

"Check now" is the single exception — POST, behind the admin guard, pressed by
a person who asked for it. A probe that throws does not fail the page: reaching
out to storage and three providers is precisely the operation that fails when
something is wrong. A refresh that ran but could not *store* its result says so
too, rather than leaving a stale snapshot looking current.

## What must not leak, and does not

| Withheld | Why |
| --- | --- |
| `jobs.payload` | the serialised job object |
| `failed_jobs.payload` | the same |
| `failed_jobs.exception` beyond its first line | a stack trace: absolute paths, directory layout, often the arguments in flight |

SaniTube's own jobs carry uuids rather than models by convention — but a
payload is not a field this platform controls the contents of. A future job, a
package's job, a Laravel-internal job: *"we believe nothing sensitive is in
there"* is not a boundary. What somebody watching a queue actually needs is the
**kind** of work and the timestamps, and both are derivable from `displayName`
and the columns beside it.

For a failure, the exception's **first line** — the class and the message — is
what says whether this is a provider outage or a bug, so it travels. Even that
is truncated at 200 characters, because a message can be arbitrarily long and
some of them quote what they were given.

Reading one field out of a payload is not the same as publishing the payload. A
payload that does not parse yields `null`, which renders as "unrecognised" —
true, and a different fact from a job with no name. A test feeds in a payload
containing a fake token and asserts the token does not reach the page while the
class name does.

## Unknown is not zero

Every queue count is nullable and null means **unknown**. The database queue
tables are optional in Laravel: an installation on Redis or SQS has no `jobs`
table at all, and rendering `0` there would say "nothing is waiting" when the
truth is "this screen cannot see the queue".

A test drops both tables — what a Redis installation looks like — and asserts
the counts read null, the screen says so in a sentence, and **the page still
renders**.

## Freshness

The three states are inherited from UI-002 rather than reimplemented, and the
third is the one that matters:

- **UNKNOWN** — nothing stored. A fresh install, or the scheduler has never run.
- **STALE** — stored but older than the threshold. **Every availability verdict
  is blanked.** A result from a year ago is not evidence about now, and a health
  screen reporting green through an outage is worse than one reporting nothing.
  The names and the timestamp survive, because they say *what* was checked.
- **FRESH** — passed through as probed.

Tested at all three, including a snapshot deliberately dated a year back with
every verdict `true`, asserting all five come back null while the provider name
and timestamp remain.

## The scheduler gets its own card

Deliberately read from the heartbeat rather than from the health snapshot: **a
scheduler that stopped is exactly why a snapshot would be stale**, and reading
both from one place would make the cause and the symptom indistinguishable.

A cron entry nobody created is one of the quietest production failures there
is — retries, distribution sync and royalty imports simply never happen, and
nothing anywhere says so. `last_run_at` of null renders as a warning naming both
possibilities, not as "0 seconds ago".

## Runtime facts, deliberately narrow

PHP version, environment, and the four driver names. Enough to answer "am I on
the configuration I think I am". **No credential, host, bucket or path** — for
those the useful fact is whether one is *configured*, and that belongs to
SET-001.

Debug mode gets a warning of its own: in production it shows stack traces and
configuration to anybody who can trigger an error.

## Guardrails proven

Five regressions injected; **every one turned a test red**:

| Injected regression | Caught by |
| --- | --- |
| the job payload reaches the browser | 2 tests |
| the whole stack trace reaches the browser | no stack trace reaches the browser |
| an unreadable queue counts as zero | an unreadable queue reports unknown rather than zero |
| a stale snapshot keeps its verdicts | a stale snapshot never reports a verdict |
| the admin guard dropped from the system routes | a member may not see what the installation is doing |

## Tests

17 new tests. **859 PHP tests / 3685 assertions**, 1 skipped (the real ffprobe
run), plus 16 component tests. PHPStan level 6 clean, no baseline. Pint clean.

completeness gate passing both directions.

## Scope not covered, and why

The ticket lists Capabilities, Storage, Providers and Scheduler as separate
pages. They are **sections of the operations page** rather than four screens,
because all four read the same stored snapshot and splitting one snapshot
across four routes would mean four pages that can disagree about when it was
taken. The capability *detail* list — sixteen detectors with their individual
findings — is genuinely a page of its own and is recorded as **SYS-001b**,
along with retrying and deleting failed jobs, which are writes to the queue and
need their own confirmation surface.

The database queue remains the baseline throughout; Redis is optional and the
screens say plainly when they cannot see a queue rather than assuming one.

## Architecture amendment

**None.** No migration, no new table, no invariant touched. Two read models,
three controllers, three routes, two pages.

## Review

Not `REVIEW_REQUIRED` under the standing policy: read-only operational screens
plus one explicit non-destructive refresh, consuming SEC-001's existing
`can.role:administer` middleware and OBS-001's existing probe and store. No
authorization semantics change, no external action beyond the probe that
`sanitube:health:refresh` already performs on a schedule.
