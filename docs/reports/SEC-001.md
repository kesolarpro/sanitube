# SEC-001 — Identity & Authentication Foundation

**Status:** delivered
**Base:** `dfe062a` (main, after DIST-001)
**Branch:** `claude/sec-001-identity-auth`

---

## Why this ticket came before UI-001

Wave 3's brief makes SEC-001 conditional: build it *if* the absence of
Identity reasonably prevents exposing the UI. It does, and not marginally.

By the end of Wave 2 the platform can promote a candidate into the catalogue,
assemble a release and **hand it to a distributor** — the one irreversible act
in the system. There is no authentication of any kind. Shipping the UI screens
first would mean publishing those actions to anyone who reaches the domain,
and the masters the platform holds are unreleased.

So SEC-001 took priority, exactly as the brief directs.

## What it is, and what it deliberately is not

Session authentication on Laravel's own `users` table, three roles, and
nothing else. **No OAuth, no self-registration, no password reset flow, no
2FA.** Each of those is a real ticket; inventing them now would mean guessing.

**No self-registration is a decision, not an omission.** This is a label's own
catalogue, not a service people sign up for. An open registration form on an
installation holding unreleased masters is a way in, not a feature. Accounts
are created by `sanitube:user:create`.

## Three roles, and why only three

`OWNER`, `ADMIN`, `MEMBER`. A permission system with twenty granular flags is
one nobody configures correctly, and the platform's real boundaries are coarse:
either you can change the catalogue or you cannot, and either you can hand a
release to a distributor or you cannot.

`canDistribute()` is separate from `canWriteCatalogue()` even though the two
currently agree for every role. They are different questions — a member who can
assemble a release still cannot send it to a store — and the day they disagree
the call sites are already asking the right one.

`OWNER` exists apart from `ADMIN` for one reason: an owner cannot be locked
out, which is what stops a single-user installation becoming unadministrable.

## What the tests are mostly about

**Refusals that must be indistinguishable.** Wrong password, unknown email and
deactivated account all answer identically. A login form that says "no such
account" confirms which addresses have accounts, and enumeration is how a
credential-stuffing run gets targeted. A test asserts the two messages are
byte-identical.

**Throttling on email *and* IP.** Per-IP alone lets a botnet spread one
account's attempts across a thousand addresses; per-email alone lets one
address work through a list of accounts. A test also proves locking one email
does not lock everybody out — otherwise the throttle is itself a denial of
service.

Once locked out, even the **correct** password is refused. A lockout that
yields to the right guess only slows down an attacker who is still guessing.

**Session fixation.** The session identifier is regenerated on sign-in, and a
test asserts it changed.

**Deactivation takes effect on the next request.** Checking `is_active` only at
sign-in is not enough: a remember-me cookie can carry a session for weeks, so
somebody deactivated on Monday would still be working on Friday.

## A privilege-escalation boundary, found by a failing test

`role` and `is_active` are **not** in `$fillable`, and the first version of the
console command silently created every account as `MEMBER` because of it. The
fix was not to widen `$fillable` — mass assignment is how a request body
becomes a column, and a body that can set `role` is a privilege escalation
waiting for the first endpoint that forwards user input into `create()`.

The command uses `forceFill` instead, which is explicit and greppable, and a
test now asserts that passing `role => OWNER` into `create()` produces a
`MEMBER`.

## The CSRF test is structural, and says why

Laravel's `ValidateCsrfToken` short-circuits when `runningUnitTests()` is true,
so posting without a token in a test succeeds **regardless of the middleware
stack**. A behavioural assertion here would pass on a route with no protection
at all.

So both halves are checked instead: the route is in the `web` group, and the
`web` group carries the middleware. Either can silently stop being true alone.

## Passwords

Hashed by the model cast, so no plaintext can reach the column by somebody
forgetting a `Hash::make`. The console command prompts with `secret()`, never
`ask()` and never a `--password` option — shell history and process listings
both record arguments, and on a shared host that scrollback is somebody else's.

Minimum length twelve, no composition rules. A twelve-character passphrase is
stronger than `P@ss1!` and is one a person will actually remember rather than
write on a note.

**No complexity rule on sign-in**, only on creation: rejecting a login because
the stored password predates a policy would lock a real user out of their own
account.

## The login page is Blade

Not Vue, deliberately. This is the one screen that must render before any
application JavaScript has been trusted, and before the asset pipeline has been
built — which is precisely the state a fresh installation is in. Its CSS is
inline and about forty lines. UI-001's Vue shell begins after this.

Every string goes through the translator. All six locales — en, fr, es, it, pt,
de — ship complete.

## The translation gate, generalised

The existing completeness test named one file, `sanitube.php`, so the identity
strings would have been invisible to it. It now walks **every** file in
`lang/en` and checks every configured locale against it — and a second test
checks the other direction, because a key that exists only in French is usually
a rename applied to one file and forgotten in the rest.

Confirmed to reject a deliberately removed key before being confirmed to accept
the restored one.

## Architecture amendment

**None to a validated ticket.** One additive migration on Laravel's `users`
table — `uuid`, `role`, `is_active`, `last_login_at` — with the uuid backfilled
before its unique index so an installation with existing rows does not fail.

`App\Models\User` stays where it is rather than moving into `src/Identity`:
`config/auth.php` points at it and Laravel's password-reset plumbing resolves
it, so a move would be a rename with no behavioural benefit. The *rules* live
in `UserRole`, which is where the domain is.

## Not done here

- **The UI is not yet gated.** SEC-001 provides `auth`, `active` and
  `can.role:*`; applying them is UI-001's job, when there are screens to apply
  them to. The middleware is proved against testing-only probe routes.
- **No password reset.** It needs mail configured, which INS-001 sets up.
- **No user administration screens.** The console command is the whole surface.
