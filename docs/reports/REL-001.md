# REL-001 — Release Workflow

**Status:** delivered
**Base:** `6e5928b` (main, after AI-001)
**Branch:** `claude/rel-001-release-workflow`

---

## What this ticket is actually about

ARCH-002 modelled what a release *is* and enforces I4. REL-001 is how one gets
**built** — and, more importantly, when it stops being buildable.

Two things carry the design: keeping the tracklist numbered in a way a store
will accept, and refusing to change a package somebody has already been given.

## "Editable" means three different things

ARCH-002 gave a release a status; it never said which edits each status
permits. `ReleaseMutationPolicy` says so in one place rather than through nine
scattered `if` statements:

| Status | Structural change | Reopen |
| --- | --- | --- |
| `DRAFT` | yes | — |
| `READY` | **no** | yes |
| `SUBMITTED` / `DELIVERED` / `LIVE` | no | **no** |
| `TAKEN_DOWN` | no | no |

`READY` refuses edits because READY is a *statement that the package passed
validation*; adding a track afterwards would leave a release marked ready that
never was. It can be **reopened** to DRAFT, which is an explicit act that
records the retraction.

A committed release cannot be edited or reopened at all. Its recordings exist
outside SaniTube — a store is serving them and a royalty statement will
reference them — and editing the local record would make it disagree with what
the world already has. **I4 is never bypassed to make any of this smoother.**

## Numbering is the builder's job, not the caller's

`addTrack()` derives the next number. A caller that picked its own would
eventually pick one that already exists, and a tracklist with two number 4s is
a delivery a store rejects.

`removeTrack()` closes the gap immediately. A list running 1, 2, 4 is rejected
on delivery, and leaving the gap until somebody happens to reorder means the
release is invalid in a way nobody looked at.

`reorder()` takes a list of uuids — the list *is* the order. Tracks the caller
did not mention keep their relative order and follow; dropping them would make
reorder a destructive operation that looks like a cosmetic one.

### The unique index, and the two-phase write

`release_tracks` carries `UNIQUE (release_id, disc_number, track_number)` from
ARCH-002 — the guarantee that no two tracks share a position. Renumbering row
by row collides with it the moment a track moves into a slot another track has
not yet left, and a test caught exactly that.

Every row is therefore parked above the occupied range first, then written to
its final number. Two passes, because the alternative was dropping the
constraint that makes the ordering trustworthy in the first place.

## Validation reports two kinds of thing

`ReleaseValidationResult` carries `valid`, `errors[]` and `warnings[]`.

The separation is the point. A release with no cover cannot be delivered —
every store rejects it — while one with no catalogue number is merely
incomplete. A validator that reported both as errors would train its reader to
ignore the list.

**Errors:** everything `Release::readinessProblems()` already enforces (I4,
unmodified and not relaxed), plus duplicate track numbers, a gap in the
numbering, a non-releasable track, a cover that is not artwork, and an
unverified cover.

**Warnings:** no label name, no catalogue number, missing ℗/© line, an
undetermined release language, no focus track on a multi-track release, a track
with no genre, and a track with no measured duration — the last of which
usually means the host has no FFmpeg rather than that anything is wrong.

`validate` and `ready` are separate endpoints because they answer different
questions. A label wants to *see* what is missing while it is still assembling;
a validator that only runs at the last moment is a validator nobody uses.

## Covers are checked when they are set

Not only at readiness. A cover that turns out to be an unverified audio file is
a mistake worth catching when it is made, rather than at the end when somebody
is trying to deliver.

## API

```
POST   /api/v1/releases                                  → 201 DRAFT
PATCH  /api/v1/releases/{uuid}
POST   /api/v1/releases/{uuid}/tracks
DELETE /api/v1/releases/{uuid}/tracks/{track_uuid}
POST   /api/v1/releases/{uuid}/tracks/reorder
POST   /api/v1/releases/{uuid}/validate
POST   /api/v1/releases/{uuid}/ready
POST   /api/v1/releases/{uuid}/reopen
```

**Nothing sets `status` directly.** Readiness is earned by passing validation,
not assigned; a settable status field would make I4 optional. A test PATCHes
`status: LIVE` and asserts the release is still DRAFT.

Every refusal carries a machine-readable code: `RELEASE_NOT_EDITABLE`,
`RELEASE_NOT_REOPENABLE`, `TRACK_ALREADY_ON_RELEASE`, `TRACK_NOT_ON_RELEASE`,
`COVER_NOT_USABLE`, `PRIMARY_ARTIST_REQUIRED`, `RELEASE_NOT_READY`.

## Architecture amendment

**None.** No migration, no column, no relation, no invariant. REL-001 is
entirely services, a policy object, a validation result and routes on top of
ARCH-002's schema. I4 is called, not reimplemented.

## Two things worth flagging

**A route edit silently did nothing.** The first attempt anchored the new
routes on a GEN-001 route that does not exist on this branch, and the
replacement no-op'd — `route:list` showed two routes where there should have
been ten, and the API tests failed with 405. Re-applied with an assertion on
the anchor. Worth stating because a silent string replacement is exactly the
kind of edit that looks applied and is not.

**`ReleaseBuilder::reopen()` has no counterpart for committed releases**, by
design. If a delivered release needs to change, that is a takedown and a new
delivery — a DIST-001 concern, not an edit.
