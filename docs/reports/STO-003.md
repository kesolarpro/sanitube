# STO-003 — uploading a master without it passing through the application

## The finding that shaped the ticket

Phase 2 opens with "add Cloudflare R2 as a first-class storage provider".
**R2 was already there** — `CloudflareR2Provider`, wired in `config/storage.php`,
with expiring download URLs. So was S3, and B2.

What was missing is the half that matters on the hosts this platform targets:
a browser cannot write into any of them directly, so every byte of every master
still went through PHP.

## Why that is not a small thing

A master is routinely hundreds of megabytes and may be two gigabytes. For that
to pass through PHP on a shared cPanel account, `upload_max_filesize`,
`post_max_size`, `memory_limit` and `max_execution_time` must all be generous
at the same time — and on the accounts SaniTube is built for, at least one of
them never is. Raising four PHP limits to move a file is not a deployment
story; it is a list of ways an upload fails at 80 %.

## The design

Two POSTs, and the application stays out of the data path between them.

1. `POST /assets/uploads` — authorises, **registers the asset**, mints a
   15-minute capability to PUT one object at one key.
2. Browser writes to object storage.
3. `POST /assets/uploads/{asset}/complete` — the server goes and measures.

**The registration comes first, deliberately.** It is what decides both the
staging key and the canonical key, from the asset's own uuid. Minting the URL
first would hand out a capability for a location nothing had claimed.

### The claim this ticket defends

> Giving up the data path is not giving up authority.

The browser chooses the bytes. It does not choose where they go, what they are
called, how large they may be, what they hash to, or whether they were
acceptable — and **the completion call is a request to go and look, not a report
to be believed.** It carries no size, no checksum and no media type, because
anything it carried would be the browser's word for it.

### No second storage workflow

`AssetStorageService::store()` had a long tail after the upload: measure, cap,
checksum, sniff, find duplicates, move to canonical, write the row. That tail is
now `settleStagedObject()`, and both paths use it.

A direct upload that measured itself, or skipped the duplicate check, or moved
its own object, would be a second storage workflow with its own bugs — and the
one that gets a fix later. Extracting rather than duplicating means the
identity rules, the refusals and the discard-on-rejection behaviour are the same
code, in the same order, whichever way the bytes arrived.

### The size cap, where it can actually be enforced

A presigned PUT cannot express a maximum. So the cap moves to the only place it
can be: after the object exists, measured from it, discarded if too large. The
comment that used to explain the byte-cap filter's `limit + 1` now explains
both arrivals, because one of them has no filter in front of it at all.

The staging lifecycle policy remains the backstop for whatever is abandoned.

### Capability, not a method on everything

`SupportsDirectUpload` — the shape DIST-001-H1 settled for submission lookup.
The local disk cannot mint an upload URL and **must not pretend to**; an
install on a shared account with no object storage keeps the ordinary path, and
the interface is how the application knows which it is looking at. The server
refuses regardless of what the interface offered.

`PresignedUpload` carries the URL *and* the headers the request must sign,
because returning the URL alone leaves every caller to rediscover the signature
mismatch one two-gigabyte upload at a time.

## Three findings

**1. The portability guards caught vendor vocabulary.** `StorageBoundaryTest`
refused the word `s3` in `src/Assets`, twice. Correct: the domain must not name
a vendor. Reworded to "object storage provider".

**2. The same guard caught a trait in `src/Storage/Providers/`** that is not a
provider. Moved to `src/Storage/Concerns/`, which is where it belonged.

**3. A test double was lying.** The first version of the no-capability test gave
`InMemoryStorageProvider` a `directUploads: false` flag — a provider that
**declares the capability and then throws**, which is precisely the broken
promise the interface exists to prevent. Replaced with the real
`LocalStorageProvider`, which genuinely does not implement it, and the flag was
removed from the double so nobody can reintroduce the lie.

## Mutation testing

Four injected, three killed, one withdrawn.

| # | Mutation | Result |
|---|---|---|
| M1 | Missing staged object no longer detected | killed by `an_upload_that_never_arrived_is_refused` |
| M2 | Size cap removed | killed by `an_object_over_the_limit_is_discarded_rather_than_kept` |
| M3 | Capability check removed | killed by `a_provider_that_cannot_mint_upload_urls_refuses_rather_than_pretends` |
| M4 | Upload URL written into the audit log | **withdrawn** |

**M4 is withdrawn rather than chased.** It survived because AUDIT-001's
redaction refuses any value containing a URL, under any key — so a call site
that deliberately logs the signed URL still cannot get it into the row. The
guarantee is real and already has its own mutation coverage where it lives.
Adding a second assertion here would test the same rule twice and imply the
call site was the thing protecting it. The test now says so.

## Not in this ticket

- **Multipart.** A single presigned PUT covers the sizes this platform sees
  today. Multipart needs `CreateMultipartUpload` / per-part signing / `Complete`,
  which is a provider-level API rather than a Laravel filesystem one — a ticket
  of its own, and only worth it once a real upload proves it is needed.
- **The browser side.** The endpoints and their contract exist and are tested;
  the upload control is a UI ticket.
- **Staging lifecycle configuration.** Documented for R2 in the deployment docs
  rather than assumed here.
