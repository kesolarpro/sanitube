# GEN-004 — The two brakes on unattended generation

Named as out of scope in GEN-003's report, and built here rather than left as a
note. PROD-001 through PROD-003 assembled a planner whose entire purpose is to
decide, without a person present, that more music should exist. Nothing bounded
how many requests that could become.

ENR-003 gave completions a ceiling and a breaker. A completion is cents. A
generation is not, and had neither.

---

## Operational safety, not finance

Stated once and enforced by a test: **this counts requests.** It holds no
prices, no currency, no balance and no invoice, and it is not a step towards
any of those. The question it answers — "should we keep going" — is an
operations question, and the answer is a number of requests.

`nothing_here_holds_money` reads the source of both services, strips comments
with `token_get_all` and scans the code alone for a list of forbidden words and
currency symbols. Comments are stripped because the docblocks *promise* there is
no currency here, and an earlier version of this test in ENR-003 failed on its
own explanation of itself.

---

## The ledger is `music_generations` itself

No second table, because there is nothing a second table would know:
`submitted_at` is written exactly when a request left this server for a
provider, which is the definition of the thing being counted. A parallel
counter would be a second source of truth and would drift the first time a row
was removed by hand — the argument `BacklogGuard` makes about queue depth.

That column also keeps the count honest in the other direction. A generation
refused before submission — no provider configured, a claim lost to another
worker, a ceiling like this one — has no `submitted_at` and cost nothing, so it
does not count against the ceiling that produced it.

---

## What was built

**`GenerationSpendGuard`** — rolling 24h / 168h / 720h windows against
`generation.limits.daily|weekly|monthly`. Zero means no ceiling and is the
shipped default: a platform whose first experience of the feature is a refusal
would be a worse platform. `exhaustedWindow()` returns a *name* rather than a
boolean, and returns the **longest** exhausted window, because "you have run
out" and "you have run out until Tuesday" are different instructions and the
monthly one is the one still true tomorrow.

Rolling rather than calendar: a calendar month needs a time zone to be
meaningful and a reset somebody has to remember, and it can be gamed by starting
a run at 23:55.

**`GenerationCircuitBreaker`** — per provider, derived from the ledger with no
state of its own, half-open for free. Kept as a separate class from
`AiCircuitBreaker` rather than generalised: the two read different ledgers with
different notions of "attempted", and an abstraction over that would have to be
told which one it was looking at on every call — which is a parameter, not an
abstraction.

**Wired in two places, and the difference is stated in the code.**
`StartMusicGeneration` refuses before a row exists, because the refusal an
operator can act on is the one that arrives before there is a QUEUED generation
sitting there looking like work in progress. `SubmitMusicGeneration` checks
again, and **that is the check that counts** — a person clicked when there was
room, and a queue can run hours later with a thousand siblings ahead of it.

### One honest limitation, in the docblock rather than in a footnote

The ceiling counts requests that *left this server*, and starting reaches
nobody. So a hundred generations started in one breath all pass the start-time
check; it fires only once earlier **submissions** have filled the window. That
check is a courtesy, not the bound.

Counting starts instead would be worse in the direction that matters: a
generation refused before submission costs nothing, and letting it consume the
ceiling would let a failed run lock out a working one.

## §1 — the two proofs

**A. COMPONENT/SERVICE PROOF.** `tests/Feature/MusicGeneration/GenerationSpendSafetyTest.php`,
18 tests / 68 assertions, covering both services directly.

**B. PRODUCTION-PATH PROOF — who calls this in production?**
`SubmitMusicGenerationJob`. Two tests run the real job class against a
generation started while things were healthy, with the brake tripping in
between:

- `a_ceiling_reached_while_the_job_waited_stops_the_request`
- `a_circuit_that_opened_while_the_job_waited_stops_the_request`

Both assert the provider was **not asked** — `generationsCreated()` unchanged —
rather than only that a status was written. A backlog discovering an outage once
per item is the failure this exists to prevent, and only the call count proves
it did not happen.

## §2 — mutation results

Sixteen mutations. **Three survived on their first run.** All three were my
tests being wrong, and all three are recorded here rather than smoothed over.

### N5 — a real scenario, not a contrived assertion

`config('generation.limits.daily', 0)`'s fallback was never exercised, because
the shipped config file always defines the key. Killed by a test for a real
situation: an operator editing `config/generation.php` by hand, or an older
config surviving an upgrade, leaves the key absent — and the fallback has to be
the same "no ceiling" the shipped file states, because any other default
silently throttles an installation that never asked to be.

### N9 — the right answer for the wrong reason

`failures_before_submission_say_nothing_about_the_provider` passed whether or
not the breaker filtered unsubmitted rows, because such a row also has no
`submitted_at` and therefore fails the freshness check too. Green, and proving
nothing about the clause it was supposed to cover.

The discriminating case puts the unsubmitted row **in the middle**: two genuine
failures must not open a threshold-of-three circuit merely because a row that
never reached the provider sits between them. With the filter the breaker sees
two rows and stops; without it, three. That test kills N9.

### N3 — withdrawn, and why

Removing `whereNotNull('submitted_at')` from the **spend guard** survives
because it is genuinely redundant: three-valued logic makes `NULL >= x` evaluate
to NULL, which `WHERE` treats as not-true, so the window comparison beside it
already drops unsubmitted rows. Killing this would need a test that breaks the
comparison to expose the clause — precisely the brittle implementation test §2
forbids.

So the mutation is recorded as **withdrawn against a redundant branch**, and the
clause stays because it states the intent at the point of the query. What
changed instead is that the redundancy is now *asserted rather than assumed*:
`a_null_submission_time_is_excluded_by_the_comparison_itself` proves the
three-valued behaviour, and it runs on SQLite, MySQL 8 and both MariaDBs in CI —
the only way to know it holds on all four rather than on the one a developer
happened to use.

The same clause in the **breaker** is not redundant, is load-bearing, and is
killed by N9. The two looked identical and are not; that is worth knowing.

## What this ticket did not do

- **No status screen.** `remaining()` exists and is tested, and nothing renders
  it. An operator can set a ceiling and cannot yet see how much of it is left.
  Named rather than quietly shipped as complete.
- **No pause switch for generation.** ENR-003's AI equivalent has one. Separate
  ticket.
- **Nothing certified against a real provider.** GEN-002 unchanged.
