# GEN-003 — Generation hardening

Two defects in the existing generation path, both of which cost something real.
Found by reading the path that PROD-003 is about to start driving
automatically, not by a test failing.

---

## What was wrong

### 1. The provider's exception message was rendered in a browser

`SubmitMusicGeneration` caught `Throwable` and wrote `$exception->getMessage()`
straight into `failure_reason`. `PollMusicGeneration` did the same with the
vendor's `failureReason`. That column is rendered by
`resources/js/Pages/Studio/Generations/Show.vue` and returned by
`Api\Http\Resources\V1\MusicGenerationResource` — neither of which sanitised
anything.

An HTTP client's exception message quotes the request that produced it. Guzzle's
carries the full request URI; Laravel's `RequestException` appends the response
body. **On a provider authenticated by a query-string token, that message *is*
the credential**, and it was going to a screen.

This is the constraint *"do not dump external provider raw secrets/errors
directly to browser"*, and the code violated it. Nothing had leaked, because no
real provider has ever been configured — which is exactly why it was still
there.

### 2. Two workers could both pay for one generation

The idempotency check was:

```php
if ($generation->provider_job_id !== null || $generation->status->isTerminal()) {
    return $generation;
}
```

A read-then-write. `provider_job_id` makes a *finished* submission idempotent,
but it cannot make an *in-flight* one exclusive, because for the entire duration
of the call it guards, the column it guards on is still null. Two workers handed
the same job both read null, both call the provider, and the installation pays
twice — with the second job identifier belonging to a row nobody polls.

The rest of the platform does not work this way. PROD-002 claims a production
slot with a guarded `UPDATE`; ENR-004 decides a suggestion with one. This was
the outlier.

Two smaller things came with it: `SubmitMusicGenerationJob` had no `$tries`, so
a queue retry could submit a second billed generation; and `poll_count` was
incremented by reading and adding one, so two concurrent polls advanced the
bound by one instead of two — the bound that exists to stop a runaway loop being
the thing a runaway loop evaded.

## What was built

**`src/MusicGeneration/ProviderFailure.php`** — the only thing allowed to write
`failure_reason`. Text is sorted by who wrote it:

| Author | Treatment | Why |
|---|---|---|
| The platform (a `GenerationException`, or a literal in these services) | carried unchanged | We wrote it. It says only what we chose to say. |
| A vendor explaining itself | kept, but redacted against every configured credential, stripped of anything URL-shaped, flattened to one line, bounded to 300 characters, and **attributed** | "Rejected for explicit content" is worth showing. A signed callback URL's token is in no config file, so redaction cannot recognise it — the only safe rule is that a failure reason never contains an address. |
| Any other throwable | message dropped entirely; status code kept when there is one | A transport exception describes the request, and the request is the thing that must not be described. 401 is a key, 429 is a rate limit, 5xx is theirs — that is the actionable part. |

Attribution is not decoration. "Rejected for explicit content" from the platform
is a policy decision somebody can appeal to us; from a vendor it is a report of
what they did. The prefix is which one a reader is looking at.

`forDisplay()` applies the same sanitiser again at both read boundaries. Rows
written *before* this ticket hold whatever the client said, and a migration
cannot clean them — the damage, if any, is already in the column. So the screen
and the API refuse to render an address regardless of how it got there.

**The submission claim.** One additive nullable column,
`submission_claimed_at`, and a guarded `UPDATE` whose affected-row count decides
the winner — atomic on every engine in the matrix, no transaction, no lock. A
worker that loses returns the row untouched: a lost race is a success, because
somebody else is doing the work.

The claim **expires**, and that is a trade rather than a fix. Its holder can die
between claiming and calling, and a permanent claim would leave that generation
QUEUED for ever with nothing able to pick it up.
`generation.submission_claim_seconds` (default 900) bounds it: too short and a
slow provider gets asked twice, too long and a crash stalls a generation. It is
configurable because there is no right answer, and the config comment says so
rather than pretending fifteen minutes is a law.

The cutoff is computed in PHP and bound as a value. ADR-0017's rule about
arithmetic on columns applies to timestamps too, and `NOW() - INTERVAL` is
spelled differently on each engine in the matrix.

**Also:** `public int $tries = 1` on `SubmitMusicGenerationJob`, matching
`TranscribeAssetJob` and `SuggestMetadataJob` from ENR-003. And `poll_count`
incremented by the database with `DB::raw('poll_count + 1')` — an addition, not
a subtraction, so ADR-0017's unsigned rule does not bite.

## §1 — the two proofs

**A. COMPONENT/SERVICE PROOF.** `tests/Feature/MusicGeneration/GenerationHardeningTest.php`,
16 tests / 50 assertions. The leak is asserted by its shape, not its wording: a
literal URL carrying `sk-live-…` in a query string goes in, and the assertions
are that the token, the host and the client's own vocabulary are all absent from
what comes out.

**B. PRODUCTION-PATH PROOF — who calls this in production?**

- **`SubmitMusicGenerationJob`**, dispatched when a generation starts.
  `the_submission_job_does_not_retry` runs the real job class twice and asserts
  the provider was asked once, and that `tries` is 1.
- **The Studio generation detail screen**, `GET /studio/generations/{uuid}`.
  `the_studio_screen_renders_the_sanitised_reason` writes a pre-ticket raw
  reason *past* the service, then asserts the rendered HTML contains neither the
  token nor the host.
- **The internal API**, `GET api/v1/generations/{uuid}`.
  `the_api_returns_the_sanitised_reason` does the same against the JSON.

The service being safe was never the claim. Both read boundaries are.

## §2 — mutation results

Sixteen mutations. **All sixteen killed.**

The harness reads the **test runner's exit code**. It does not grep its output:
this session established that test *names* contain the word "fail", so a
grep-based harness reports a kill on a run where everything passed. Baseline
(unmutated) was confirmed exit 0 first.

| # | Mutation | Verdict |
|---|---|---|
| M1 | `fromThrowable` treats every exception as ours | killed |
| M2 | drop the `GenerationException` branch | killed |
| M3 | drop the `RequestException` branch | killed |
| M4 | remove URL stripping | killed |
| M5 | a wholly-redacted message is attributed instead of falling back | killed |
| M6 | remove the length bound | killed |
| M7 | skip the claim entirely | killed |
| M8 | claim succeeds on any affected-row count | killed |
| M9 | claim ignores its guard (always wins) | killed |
| M9b | claim never expires | killed |
| M10 | claim not released after a successful submission | killed |
| M11 | poll count back to read-then-write | killed |
| M12 | the Studio query stops sanitising | killed |
| M13 | `tries = 3` | killed |
| M14 | the poll path writes the vendor's words raw | killed |
| M15 | the submit path writes `$exception->getMessage()` — the original defect | killed |
| M16 | the API resource stops sanitising | **survived at first** |

**M16 survived on its first run, and that is worth recording rather than
smoothing over.** I had added `forDisplay()` to the API resource with no test
behind it — a guard nobody was checking, which is indistinguishable from no
guard the next time someone refactors. The fix was the missing test
(`the_api_returns_the_sanitised_reason`), not a weaker mutation. M16 was then
re-run and killed.

No mutation was withdrawn.

## One existing test changed

`MusicGenerationTest::a_provider_failure_is_recorded_with_its_reason` asserted
`'Content policy refusal.'` exactly. It now asserts
`'The [fake] provider reported: Content policy refusal.'`. That is a deliberate
contract change, not a test bent to fit: the vendor's words are still there in
full, now attributed. Recorded here because a changed assertion in an existing
test is exactly where a regression hides.

## What this ticket did not do

- **No spend ceiling or circuit breaker for generation.** ENR-003 built both for
  AI completions, and music generation is at least as expensive and about to be
  driven by production plans. It belongs in its own ticket, against the same
  invocation-ledger shape, and is not silently covered by this one.
- **`DeliveryDetailQuery::reason()` truncates but does not redact.** The same
  class of exposure exists in the distribution module — a first line is exactly
  where a URI lives. Out of scope here; named so it is not lost.
- **Nothing was certified against a real provider.** GEN-002 is unchanged. This
  hardens the path a real adapter will take; it does not create one.
