# SET-002 — changing configuration from the interface

## The shape of the problem

SET-001 built the read side and was careful about it: a credential is reported
as **configured** or **not configured** — never a value, never a mask, never a
length, because a length narrows a search and a suffix confirms a guess.

SET-002 has to do the opposite thing while keeping that promise. The screen must
accept a new API key without ever having sent the old one.

## Four rules

**A blank field never clears anything.** For a secret that is the point: the
field renders empty because the browser is never told what is in it, so a blank
submission is what an operator sends when they edited something *else* on the
page. Treating it as "set to nothing" would erase a provider key every time
somebody changed the poll interval beside it.

For a plain setting it is a consequence rather than a choice — see the finding
below — and the outcome is the same: **removal is not offered through this
form.** Emptying a value stays a `.env` edit, which is visible and deliberate.

**One write, or none.** Four calls to `set()` are four rewrites of the file, and
a failure on the third leaves an installation configured half one way and half
the other. `EnvironmentFile::setMany()` does it in a single `file_put_contents`
over a backup taken first.

**The config cache is rebuilt, or the whole thing was theatre.** An installation
that has run `config:cache` reads nothing from `.env` at runtime. Writing the
file and reporting success would leave an operator staring at a screen saying
the new key is configured while the platform keeps using the old one. If the
rebuild fails the previous `.env` is restored: a cache that no longer matches
the file is worse than the state we started in.

**Nothing written is reported back.** The audit line names the variables that
changed, never their values; the response says whether anything changed at all.
A confirmation quoting the new API key would undo the entire read side in one
line.

## What may be written, and what may not

An allowlist of thirteen variables. What is **absent** is the interesting part:

- `APP_KEY` — replacing it makes existing sessions and any encrypted column
  unreadable. The installer refuses to regenerate it for the same reason.
- `APP_ENV`, `APP_DEBUG` — debug on in production puts stack traces, queries and
  environment values in front of whoever triggers an error. A deployment
  decision, not a form field.
- `DB_*` — repointing a running installation's database from a web form is not a
  setting, it is a migration. The installer is where that belongs.

What is there is what a label genuinely has to rotate without a shell: provider
keys, bucket credentials, the two API tokens, and the numeric limits that change
with usage.

`every_writable_variable_is_one_the_screen_actually_shows` asserts the registry
against the read model across several provider selections. Two lists that can
drift are two lists that will, and the failure mode is a field an operator can
change and cannot see the state of.

## Three findings, all from mutations that survived

**1. The `secret` qualifier on "is this unchanged" was dead code.** The first
version treated a blank *secret* as unchanged and a blank *plain* setting as
empty. Laravel's `ConvertEmptyStringsToNull` turns every empty field into null
before it arrives, so the empty-string branch was unreachable and the two cases
had always behaved identically. A distinction that reads as a decision and does
nothing is worse than being uniform, so the rule is now uniform and says why.

**2. The allowlist is enforced twice, which is why one mutation could not kill
it.** `UpdateSettingsRequest::validated()` strips unknown keys, and
`UpdateSettings` iterates the registry rather than the submission. Removing
either alone changes nothing. The mutation that names the property removes both
— and then the test fails. Defence in depth is the finding, not a gap.

**3. Backup count proves nothing about write count.** `EnvironmentFile` takes one
backup per run whether it writes once or four times, so the original
"several changes are one write" test asserted a number that a mutation walked
straight through. Replaced with the property that actually matters and is
observable: **a write that cannot happen is refused, changes nothing, and
records nothing.**

That third test also had to be made deterministic. A `chmod 0444` version passed
locally and proves nothing in a container running as root — root writes
read-only files happily. It points the environment file at an unwritable *path*
instead.

## Mutation testing

Six injected, five killed, one withdrawn.

| # | Mutation | Result |
|---|---|---|
| M1 | A blank field no longer means unchanged | killed by `a_blank_secret_leaves_the_existing_one_alone` |
| M2 | Both allowlist layers removed | killed by `nothing_outside_the_list_is_written_however_it_is_submitted` |
| M3 | A failed write reported as a success | killed by `a_write_that_fails_leaves_the_file_exactly_as_it_was` |
| M4 | Audit context carries the written values | killed by `the_audit_line_names_the_variable_and_never_the_value` |
| M5 | Config cache never rebuilt | **withdrawn** — see below |
| M6 | Write route moved outside the administer group | killed by `a_member_may_read_the_settings_screen_and_change_nothing_on_it` |

**M5 is withdrawn rather than distorted.** The rebuild branch only runs on an
installation that has actually executed `config:cache`, which the test suite
never has — and creating a real `bootstrap/cache/config.php` mid-test to force
it would leave a stale cache behind on a crash and break every subsequent run.
The branch is therefore **unproven by the suite** and belongs to real-host
certification, which is where it is now listed. Manufacturing a green assertion
for it would have been worse than saying so.

## REVIEW_REQUIRED?

No. §6 sets the bar at "a fundamentally new secrets architecture", and this is
not one: it writes through the installer's existing `EnvironmentFile` — which
already backs up before writing and refuses to write without a backup — reads
through `config` and never `env()`, and records through the audit log built in
AUDIT-001. It is a security surface and is flagged as one, but it introduces no
new mechanism for handling secrets.
