# UPL-005 — le jeton que la mise en page ne publiait plus

## Le problème

`resources/views/app.blade.php` ne contenait aucune balise
`<meta name="csrf-token">`. Trois écrans en lisaient une :

| Écran | Ce qu'il construit à la main | Pourquoi pas Inertia |
|---|---|---|
| `Pages/Ingestion/Import.vue` | `XMLHttpRequest` vers `/ingestion/import/relay` | progression d'envoi, et annulation en cours de transfert |
| `Pages/Assets/Upload.vue` | `XMLHttpRequest` vers `/assets/uploads/relay` | idem |
| `Pages/Settings/Index.vue` | `fetch` vers `/settings/test` | réponse lue, pas une visite de page |

Une visite Inertia signe toute seule : axios lit le cookie `XSRF-TOKEN` et pose
`X-XSRF-TOKEN`. C'est précisément pour cela que le reste de l'interface — y
compris l'enregistrement des réglages par `router.patch` — n'a jamais rien eu.
Les requêtes bâties à la main, elles, ne signaient plus rien.

La balise absente, `csrf()` renvoyait la chaîne vide, l'en-tête `X-CSRF-TOKEN`
partait vide, `VerifyCsrfToken` refusait, et la requête mourait en **419 avant
d'atteindre le contrôleur**. Aucun octet n'a jamais atteint
`InboxDepositController`.

**La preuve.** Requête réelle depuis le navigateur authentifié de l'utilisateur
sur `https://sanitube.livegine.com/ingestion/import` : MP3 de 4 700 000 octets
posté sur `POST /ingestion/import/relay`, en-tête CSRF vide, réponse `419`,
`content-type: application/json`, corps `{"message": "CSRF token mismatch."}`.
Le payload Inertia de la même page montrait une configuration saine :
`direct: false`, `effective_maximum_bytes: 67108864`,
`php_post_limit_bytes: 67108864`, `limited_by_php: true`, `audio/mpeg` dans
`accepted_types`, `per_request: 50`, `concurrency: 3`.

**Pourquoi le message était générique.** `readCode()` ne lisait que la clé
`code` du corps JSON. Une 419 de Laravel est `{"message": "…"}` sans `code`, donc
`readCode` retombait sur `DEPOSIT_FAILED`, traduit par « Le fichier n'a pas pu
être déposé. » Le serveur disait exactement ce qui n'allait pas ; l'interface
l'a jeté et l'a remplacé par une phrase qui ne nomme rien.

**Pourquoi les journaux étaient vides.** Une 419 est une `HttpException` rendue,
pas une exception rapportée. Rien n'apparaît dans `laravel.log`. L'absence de
trace n'était pas l'absence de problème.

**Ce que cela explique.** La taille n'a jamais compté : 4,7 Mo et 126 Mo
échouaient à l'identique. Ni le type MP3, ni le nom du fichier, ni les
permissions de stockage n'étaient en cause. `upload_max_filesize`,
`post_max_size` et `client_max_body_size` étaient déjà corrects, et les relever
n'aurait rien changé. UPL-004 a corrigé un défaut voisin bien réel — l'écran
promettait un plafond que `post_max_size` refusait — mais pas celui-ci.

**Pourquoi les tests ne l'ont pas vu.** Les tests de fonctionnalité passent par
le client de test de Laravel, où `VerifyCsrfToken` ne s'applique pas du tout.
Les tests Vitest simulent le réseau. Entre le gabarit Blade qui publie le jeton
et le JavaScript qui le lit, il n'y avait rien : le seul contrat de
l'application avec un producteur, un consommateur, et aucune assertion pour les
joindre.

## Ce que fait ce changement

### 1. La cause : la balise

Une ligne dans `app.blade.php`, une seule source pour les trois écrans. Les
gabarits d'identité (`login`, `password-request`, `password-reset`) l'avaient
déjà ; c'est le gabarit de l'application qui ne l'avait pas.

### 2. La robustesse : lire un refus pour ce qu'il est

`resources/js/Support/request.ts` — un utilitaire, partagé par les trois écrans,
plutôt que trois copies qui divergeront.

```
refusalCode(status, body, fallback)
```

1. **Le corps d'abord.** Tout refus que l'application écrit elle-même porte un
   `code`, et ce code est plus précis que n'importe quel statut :
   `MEDIA_TYPE_NOT_ACCEPTED` et `FILE_TOO_LARGE` sont tous deux 422 et ne se
   lisent pas pareil. `503 STORAGE_UNAVAILABLE` — « rien n'est perdu, réessayez »
   — reste `STORAGE_UNAVAILABLE` et ne devient pas « erreur serveur ».
2. **Le statut ensuite**, et seulement pour les refus que l'application n'écrit
   jamais : ceux du framework, du serveur web, de PHP.

   | Statut | Code | Ce que la personne lit |
   |---|---|---|
   | 419 | `SESSION_EXPIRED` | rechargez la page — c'est l'action qui règle son problème |
   | 413 | `HOST_UPLOAD_LIMIT` | corps jeté par nginx/Apache avant PHP, page HTML, aucun code à lire |
   | 401 | `NOT_SIGNED_IN` | plus de session |
   | 403 | `NOT_PERMITTED` | ce compte n'a pas le droit |
   | 5xx | `SERVER_ERROR` | le serveur n'a pas pu terminer |

3. **Le mot de l'appelant en dernier.** `DEPOSIT_FAILED` sur l'écran d'import,
   `UPLOAD_NOT_ACCEPTABLE` sur l'écran d'upload : un vrai dernier recours, et
   plus le sort de tout ce qui n'était pas prévu.

Le ticket demandait « 401 et 403 vers un code d'autorisation ». Deux codes
plutôt qu'un : « vous n'êtes plus connecté » et « ce compte n'a pas le droit »
appellent des gestes différents, et fondre les deux aurait reproduit en petit le
défaut que ce ticket corrige.

`csrfToken()` lit la balise et **rien d'autre** : chaîne vide si elle manque.
Une requête non signée doit être refusée — le correctif est de fournir le jeton,
jamais de cesser de le vérifier, ni d'en inventer un.

### 3. Trois écrans, la même règle

- **Import** : `refusalCode(request.status, …)` sur le relais,
  `refusalFrom(response, …)` sur la frappe de capacité.
- **Upload unitaire** : idem, et `ui.upload.refusal.HOST_UPLOAD_LIMIT`
  n'existait dans aucune langue alors que son chemin relayé peut le recevoir —
  ajouté.
- **Réglages** : un test de connexion refusé n'est plus rapporté comme
  « injoignable ». Une session expirée envoyait quelqu'un vérifier des
  identifiants de stockage qui n'avaient jamais été sollicités. `ProbeReport`
  distingue désormais ce qui décrit la requête de ce qui décrit le fournisseur :
  seul `SERVER_ERROR` rejoint `FAILED` et `UNREACHABLE` en rouge.

Traductions ajoutées dans les six langues (en/fr/es/it/pt/de), aux trois
endroits : `ui.import.refusal.*`, `ui.upload.refusal.*`, `ui.settings.probe.*`.

## Le chemin direct

Inchangé, délibérément. Le `PUT` vers l'objet ne passe pas par
`refusalCode` : un 413 de R2 ne veut pas dire ce que dit
`HOST_UPLOAD_LIMIT`, dont la phrase parle de `upload_max_filesize` et de
`post_max_size`. Router cette réponse-là dans la même règle aurait donné un
message faux sur le seul chemin qui n'a pas de limite PHP. Seules les réponses
de nos propres routes sont lues ainsi.

## Les tests

| # | Ce qui est tenu | Où |
|---|---|---|
| 1 | La mise en page publie un jeton non vide, égal à celui de la session | `CsrfTokenIsAvailableTest::the_layout_publishes_a_token_the_browser_can_read` |
| 1b | Les trois écrans qui déposent le publient | `…::every_screen_that_uploads_publishes_it` |
| 2 | Dépôt relayé **avec `VerifyCsrfToken` actif** : le jeton lu dans le HTML rendu passe | `…::a_relayed_deposit_carrying_the_published_token_is_accepted` |
| 2b | Jeton vide → 419, jeton faux → 419, sur les trois routes | `…::a_relayed_deposit_carrying_an_empty_token_is_refused_with_419` et deux autres |
| 3 | 419 → `SESSION_EXPIRED`, 413 → `HOST_UPLOAD_LIMIT`, 422 codée garde son code | `deposit-refusals.spec.ts` |
| 4 | Un MP3 de 4,7 Mo est accepté quand les limites le permettent | `CatalogueImportFromTheBrowserTest::a_real_mp3_of_the_size_production_refused_deposits` (UPL-004) |
| 5 | Deux fichiers de même nom sont deux objets, et les octets des deux survivent | `…::two_files_with_the_same_name_are_two_objects_and_neither_is_lost` |
| 6 | Aucun chemin interne ni secret dans les réponses de refus | `CsrfTokenIsAvailableTest::a_refusal_names_no_path_and_no_secret` |

Le test 2 est celui qui vaut le ticket. Il lit le jeton **dans le HTML rendu**,
comme le navigateur, puis l'envoie dans l'en-tête, comme l'écran — et le
middleware réel fait la vérification réelle. `Tests\Support\Ui\EnforcesCsrfTokens`
ne fait qu'une chose : rendre `false` là où le framework court-circuite en
contexte de test. Ce qu'il ne doit jamais devenir, c'est un moyen de désactiver
la vérification là où elle s'applique.

Le test 6 s'exécute avec `app.debug` à `false`. Avec le débogage actif — le
défaut de la suite, jamais celui d'un déploiement — Laravel met la trace
complète dans le corps, et une trace est une liste de chemins absolus. La fuite
qui compte est celle de la configuration que la production exécute.

## Mutations

| Mutation | Test qui a échoué |
|---|---|
| la balise `csrf-token` retirée de `app.blade.php` | `the_layout_publishes_a_token_the_browser_can_read` (+2) |
| `csrfToken()` renvoie toujours la chaîne vide | `sends the published token and reports a 419 as an expired session` (+1) |
| la correspondance 419 retirée | 4 tests, dont celui de l'écran de réglages |
| la correspondance 413 retirée | `reports a body the web server threw away as the host limit` (+1) |
| la plage 5xx retirée | `says a server could not finish rather than blaming the file` (+1) |
| le statut lu avant le corps | `lets a code the server named beat the name the status would have got` — survivante d'abord, tuée par ce test |
| `EnforcesCsrfTokens` rendu inopérant | les trois tests de refus 419 |
| `keyFor` sans le uuid par fichier | `two_files_with_the_same_name_are_two_objects_and_neither_is_lost` |

La mutation « statut avant corps » a survécu au premier passage : aucune route
ne répond aujourd'hui à un statut correspondant avec un code différent, donc
rien d'observable n'en dépendait — c'est exactement le moment où un ordre bascule
sans bruit. La règle est désormais énoncée comme règle.

## Import massif

Vérifié dans le code, rien à changer : `concurrency: 3` signifie trois requêtes
parallèles portant **un** fichier chacune, `Import.vue` construisant un
`FormData` par fichier. `post_max_size` n'a donc à couvrir qu'un seul fichier
plus l'overhead, quelle que soit la taille du catalogue.

## Pas dans ce ticket

- **Rafraîchir le jeton après une longue session.** La balise est rendue au
  chargement de la page ; une session qui expire ensuite donne une 419, et la
  419 dit maintenant de recharger. Un jeton qui se rafraîchit tout seul est une
  requête de fond dont personne n'a encore eu besoin.
- **Le `PUT` direct vers l'objet.** Voir plus haut : un statut du magasin
  d'objets ne se lit pas avec le vocabulaire des limites de PHP.
- **Une 429.** Aucune de ces routes n'est limitée en débit ; l'ajouter au
  tableau serait une correspondance sans appelant.
