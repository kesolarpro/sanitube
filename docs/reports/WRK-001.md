# WRK-001 — one boundary, addressed by capability

GEN-008 built a remote boundary for one purpose: running ACE-Step on a host with
a GPU. The temptation immediately afterwards is a second for FFmpeg, a third for
Chromaprint, a fourth for transcription — **four authentication schemes, four
failure vocabularies, four things to deploy and four places for one bug.**

So the boundary was generalised before a second subsystem could copy it.

---

## Two routes, however many capabilities

```
GET  /api/worker                        the handshake
POST /api/worker/jobs/{capability}      the work
```

Adding a capability needs a handler and one registration. It changes neither the
protocol, the middleware, Core's client, nor the routes.

`WorkerCapability` names nine kinds of work — media probe, fingerprint, loudness,
waveform, derivative audio, transcription, music generation, stem separation,
audio understanding. **Eight have no implementation, deliberately.** A capability
named here is a word the protocol already has; it is not a promise that any
worker answers to it, and the registry reports only what is actually registered
and actually runnable.

## The handshake

Cheap enough to poll: a configuration read, the registry's own state, and tool
versions cached for an hour. No work, and no third-party call.

It reports what a worker can do **now** and what it knows how to do **at all**,
because "does not do that" and "does that but cannot right now" lead to
different afternoons. A worker whose ACE-Step is switched off still answers,
omits `MUSIC_GENERATION`, and Core stops offering generation — instead of
offering it and failing. A test pins that.

The worker's **name is configured, never derived**. A hostname changes when a
machine is rebuilt and an address changes when it moves; an audit line saying
which worker did something has to survive both. It is also what a log carries
instead of a token — never the value, never a prefix, never a fingerprint.

## Tool versions are configuration

`config/worker.tools` lists what to probe and with which flag. Knowing FFmpeg is
*present* is weaker than an operator needs: a five-year-old build and a current
one both answer yes, and only one decodes what a distributor will ask for.

A list of binary names **in the worker's code** would have been the first place
the boundary stopped being general — which is exactly what a test caught. It
also means an operator can add a tool their own capability needs without
touching PHP. Probed with `Process` and an argument array; never a shell.

## The security boundary moved next to what it protects

`rules()` is declared by the **handler**, and the generic controller applies it.
The handler receives the *validated* payload, so a field it did not declare is a
field a caller cannot set — which for generation is what keeps a request away
from a checkpoint path and a GPU. A mutation that hands the handler
`$request->all()` instead is killed.

## WHO CALLS THIS IN PRODUCTION?

```
sanitube:production:run → ProduceForProductionSlot → StartMusicGeneration
  → SubmitMusicGenerationJob → SelfHostedAceStepProvider::generate
      → WorkerClient::run(MUSIC_GENERATION)          [Core]
          → POST /api/worker/jobs/music-generation    [the boundary]
              → VerifyWorkerToken → RunWorkerJobController
                  → MusicGenerationJobHandler → RunGenerationOnWorker → ACE-Step
  → SelectMusicGenerationResult → Asset → Candidate
```

`isAvailable()` now asks the worker rather than trusting configuration, through
the cached handshake.

## Three defects the tests found

### 1. Booting cost what a handler's dependencies cost

The registry took handler *instances*, so `boot()` built the generation handler
on every request — including the overwhelming majority that are not worker
requests — and froze its dependencies while the container was still being
assembled. It surfaced as a storage manager that had read its configuration
before a test finished writing it. Handlers are now registered as factories and
built once, on demand.

### 2. The boundary imported the module it carries

`WorkerJobFailed` imported `CarriesRefusalCode` from `MusicGeneration`, and
`WorkerCapability` imported an analyser class purely for a docblock link. A
general boundary that depends on one subsystem is general only until the second
arrives. The contract moved to `Foundation`; the docblock names its subject in
prose instead.

Enforced by a test that scans `src/Worker` for namespace references to the
modules it must not know about — with comments stripped, because naming a tool
in prose to explain what a capability *means* is legitimate and importing it is
not.

### 3. A malformed worker answer was a TypeError

A proxy returning a login page, a load balancer answering with a string, a
worker mid-upgrade: each is a 200 carrying something that is not a result.
Without the check it became a `TypeError` inside a queue worker rather than a
generation that failed with a reason.

## Verification

- **20 tests, 111 assertions** in `tests/Feature/Worker/WorkerBoundaryTest.php`
- Full suite: **1968 passed, 1 skipped, 25413 assertions**
- PHPStan level 6 clean, Pint clean, vue-tsc clean, Vitest 23 passed
- `docs/deployment/worker.md` — the guide is now about the boundary, not one capability

### Mutation testing — 12 mutations, 12 killed

Killed: the raw request reaching a handler unvalidated (M1), accepting a job a
capability cannot run (M2), sharing the catalogue's token (M3), reporting a
known capability as runnable (M4), accepting an anonymous worker (M5), trusting
configuration instead of the handshake (M6), rebuilding a handler per job (M7),
dropping the handshake cache (M9), accepting a malformed answer (M10),
discarding the worker's own refusal code (M11), and carrying a client
exception's words — address and token header included — into a log (M12).

Two survivors in the first round, both real: **M6**, which is §10's "configured
but worker unavailable must not be a false green", and **M10**, above.

## What did not change

`ProbeRunner` still runs ffprobe and fpcalc locally, and that remains correct
for a capable VPS. Making execution strategy selectable — `LOCAL` or
`REMOTE_WORKER` — is the next ticket, and local stays valid.
