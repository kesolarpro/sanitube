# REL-003 — The one description of a release that crosses to a distributor

Item 15 of the Phase 2 order. Internal work, no external dependency — which is
where effort belongs while every provider-facing item waits on an account.

---

## Why it exists

`Distributor::prepareRelease()` and `submitRelease()` take a `Release` model.
So an adapter would walk the aggregate itself: tracks, credits, identifiers,
assets. Three consequences, none of them acceptable once there is more than one
adapter:

- **Every adapter reaches differently.** The same release becomes a different
  package depending on who is sending it.
- **Every adapter gets its own chance to read a revoked identifier as current.**
  ARCH-002 made that impossible in the *database*; nothing stopped a reader from
  ignoring `active_marker`.
- **"What did we actually send" is unanswerable** except by re-running whatever
  that adapter happened to do.

`ReleasePackage` is now the only thing that crosses the boundary: assembled once
from a release that has passed validation, immutable afterwards.

---

## What it carries, and what it refuses to

**Validation first, as a refusal.** Packaging an invalid release does not make
it valid — it moves the rejection from somewhere this platform controls to
somewhere it does not, after a delivery has partly happened. Only *errors*
block: a missing catalogue number is a label's business.

**Identifiers are read active-only.** A revoked ISRC or UPC is still a row, on
purpose, so the history stays readable. Reading through the `active` scope is
what stops the package being the place a revoked identifier is presented as
current.

**A missing identifier is null, never invented.** SaniTube does not mint ISRCs,
so a track may legitimately reach a distributor without one and let the
distributor assign it. The nullable field is the honest answer.

**A track without a master is an error, not an omission.** Dropping it would
deliver a release missing a track, and nobody would find out until a store
published a four-track album as three.

**A track with no ℗ line inherits the release's.** A store prints one per
recording; a track that says nothing is published with no ownership line at all.

**The contributor's *legal* name, not the display name.** A distributor passes
it to collecting societies, which match on the registered name.

**`toArray()` is hand-written, not reflected.** What leaves this platform for a
distributor should change only when somebody decides it should, and a reflective
serialiser would quietly export any property a later ticket adds. A test pins
the exact key order at both levels.

---

## Two negatives, asserted rather than asserted-about

**No location and no secret is anywhere in the structure.** Assets are named by
uuid. The test serialises the *whole* package and searches it for the cover's
and the master's path, disk, filename and checksum — naming each one and
asserting it is non-empty first, so the loop cannot quietly check fewer things
than it claims. That precaution is there because ENR-005 shipped exactly that
defect before mutation caught it.

**Nothing here holds money.** Rights *metadata* — ℗ and © lines, contributor
roles — is present because a distributor requires it to publish. A price, a
rate, a split: never. Scanned with comments stripped, because the docblocks
promise it and an earlier version of this test in ENR-003 failed on its own
explanation of itself.

## §1 — the two proofs

**A. COMPONENT PROOF.** `tests/Feature/Releases/ReleasePackagingTest.php`,
11 tests / 45 assertions.

**B. PRODUCTION-PATH PROOF.** Stated honestly: **nothing calls `PackageRelease`
in production yet, and this report does not pretend otherwise.**

That is not an oversight, it is the sequencing. The package exists so that the
DDEX document and the first distributor adapter — the next two items in the
order — have one shared thing to build from rather than each walking the
aggregate. Wiring it into `SubmitDelivery` before either exists would mean
inventing the calling convention twice.

What *is* proved is that the package is assembled from the real aggregate
through the real services: identifiers are assigned and revoked through
`AssignExternalIdentifier` and `RevokeExternalIdentifier` rather than by
inserting rows, because a hand-built row can be a shape the platform would never
produce — and then the test proves the packager handles something that cannot
happen while saying nothing about what does.

## §2 — mutation results

Seven mutations. **Three survived; one was a real test defect and two are
recorded as withdrawn.**

| # | Mutation | Verdict |
|---|---|---|
| R1 | validation ignored | killed |
| R2 | identifiers read without the `active` scope | killed |
| R3 | a track without a master is silently dropped | killed |
| R4 | the no-tracks guard removed | **withdrawn — unreachable** |
| R5 | the ℗ fallback removed | killed |
| R6 | the display name used instead of the legal name | **survived → killed** |
| R7 | the no-cover guard removed | **withdrawn — unreachable** |

### R6 — a fixture that made two different things identical

`ContributorFactory` leaves `display_name` null, so `legal_name` and any
fallback to it are the same string and the mutation swapping them survived. The
fixture now sets a *different* display name, so the assertion discriminates.

### R4 and R7 — withdrawn, with the evidence

`ValidateRelease` already refuses a release with no tracks (`TRACKS_REQUIRED`)
and one with no cover (`COVER_REQUIRED`), and validation runs first, so both
guards are unreachable through the public path.

Measured before recording it, not assumed: **PHPStan is indifferent to whether
the cover guard is present**, so "the type system requires it" is not offered as
the justification. They stay because an unreachable guard is what defence in
depth looks like while the outer layer works, and because without the cover
check a future validator change would turn a named refusal into a `TypeError`.
Reaching them would need a stubbed validator, and `ValidateRelease` is `final`
— so the alternative is not a better test, it is a worse design adopted to
satisfy a mutation. The code says all of this at the guards themselves.

## A near-miss worth recording

`StorageBoundaryTest::no_storage_vendor_is_named_in_the_domain` failed on my own
docblocks — the sentence promising the package contains "no bucket" contains the
word. **The second time this session a comment has failed its own promise**, the
first being `nothing_here_holds_money`.

The tempting fix was to make the guardrail strip comments, as the money test
does. I reworded the prose instead. Weakening a security guardrail so that a
sentence about it can be phrased more neatly is the wrong trade, and the
guardrail is at full strength.

## What this ticket did not do

- **No DDEX.** The package is the input to it, not a substitute.
- **No adapter change.** `Distributor` still takes a `Release`; changing the
  contract belongs with the first real adapter that needs it.
- **No manifest written to storage.** `toArray()` produces the structure; where
  it is persisted is a distributor's requirement and nobody has one yet.
