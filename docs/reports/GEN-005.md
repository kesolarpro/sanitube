# GEN-005 — Suno research

**Research only. No adapter was built, and the finding is that one cannot be.**

Deliverables: `docs/research/suno-2026-08.md` (the record),
`docs/adr/ADR-0018-no-adapter-without-a-published-contract.md` (the decision),
and `tests/Feature/MusicGeneration/ProviderProvenanceTest.php` (the enforcement).

---

## The finding

As of August 2026 Suno has **no public, self-serve API** — no developer console,
no documentation site, no published request or response shapes, no stated rate
limits, no pricing. In July 2026 Suno's Chief Product Officer said a developer
API is being *explored*, starting with a curated group of partners recruited
through an intake form. No timeline.

So §5's rule — use only official API contracts, do not guess model names,
formats, limits or response fields — has nothing to be applied to. There is no
contract to write an adapter against.

Every commercial search result for "Suno API" is a third party reverse
engineering Suno's web client and reselling access. The standing constraint
forbids those, and ADR-0018 records **why** it is right rather than treating it
as a rule to be obeyed without understanding: such a wrapper works by holding a
Suno account's session credentials, and that account is what holds the
commercial rights to everything made through it.

## What the research is actually for

The useful half was not "does an API exist" — the answer to that was
predictable. It was the commercial and legal picture, because SaniTube's job is
to assert rights to a distributor:

- Rights attach **at the moment of creation**, to a paid subscriber, and persist
  after cancellation. Free-tier output is non-commercial and subscribing later
  does **not** grant rights retroactively.
- Fully AI-generated music likely **cannot be registered for copyright** under
  current US law. The protection is contractual, not copyright.
- **No indemnity** is reported: an infringement claim is the user's to defend.
- Pro downloads are **capped monthly**, tightened during 2026 under the Warner
  agreement.
- Warner settled and licensed in November 2025. **UMG's suit against Suno is
  ongoing and Sony has settled with neither.**

Three consequences are written into the research document, and one of them is
new work nobody had identified: **a download cap is an operational bound that
GEN-004 does not cover.** GEN-004 ceilings count *requests*. If a provider
separately caps how many results may be **retrieved**, a production plan can
succeed at generating and still fail at collecting. That is a distinct limit,
and it is now written down before it can surprise anyone.

## The evidence caveat, stated in the document itself

This session's egress allows web search but **blocks direct fetches** of
`suno.com`, `help.suno.com`, `musicbusinessworldwide.com` and Wikipedia. So no
primary source was read. Everything above rests on search-engine summaries of
those pages.

The research document opens with that limitation rather than burying it, and
says plainly that every commercial claim must be re-verified against Suno's
actual terms before a single track is distributed. A rights claim sourced from a
search summary is exactly the sort of thing that looks authoritative in a
document and is wrong at the distributor.

## §1 — the two proofs

This ticket has no production path, because it adds no production behaviour —
which is precisely the sort of ticket where "the docs say so" quietly replaces
"the code does so".

**A. COMPONENT PROOF.** `ProviderProvenanceTest`, 4 tests / 5968 assertions:

- no reverse-engineered provider endpoint appears anywhere in `src/` or
  `config/`, scanned with comments stripped so that documents and docblocks may
  name them freely — explaining an exclusion requires naming the thing excluded
- no dependency wraps a generation provider
- the platform **ships** with `default => none` and exactly two configured
  providers
- `src/MusicGeneration/Providers/` contains exactly the three adapters this
  repository wrote

**B. ENFORCEMENT PROOF.** A rule in a document is not a rule. The point of the
fourth test is that adding a real adapter becomes a deliberate act that must
update an explicit list — at which moment ADR-0018's four conditions are the
question being answered — rather than something that slips in because nobody
re-read `docs/adr`.

## §2 — mutation results

Five mutations. **Two survived, and both were defects in what I had just
written.**

| # | Mutation | Verdict |
|---|---|---|
| P1 | a forbidden endpoint added to a module-root file | **survived → killed** |
| P2 | a forbidden name added to a nested file | killed (first attempt invalid) |
| P3 | shipped default changed from `none` to `fake` | **survived → killed** |
| P4 | a `suno` provider added to the shipped config | killed |
| P5 | the env-clearing step removed from the test helper | withdrawn |

### P1 — the scan had a hole and reported a pass

The first version globbed `src/*/**/*.php`. That looks exhaustive and is not:
PHP's `**` is an ordinary `*`, so the pattern matched files at exactly one depth
and silently skipped module roots — including
`src/MusicGeneration/ProviderFailure.php`, the file GEN-003 had just added.

**It scanned 368 of this repository's 634 source files and passed.** Replaced
with a recursive directory walk, which took the assertion count from 3574 to
5968, and the count is now asserted (`> 400`) rather than merely non-empty —
because "some files" is what a broken pattern also returns.

### P3 — the test was reporting on the environment, not the code

`the_platform_ships_with_no_generation_provider_at_all` required
`config/generation.php` and asserted the default was `none`. It passed with the
default mutated to `fake`.

The reason: this machine's `.env` and the shipped `.env.example` both set
`SANITUBE_GENERATION_PROVIDER=none`, so `env()` never reached its fallback. The
assertion held on every environment regardless of what the code said. **It could
never have failed.**

Fixed by removing the variable from `$_ENV`, `$_SERVER` and the process
environment before reading the file, and restoring it in a `finally` — otherwise
every later test in the process would run against an environment this one
quietly emptied. P3 is killed with the clearing in place, which is also what
proves the clearing is load-bearing.

### Recorded honestly rather than quietly fixed

- **P2's first run was an invalid mutation of mine**, not a surviving one: I put
  the forbidden string in a `//` comment, which the test strips *by design*.
  Re-run with the string in real code, it was killed. A mutation that does not
  represent the threat is not evidence about the test.
- **P5 is withdrawn.** It mutates the test helper rather than the
  implementation, which is outside §2's discipline — §2 breaks the
  implementation and watches the test fail. The clause it targets is already
  proven load-bearing by P3.

## What this ticket did not do

- **No adapter, and none is recommended.** ADR-0018 states the four conditions
  that would unblock one. None currently holds.
- **No partner-programme application.** That is a commercial decision for a
  human, not something to submit autonomously on somebody's behalf.
- **Nothing was verified against a primary source.** See the evidence caveat.
- **The download-cap bound is identified, not built.** It needs its own ticket
  and cannot be designed until a real provider states its cap.
