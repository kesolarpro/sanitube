## Scope, and why it stops where it does

This ticket is the hinge the project's own vision identifies: do not let twenty
screens be built before a coherent design system exists, because whatever the
first screen establishes becomes the convention the other nineteen copy —
correct or not.

So UI-001 delivers the foundation and **one** showcase screen, and deliberately
**no business screen**. No Catalog, no Releases, no Distribution, no Studio, no
Royalties. Those wait for this to be reviewed.

## What is here

**Stack.** Vue 3, TypeScript (strict, with `noUncheckedIndexedAccess`),
Inertia 2, Tailwind 4, Vite 7. `vue-tsc` runs in CI as its own step, so a type
error fails the build rather than being noticed later.

**Tokens.** Colour, typography, radius, elevation, z-index and motion, all
semantic — `--color-surface`, never `--color-zinc-900`. Light and dark, plus
follow-the-system. The full reasoning is in `docs/adr/ADR-0013`.

**Primitives.** Button, Card, MetricCard, StatusBadge, Alert, Modal,
ConfirmDialog, Skeleton, ProgressBar, EmptyState, ErrorState, CodeValue,
FormField, TextInput, TextareaInput, SelectInput, ToggleInput, DataTable with
header/cell, CursorPagination, NavIcon, Sidebar, and the AppLayout shell.

**Shell.** Fixed sidebar on desktop, drawer below `lg`, sticky top bar, skip
link, theme switcher, flash messages. Navigation built on the server.

**One screen.** `/design-system` — every primitive in both themes.

## Decisions worth challenging

Ten are set out in `docs/adr/ADR-0013-design-system-foundations.md`. The four
most consequential:

**Semantic tokens rather than a colour scale**, so dark mode is a redefinition
of names rather than a second set of classes through every template.

**Status colour is decided in exactly one component.** Every module has its own
status enum; without one place deciding what "in progress" looks like, the same
idea ends up amber on one screen and blue on another. The *label* always comes
from the translations — showing `WAITING_CAPABILITY` to a user is showing them
the database.

**Navigation is built on the server, and unbuilt sections are shown as
disabled** rather than hidden. A navigation that grows as features land is
disorienting. `available` is presentation only and never the authorisation.

**Null renders as an em dash, never zero.** `MetricCard` takes `number | null`.
"No failed jobs" and "we could not count the failed jobs" are different facts,
and showing `0` for both hides an outage.

## No invented data — enforced, not promised

The showcase queries nothing. Its metric cards pass `null`, so they render em
dashes, and the page carries a visible notice saying the placeholders are
placeholders. A showcase displaying "1,284 tracks" would be exactly the
fabricated figure the platform's rules forbid, and it would be screenshotted.

## Everything is behind SEC-001

`/design-system` sits in a route group carrying `auth` and `active`. Two tests
assert it: a guest is redirected to sign-in, and an account deactivated
mid-session loses access at the *next request* rather than when its remember-me
cookie expires.

`/` now redirects — guests to sign-in, signed-in people to the interface.
SaniTube has no public face.

## Nothing secret reaches the browser

The internal API token, storage keys and provider keys stay on the server. A
test puts a realistic token and an OpenAI-shaped key into config, renders a
page, and asserts neither appears anywhere in the response — then walks every
shared prop key against a list of credential names.

The first version of that key list contained a bare `key`, which matched the
navigation items' own `key` field. Narrowed to unambiguous names: this is the
same false positive ING-001 hit with `path`, and a check that cries wolf is one
people start deleting.

## Accessibility

`:focus-visible` rather than `:focus`. Dialogs move focus in, trap it and
return it. Real `<table>` semantics. `role` chosen by severity so only danger
and warning interrupt a screen reader. `prefers-reduced-motion` honoured. Skip
link. Toggle is a `role="switch"`, not a styled checkbox.

## The dependency constraint, recorded

`@vitejs/plugin-vue@5` declares a peer range of Vite `^5 || ^6`; the project is
on Vite 7, and npm refused.

**Resolved by using `@vitejs/plugin-vue@6`, which supports Vite 7 — not by
`--force` or `--legacy-peer-deps`.** Forcing would have installed a plugin
against a Vite major it was never tested on, and that failure mode is a build
that works until it silently does not. A peer conflict is information about
compatibility; overriding it discards the information and keeps the
incompatibility. Same for `vue-tsc@3`.

This will recur — the frontend toolchain moves faster than the peer ranges
declared against it. Recorded in the ADR.

## Translations

All new strings ship in en, fr, es, it, pt and de. The completeness gate
generalised in SEC-001 now covers `ui.php` automatically, in both directions.

Shared from the server as a **flat map with dotted keys**, so `trans('ui.actions.save')`
is one lookup rather than a walk down an object. A missing key returns the key
itself: blank text looks like a layout bug and gets ignored.

## Architecture amendment

**None.** No migration, no column, no relation, no invariant. One new module
(`Ui`), one route, the frontend toolchain, and a `Type-check` step added to the
existing frontend CI job.

## Deferred, and named

The mission's component list also names Breadcrumbs, Tabs, Dropdown, Popover,
Tooltip, Toast, Radio, Checkbox, SearchInput, CoverImage, TrackIdentity,
ArtistIdentity and AudioPlayerShell. They are **not** in this PR.

Each is shaped by the screen that first needs it — a Toast queue's behaviour
depends on what raises toasts, and `TrackIdentity` depends on what a track row
must show. Building them now against a guess is how a component library
acquires a dozen unused variants. They arrive with UI-002 onwards, on the token
system this ticket establishes.
