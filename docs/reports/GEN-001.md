# GEN-001 — Music Generation Foundation

**Status:** delivered
**Base:** `ee050fa` (main, after CAT-001)
**Branch:** `claude/gen-001-music-generation`

---

## What this ticket is actually about

Two negatives hold the whole design up.

**It must never require a provider.** No music generation API is wired to this
platform — Suno is the first intended adapter and there are no credentials —
and the Studio has to be buildable, demonstrable and testable anyway. The
default provider is `none`, and `fake` is shipped rather than test-only so the
entire workflow can be run end to end on an installation with no account.

**It must never produce a Track.** Generated audio is precisely the material
that most needs a person to listen before it enters the catalogue: it was
produced by a machine from a sentence. So it joins the *same* review queue as
an imported file and CAT-001 promotes it or does not. A campaign that runs
overnight cannot write into the source of truth.

```
GenerationProject → MusicGeneration → provider job
                                    → MusicGenerationResult (N takes)
                                    → selected → Asset → VERIFIED
                                    → TrackCandidate (source GENERATED)
                                    → CAT-001 review
```

## Four tables

| Table | Holds |
| --- | --- |
| `generation_projects` | a campaign, and the defaults it states once |
| `music_generations` | one request to a provider |
| `music_generation_results` | one audio variant; a request routinely returns several |
| `provider_terms_snapshots` | what a provider's terms said, on the day |

`parameters` and `raw` are `longText` with an array cast, never `json` — the
rule ING-001 established, because MariaDB aliases `json` to
`longtext/utf8mb4_bin` while MySQL 8 uses a native binary type.

## Commercial provenance is never inferred

`commercial_rights_status` defaults to `UNKNOWN` and **nothing in SaniTube ever
sets it from the fact that a generation succeeded.** A generation existing says
nothing about whether it may be sold: that depends on the provider's terms, the
plan the account held when the audio was made, and frequently on a human
reading a licence. Only `ALLOWED` clears a recording for distribution — unknown
is the absence of an answer, not permission.

`ProviderTermsSnapshot` exists because terms change and the recording made in
March is still in the catalogue in November. Every column is entered by a
person who read the licence, and `source_reference` is where they read it.
**Nothing is scraped and no provider condition is invented.**

`commercial_use_allowed` is nullable *and* boolean, deliberately: null means
nobody established it, false means somebody read the terms and they say no.
Collapsing those loses the difference between "unchecked" and "not permitted".

## The contract, finalised small

```php
createGeneration()  getGenerationStatus()  fetchResults()  cancelGeneration()
```

ARCH-001 left this provisional pending a real provider's semantics. GEN-001
finalises it at four methods and **deliberately excludes `extend`, `remix` and
`stems`**: no provider supports all three, they mean measurably different
things where they exist, and a base contract demanding them forces every
adapter to write refusals for capabilities it never had — which is how an
interface stops describing anything. They arrive as capability interfaces
(`SupportsExtend`, `SupportsStems`, declared and unimplemented) that a caller
tests for.

`getGenerationStatus()` and `fetchResults()` are split because status is cheap
and polled often while results are the payload. Providers bill and rate-limit
them differently, and returning both together makes a status poll expensive.

## Idempotency, three ways

**One provider job, one generation.** `UNIQUE (provider, provider_job_id)`,
with `provider_job_id` null until the provider answers — NULLs stay distinct
inside a unique index on every engine, so unlimited unsubmitted drafts coexist.
The same trick ARCH-002 uses for one active identifier per track and ING-001
for one in-flight item per key.

**One take, one row.** Results are written with `updateOrCreate` on
`(generation, provider_result_id)`. Polling re-fetches the whole list on every
pass, and a plain insert would multiply the takes by the number of polls.

**One selection, one asset.** The result carries `asset_id` and `candidate_id`
once imported; re-selecting returns them. The asset id is written *before* any
bytes move — ING-001's ordering — so a crash mid-download leaves a retry with
one address to overwrite rather than an orphaned object. A test kills the audio
reader mid-import, recovers it, retries, and asserts one asset.

## Polling is bounded twice

A job that dispatches itself is one provider outage away from running for ever.

1. `PollMusicGenerationJob` re-dispatches **only** while the generation is
   still pollable.
2. `PollMusicGeneration` fails the generation once `max_polls` is reached,
   which terminates the loop from the other side.

Two independent bounds, because a self-dispatching job with one bound is one
bug away from none. A row left permanently `QUEUED` is a row nobody cleans up.

A transient outage does **not** fail the generation — the next poll may
succeed, and the poll bound is what limits the retrying.

## Selecting does not delete

A request routinely returns several takes and the platform keeps all of them.
`selected` is a flag, not a delete. A reviewer who changes their mind an hour
later must still be able to hear take two, and these are the only copies. Two
takes may both be selected — they are two recordings, and a label may want
both.

## Two vocabularies, on purpose

`GenerationStatus` is what a *provider* reported. `MusicGenerationStatus` is
what the platform believes about the row. They are separate enums because
`DRAFT` has no provider counterpart at all — it is a generation somebody
composed and has not submitted — and a single enum would have had to invent a
provider state for it.

## A completed job with no audio is a failure

Rare, real, and the case that would otherwise put a silent recording in the
review queue. `fetchResults()` returning nothing on a completed job fails the
generation with a stated reason rather than recording a success with no takes.

## The disabled provider is `none`

Same rule and same wording as AI-001, so an operator does not have to learn two
conventions: Laravel reads the literal string `null` in a `.env` file as PHP
null, so `null` as a configuration value means "no value" rather than "the
provider named null". Empty, absent, blank and `"null"` all normalise to
`none`; an unknown non-empty name such as `sunoo` is an error, because somebody
who typed it intended a provider.

## API

```
POST /api/v1/generation/projects          → 201
GET  /api/v1/generation/projects
GET  /api/v1/generation/projects/{uuid}
POST /api/v1/generations                  → 202, work is queued
GET  /api/v1/generations/{uuid}
POST /api/v1/generations/{uuid}/cancel
GET  /api/v1/generations/{uuid}/results
POST /api/v1/generation/results/{uuid}/select
```

**Nothing published carries `provider_job_id` or `source_reference`.** The job
identifier is a handle on a billed vendor job; the source reference streams the
audio without going anywhere near SaniTube's signed-URL policy. `provider` *is*
published — a label needs to know which supplier made a recording, and that is
provenance rather than a credential. A test walks every key of every response
recursively.

Selection flags the take immediately so the Studio reflects the choice, and
queues the download: a rendered master will not survive an HTTP request.

## Architecture amendment

**None to a validated ticket's schema.** Four new tables; nothing existing is
altered.

One declared change to an ARCH-001 *interface*: `MusicGenerationProvider` was
explicitly marked provisional in its own docblock — *"It will gain … in
GEN-001, once a real provider's semantics are known"* — and this is that
finalisation. `generate`/`status`/`cancel` became
`createGeneration`/`getGenerationStatus`/`cancelGeneration`, and `fetchResults`
was added. The only implementations are the fake and the new unavailable
provider, both updated, plus the ARCH-001 unit test. No persisted data, no
column, no invariant is affected.

## Deliberately out of scope

- **No Suno adapter.** Credentials do not exist. Writing one against a guessed
  request body would bake an invented API into the platform.
- **No webhook endpoint.** Polling is bounded and sufficient; a webhook needs a
  publicly reachable URL, which a cPanel install may not have.
- **No cost tracking.** Generation providers bill per credit with per-plan
  rates that change; a stale table is worse than none.
