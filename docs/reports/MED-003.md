# MED-003 — what each asset sounds like, as evidence

## Where this sits

Phase 3 is deduplication. It cannot be built on top of nothing: telling that
`master.wav` and `master-320.mp3` are the same recording needs an acoustic
fingerprint, and a fingerprint is worth nothing unless it is stored in a form
that can be *re-read* later.

This ticket produces the evidence. It decides nothing.

## Two things deliberately not stored

**Not a score.** A similarity percentage is a decision made with today's
threshold, and thresholds get recalibrated once real data arrives. Storing the
fingerprint means a hundred thousand comparisons can be re-decided without
re-reading a single master — and re-reading fifty thousand masters to change one
number is the sort of thing nobody actually does, so the number never gets
changed and the wrong threshold becomes permanent.

**Not a verdict.** Nothing here declares a duplicate, merges anything or trashes
anything. `FindFingerprintCandidates` answers one question — what is even worth
comparing — and the comparison, the threshold and the human review all live
elsewhere.

## The constraint that shaped the schema

Comparing every fingerprint against every other is O(n²). At the 50,000 assets
this platform must support, that is **1.25 billion pairs**. It is not a slow
query; it is the wrong shape of query, and no index makes it right.

The way out is that **two recordings of different lengths are not the same
recording.** So `duration_seconds` is stored on the fingerprint row, indexed
together with the algorithm, and narrows 50,000 rows to a handful before a
single fingerprint is looked at.

The tolerance is **proportional, not fixed**: two seconds is nothing across a
nine-minute recording and a great deal across a fifteen-second one. A fixed
window would either miss re-encodes of long tracks or drag every jingle in the
library into every comparison.

`fingerprint_hash` is an indexed fast path for byte-identical fingerprints — the
same decode of the same audio. It is explicitly **not** an identity: two files
differing by one sample hash differently and are still the same recording, which
is exactly why the raw fingerprint is kept beside it.

## A capability, not a dependency

Chromaprint is absent on essentially every shared cPanel account, and that is
the ordinary case rather than a broken one. An installation without it stores,
analyses and promotes exactly as before; it simply cannot compare acoustically.

Same shape as the existing FFmpeg decision: `UnavailableAudioFingerprinter`
says so, the provider binds by capability, and a missing tool produces no row
and no exception.

`algorithm` and `tool_version` travel on every row because fingerprints from
different algorithm versions are not reliably comparable. Comparing them anyway
produces confident nonsense, and the candidate query refuses to.

## Safety

The tool is invoked through the existing `ProbeRunner` — an **argument array**,
never a shell string. A filename is caller-controlled, and `fpcalc "$path"` is a
command injection waiting for the first file called `; rm -rf`.

`-length` bounds the decode to the opening of the track: fingerprinting four
thousand full masters end to end is minutes of CPU each, and the opening
identifies a recording as well as the whole of it — the tail is where fades and
silence live, the least distinctive part. The value is clamped, so a configured
zero cannot fingerprint nothing and a configured hour cannot make the nightly
pass never finish.

The object is streamed to a temporary file and removed in a `finally`, including
when the tool fails. Over four thousand files, the missing `finally` is what
fills a shared account's disk quota.

## A finding

The portability scanner refused the migration — because a **comment** in it
named the forbidden JSON column builder. The scan is textual by design, and the
ING-001 migration already carries a note saying so. Reworded rather than
exempted: the guard is right, and a scan that can be talked out of its rule is
not a guard.

## A second finding — caught by the engine matrix, not by SQLite

The candidate query ordered by the obvious expression:

```sql
ORDER BY ABS(duration_seconds - 300)
```

It passed every local run and every SQLite job, and failed **MySQL 8.0, MariaDB
10.6 and MariaDB 11.4 identically**:

```
SQLSTATE[22003]: Numeric value out of range: 1690
BIGINT UNSIGNED value is out of range in '(`audio_fingerprints`.`duration_seconds` - ?)'
```

`duration_seconds` is an **unsigned** column. MySQL and MariaDB evaluate
unsigned minus unsigned as unsigned, so the first candidate *shorter* than the
target underflows and the engine aborts the whole query — `ABS` never runs.
SQLite has no unsigned arithmetic and quietly returns a negative number, so the
same code is correct there and fatal everywhere else.

Exactly one test failed, which is the part worth keeping in front of whoever
reads this: every other candidate query in the suite happened to compare
against rows at or above the target. The bug was not rare, the *coverage* was
one-sided.

The fix is a CASE that always subtracts the smaller value from the larger, so
the result is non-negative on every engine and no cast is needed:

```sql
ORDER BY CASE WHEN duration_seconds >= ? THEN duration_seconds - ?
              ELSE ? - duration_seconds END, id ASC
```

Two things came with it:

- **A deterministic tiebreak.** Two candidates equidistant from the target — 199
  and 201 against 200 — were previously ordered by whatever the engine returned,
  which decided which one survived the cap. Truncation must not be a coin toss.
- **A clamped lower bound**, so `whereBetween` never compares a negative number
  against an unsigned column.

`a_candidate_shorter_than_the_target_is_ordered_rather_than_aborting_the_query`
pins the shape with candidates on **both sides** of the target. It is red on
MySQL and MariaDB before the fix for the reason it names, and its ordering
assertion is load-bearing on SQLite too: replacing the distance ordering with
`orderBy('duration_seconds')` returns `[295, 298, 303]` instead of
`[298, 303, 295]`.

The first instinct was that MySQL returns column values as strings where SQLite
returns integers, and a model cast was written on that theory. It was reverted
before it was committed: the theory was never tested, the real log said
something else entirely, and a cast justified by an unverified claim about an
engine is a comment that will mislead the next person. **The CI matrix exists so
that this class of difference is found by an engine rather than by a guess.**

## Not in this ticket

- **Comparison and scoring.** `FindFingerprintCandidates` narrows the set;
  deciding `SAME_RECORDING` from a fingerprint distance is Phase 3.
- **Cover/remix detection.** Deliberately absent — it is a research problem, and
  on a single-artist single-style catalogue it would produce mostly false
  positives.
- **The remote worker.** The contract is shaped so a worker can implement it,
  but running Chromaprint off the cPanel host is its own ticket.
