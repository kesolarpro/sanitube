# UI-004 — The ingestion screens

## What this delivers

Four screens, all read-only:

| Screen | What it answers |
| --- | --- |
| `/ingestion/batches` | Which imports have run, and what became of their files |
| `/ingestion/batches/{uuid}` | Every file in one import, and why any of them stopped |
| `/ingestion/candidates` | What is waiting for somebody to decide about it |
| `/ingestion/candidates/{uuid}` | Everything needed to decide about one file |

Plus the read models behind them, filter validation, cursor pagination, six
locales, and the navigation entries that make them reachable.

**Nothing here writes.** Starting an import is `sanitube:import` (BULK-001b);
promoting and rejecting a candidate are catalogue writes and are a separate
ticket. A read-only surface first is deliberate: the review actions are worth
designing against a screen somebody has actually looked at.

## The candidate screen is the ticket

Everything else is a list. The candidate detail is where a person decides
whether a file belongs in the catalogue, and it is built around keeping **four
kinds of evidence visibly apart**:

1. **What the file is** — the measurements MED-001 took. Facts.
2. **What the manifest claimed** — the operator's spreadsheet row. Assertions.
3. **What the platform noticed** — duplicate bytes, an ISRC already in use.
   Findings.
4. **The decision** — what a person already concluded, if anything.

Merging the manifest's title into the same block as the analyser's duration
would invite a reviewer to accord them the same confidence, and they have
earned very different amounts. The read model names the manifest block
`claimed` for the same reason: it is the last chance to say, before a template
renders it, that nobody has established any of this.

`suggested_title` keeps its name from the database all the way into the
column heading. A column headed "Title", beside the catalogue's own lists,
gets read as a catalogue title — and nothing on these screens is in the
catalogue.

Where the suggestion came from is shown beside it. "The operator typed it" and
"we parsed it out of `01 - track.wav`" deserve different amounts of trust, and
a screen that does not say which it has gets both wrong.

## What must not leak, and does not

| Withheld | Why |
| --- | --- |
| `ingestion_items.source_reference` | an object key in somebody's storage |
| `assets.path` / `disk` / bucket | the same rule the catalogue screens follow |
| `ingestion_items.failure_message` | quotes the storage driver, which quotes a path |
| `audio_analyses.failure_message` | quotes the analyser, which quotes a path |
| `audio_analyses.raw` | the analyser's whole output |
| any signed URL | a bearer credential is never minted by a page load |

What *is* shown is `original_filename` — the basename, which the operator
already knows and without which a failure report is useless — and
`failure_code`, translated into a sentence a person can act on. The precedent
is `TrackCandidateResource`, which draws the same line.

One test asserts all of it at once, against a rendered page with a deliberately
incriminating reference (`private-bucket/secret-prefix/track.wav`) and a
deliberately incriminating driver message.

## Counts

**Every state gets a tile, including the ones at zero.** A bucket that
disappears when empty makes "no failures" and "the failed count is not being
shown" look identical, and those call for opposite reactions from somebody
watching nine hundred files import.

**Counts for a whole page come from one grouped query.** `IngestionBatch` has
an `itemCounts()` that is correct and cheap for one batch; calling it per row
would be fifty queries for a page of fifty. That is invisible in development,
where nobody has fifty batches, and is the first thing to hurt on the machine
that actually ran the nine-hundred-file import. A test counts the queries.

A status the enum no longer declares is counted into the total rather than
dropped. An item that exists is an item, and a total that silently excludes it
is a total nobody can reconcile against the item list.

**No percentage and no estimated finish time**, on any screen — inherited from
BULK-001a and re-stated here because a progress screen is exactly where
somebody would add one. Item durations vary by orders of magnitude between a
three-minute MP3 and an hour-long WAV, and a progress bar that stalls at 94%
teaches people to ignore progress bars. A batch still running shows "still
running", not a guessed finish time.

## Filters and cursors

A filter the platform does not understand is refused with 422 rather than
ignored. Silently dropping it shows an unfiltered list under a filtered
heading, and somebody reading "no failed batches" would be reading a list that
was never asked the question.

Every list validates that a cursor describes *its own* ordering, via the shared
`CursorShape`. A cursor copied from another screen decodes cleanly, reaches the
paginator and surfaces as a 500 about an unexpected value; it is a mangled URL,
and answering it with a server error hides that. This now applies to the item
list inside a batch as well, which is why `IngestionBatchDetailRequest` exists
despite taking no filters.

The review queue's `awaiting_review` filter includes `READY` alongside
`NEEDS_REVIEW` and `DUPLICATE`. A candidate the platform has finished with is
still waiting for somebody to decide about it — "awaiting review" is about the
decision, not about the platform having finished its part.

Ordering is `(created_at, uuid)` on both lists, and nothing is promoted to the
top by urgency. A queue that reorders itself means a row's position says
something different on every load, and a reviewer working through nine hundred
files needs the list to stay where they left it.

## Guardrails proven

Six regressions injected; **every one turned a test red** before the
implementation was trusted:

| Injected regression | Caught by |
| --- | --- |
| empty buckets vanish instead of reading as a real zero | 2 tests |
| counts computed per row (the N+1) | counting a page costs one query not one per batch |
| the object key reaches the item list | no object key disk or bucket reaches any ingestion screen |
| the driver's failure message reaches the item list | the same test |
| the analyser's failure message reaches the reviewer | an analyser failure message never reaches the reviewer |
| the manifest's reference echoed back to the browser | the manifest is presented as a claim |

## Accessibility and localisation

Built from the UI-001 primitives, so the table semantics, focus handling and
contrast come from components already reviewed. Every string is a translation
key in `en/fr/es/it/pt/de`; the completeness gate passes both directions.
Three generic status labels the ingestion states needed — `IMPORTED`,
`SKIPPED`, `COMPLETED_WITH_ERRORS` — were added to the shared status map rather
than being written into a template.

## Tests

17 new tests. **783 PHP tests / 3248 assertions**, 1 skipped (the real ffprobe
run), plus 16 component tests. PHPStan level 6 clean, no baseline. Pint clean.
vue-tsc clean. Frontend build clean.

## GAP recorded, not filled

The domain supports promoting, rejecting and revising a candidate
(`PromoteTrackCandidate`, `RejectTrackCandidate`, `ReviseTrackCandidate`, all
merged in CAT-001), and none of those actions appears on these screens. That is
scope, not an oversight: they are catalogue writes, they need a confirmation
surface and an override-reason flow, and they belong in a ticket that can give
them the attention a write deserves. Recorded as **UI-004b**.

## Architecture amendment

**None.** No migration, no new table, no invariant touched, no existing
behaviour changed. Four read models that only read, four controllers, three
form requests, four pages.

## Review

Not `REVIEW_REQUIRED` under the standing policy: read-only UI over already
approved domain services, no authorization semantics, no destructive behaviour,
no external action, and no write of any kind.
