# EDI-001 — how one imprint wants its catalogue to sound and read

## A label is data

**The whole ticket is one boundary.** Everything specific to an imprint — its
language, its palette of genres, the words it does not use, how a title should
read — lives in a row. A second imprint on the same installation is a second
row, not a fork.

That boundary erodes the first time somebody writes "our label always releases
in French" into a service, and it erodes *invisibly*: the code still works, for
exactly one installation. So the check is mechanical.
`no_imprint_is_named_in_the_source` walks every PHP, Vue and TypeScript file
under `src`, `app`, `config` and `lang`, and fails if a real imprint name
appears in any of them. A mutation that drops the name into a docblock dies
against it.

## Not an artist, and not part of one

An `Artist` is a **public credit** — the name printed on a release. This is
**editorial policy**. They are different tables because:

- one artist can be released under several profiles, and
- one profile can credit several artists.

Folding these columns onto the artist row would make both impossible, and would
put editorial policy in a table that distribution reads as identity.
`one_artist_may_be_released_under_more_than_one_profile` is the test that pins
it, and `a_profile_is_not_an_artist_and_the_artist_row_is_untouched` asserts
that creating a profile writes nothing to the artist at all.

It is not a `Contributor` either. A contributor is a person or company with
rights; nothing here has rights.

`default_artist_id` is nullable and is a **preference**. A profile with no
default artist is an imprint that decides the credit per release, which is an
ordinary way to run one.

## Preferences, never constraints

Nothing here refuses anything. An editor who wants a track outside the palette
makes one; the profile is what a suggestion, a plan or a proposal *starts from*,
not what any of them are limited to.

`a_profile_constrains_nothing` asserts it by absence — no method on the model
may be named for refusing, enforcing or validating. That is a blunt test and a
deliberate one: this is the class somebody will eventually be tempted to give a
`refusesGenre()` to, and the moment it has one, an imprint's taste has become a
rule the catalogue enforces.

## The guidance block

Assembled on the model, in one place, so a second caller cannot assemble it
differently and produce quietly different suggestions from the same profile.

Two details earned their tests:

**Nothing means nothing.** A profile that says nothing produces `null`, not an
empty block. An empty guidance block is worse than none — it fills a prompt with
headings and no content, and a model reading `Preferred genres:` with nothing
after it will invent some.

**Avoided terms are phrased as a prohibition**, not as a negative preference. A
model handed "avoid: X" in the same list as "prefer: Y" treats both as
suggestions of equal weight.

Blank terms are stripped in **two** places — by the writer before they are
stored, and by the model when guidance is assembled — and each is tested where
it acts. The model's filter is not redundant: `guidance()` runs over whatever is
in the row, including rows a seeder, a migration or a future importer wrote. A
mutation removing it dies against a test that writes the row *around* the
service, deliberately.

## The slug is frozen

Derived once from the name and never again. It is how a production plan and a
console command will name a profile, and a slug that followed a rename would
silently repoint every reference — turning "rename this imprint" into "orphan
everything that mentioned it".

A name in a script `Str::slug` cannot transliterate produces an empty slug, and
an empty unique column is a collision waiting for the second such imprint. It
falls back to a uuid prefix, which is ugly and correct.

## Mutation record

Fourteen mutations, all killed.

| # | Mutation | Killed by |
|---|---|---|
| K1 | slug follows a rename | `renaming_an_imprint_does_not_repoint_what_referred_to_it` |
| K2 | slug collision allowed | `two_profiles_cannot_share_a_slug` |
| K3 | empty slug allowed | `a_name_in_a_script_that_does_not_transliterate…` |
| K4 | name not required | `a_profile_needs_a_name` |
| K5 | language not validated | `a_default_language_must_be_a_code` |
| K6 | terms not deduplicated | `terms_are_deduplicated_case_insensitively` |
| K7 | writable list opened up | `a_payload_cannot_set_what_it_was_not_offered` |
| K8 | empty guidance returned | `a_profile_that_says_nothing_produces_no_guidance_at_all` |
| K9 | the model lets blanks become headings | `blank_terms_do_not_become_headings` |
| K9b | the writer stores blank terms | `the_writer_strips_blanks_before_they_are_ever_stored` |
| K10 | avoided terms phrased as a preference | `the_guidance_block_is_assembled_in_one_place` |
| K11 | an imprint named in a service | `no_imprint_is_named_in_the_source` |
| K12 | fields validated after the row is created | `a_default_language_must_be_a_code` |

**K12 is a bug I wrote during this ticket and the tests caught immediately.**
Refactoring `create()` to satisfy static analysis moved the row's creation
*before* the fields were read — so a refused language left a half-made profile
behind: a named imprint with none of the policy that was the reason for creating
it, sitting in a unique slug so the corrected attempt could not succeed either.
The existing assertion that nothing is stored on a refusal failed on the next
run, and the mutation now pins the ordering.

**K9 survived its first pass** and the resolution was to split the test rather
than adjust it. Two filters exist; a test that went through the writer proved
only the writer. Each is now tested where it acts.

Two assertion bugs of my own were also found and fixed while writing this:
comparing a freshly-created model's attribute array against a re-fetched one
(they differ in key order and in how the driver returns booleans, so the test
reported a change nothing made), and `assertSame` on two `Carbon` instances for
the same moment.

## Who calls this in production?

**Nothing yet, and the report says so rather than letting the suite imply
otherwise.** An editorial profile is the thing a production plan is written
against — PROD-001 — and a plan is what a slot, an inventory check and a
generation proposal hang off after that. Wiring a caller here would have meant
shipping the plan in the same change as the profile it points at.

The one thing that could have been wired now and was not: the enrichment prompt
does not read `guidance()`. That is a real improvement — a suggestion made
against an imprint's palette is a better suggestion — and it belongs with a
prompt-version bump and its own before/after, not smuggled into the ticket that
created the table.

## Not in scope, deliberately

There is no HTTP surface and no screen. A profile is created rarely, by an
operator who is setting the installation up, and the shape of the form depends
on what a production plan turns out to need from it. Shipping a screen before
the first consumer exists is how a form grows fields nothing reads.
