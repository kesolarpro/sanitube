# OPS-002 — the brakes

## Where this sits

Four reports in a row — DEDUP-001, DEDUP-002, DEDUP-003 and TRN-001 — deferred
backfilling with the same sentence: *"needs the backlog circuit breaker"*. This
is that, plus the global stop it belongs beside.

Neither existed. Both are §27 and §28 of the mission brief, and both are
prerequisites rather than polish.

## The failure this prevents is specific

`StartIngestionBatch` enqueues **one job per item**, in a loop. An import of
nine hundred files is nine hundred jobs; a backfill over an existing library
would be fifty thousand.

On this platform's baseline — a database queue drained by a cron-driven worker
on a shared cPanel account — that is not slow, it is fatal. The jobs table grows
faster than it drains, every other feature needing a job waits behind it, and
the operator's only remedy is a `DELETE` they should not be running.

## Two gates, kept separate on purpose

| Gate | Question | Kind |
|---|---|---|
| `BackgroundWork` | should this installation be doing anything right now? | a person's decision |
| `BacklogGuard` | is there room? | a measurement |

They stay separate so an operator can see which one stopped them, and so
lifting one does not lift the other. `WorkAdmission` asks both.

## The switch is a database row, not configuration

A kill switch has to work **when the thing that is wrong is the cache**, and it
has to survive `config:cache` — which on the cPanel baseline runs at deploy time
and then not again for weeks. Somebody stopping a runaway backfill cannot be
asked to edit a file and redeploy.

It is also deliberately blunt: paused means *no* new background work, not "less"
or "only the important sort". An operator reaching for this is usually watching
something go wrong and needs one action with an obvious effect.

**It stops work being taken on, not work already running.** A job mid-flight
finishes — killing one halfway is how a half-written object or a half-imported
batch happens, and this switch exists to prevent damage rather than cause a
different sort. The console command says so in as many words, because that is
the thing an operator will otherwise assume it does.

Re-pausing keeps the first moment and the first reason. The useful question is
when this started, and a second press of the same button must not reset the
answer.

## The ceiling refuses whole requests

Not a throttle. Half-enqueuing a batch and leaving the remainder to a sweep that
may never come is how work gets stranded where nobody is watching; refusing the
whole request tells somebody now, while they are still looking at it.

The check sits beside the acceptability check that was already there, and for
the reason that class already gives: *"a request naming five hundred objects the
platform refuses to import fails once, in the response, rather than five hundred
times in a queue where nobody is watching."* Capacity is the same argument.

Two decisions worth stating:

- **Depth comes from the queue driver**, not from a counter this platform keeps.
  A counter is a second source of truth that drifts the first time a job is
  deleted by hand.
- **`depth()` returns null, never zero, when the driver cannot answer.** Zero
  would let an unmeasurable queue read as an empty one and disable the guard
  silently on exactly the drivers it cannot see into. A null admits the work —
  refusing every import on a driver that cannot report its size would break a
  configuration this platform supports, and the ceiling is a safeguard rather
  than a correctness requirement. Both halves are asserted.

`0` removes the ceiling, which is legitimate on a machine with a real worker.
It is a count rather than a proportion because a fraction of an unknown machine
is not a limit anybody can reason about.

## The console, not only a screen

`sanitube:work:pause`, `:resume`, `:status`. The moment an operator most needs
this is the moment the interface is the thing that is struggling.

`:status` reports the queue as **unknown** rather than as zero when the driver
cannot say. A number nobody measured is worse than an admission, because it is
the one somebody will act on.

## Audited

`operations.background_work.paused` and `.resumed`, against the installation
itself. This is the one control that changes what the whole platform will and
will not do, and the question after an incident is always when it was pressed
and by whom — including the case where the answer is "a console command, so
nobody is recorded", which is itself worth knowing. A pause that changes nothing
is not audited twice.

| Mutation | Test that failed |

| an unmeasurable queue reads as empty | `a_queue_that_cannot_report_its_size_admits_rather_than_refuses` |
| a ceiling of zero becomes a real ceiling | `a_ceiling_of_zero_is_no_ceiling` |
| the pause gate dropped from admission | `pausing_stops_an_import_from_starting_at_all` |

## Not in this ticket

- **An interface control.** The console covers the incident case, which is the
  one that cannot wait. A settings toggle is small and belongs with the next
  operations screen work.
- **Per-queue or per-feature pausing.** Deliberately not: the value of this
  switch is that its effect is obvious, and a policy engine is the opposite of
  that. If a real need for granularity appears it should arrive with the case
  that motivated it.
- **Holding jobs already queued.** The switch stops intake; the backlog drains.
  Releasing queued jobs back with a delay would need job middleware on every job
  class and would turn a drain into an indefinite hold.
- **The backfills themselves.** Unblocked now, but each is its own ticket.
