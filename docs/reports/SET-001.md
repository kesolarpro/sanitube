# SET-001 — The settings shell

What this installation is configured with, and never what it is configured
*to*.

## The one rule

Every credential is reported as one of two words: **configured** or **not
configured**. Not masked, not truncated, not four asterisks and the last two
characters, not a length.

A masked secret is a secret with the guessable part left in. The length of an
API key narrows a search; the last four characters of a token confirm one; a
prefix says which provider issued it. So the payload carries a boolean, and
there is no reveal button because there is nothing to reveal — the value was
never sent.

Four tests hold this: the value is absent from the payload, absent from the
rendered HTML, absent as a prefix, absent as a suffix, and the secret object
has no `value`, `length`, `masked` or `preview` key.

## What *is* published, and why it is not a secret

- **Which provider is selected.** A label has to know whose service holds their
  masters. That is provenance.
- **Which environment variable a value comes from.** Documentation, and it is in
  the repository already.
- **Whether a value is present.**
- **Debug mode**, because being wrong about it is invisible from every other
  screen and hands stack traces, queries and environment values to whoever
  triggers an error.
- **Whether the configuration cache is built**, because until it is rebuilt an
  edited `.env` has changed nothing at all, and nothing else in the interface
  says so.

## Three vocabularies, kept apart

- **Not configured** — the variable is empty. A fact about this machine.
- **Unavailable / unknown provider** — a name is configured that this
  installation has no adapter for. A configuration mistake, not a missing
  credential, and a different thing to fix.
- **Unknown** — deliberately unused here. This screen reads configuration, which
  is always readable. It is the *health* screens that have to say "unknown",
  because they report on things that can be unreachable.

A provider that needs no credentials — `none`, local storage — is **complete**,
not incomplete. "Disabled" is a finished configuration, and reporting it as
missing something teaches an operator to ignore the flag.

## Read-only, and administrator-only

Read-only because SET-001 is the *shell*. Knowing what is set is a different
problem from changing it, and changing it means writing a `.env` file from an
HTTP request — a security surface that deserves its own ticket and its own
review rather than arriving as a side effect of a screen that reports.

Administrator-only even though it publishes no secret: the list of which
credentials are *missing* is itself a map of where the soft spots are.

Nothing is probed. No provider call, no bucket round trip. This is the page
somebody opens to find out what is set, and an outage must not take it down.

## A real bug PHPStan caught

The first implementation read presence with `env()`. Larastan refused it, and
it was right for a reason that matters more than the rule: **an installation
that has run `config:cache` — which every production one should — gets `null`
from `env()` for everything.** The screen would have reported a fully working
platform as entirely unconfigured, on exactly the installations that are
hardest to debug.

Presence is now read through config. The variable name still travels, as
documentation. `a_configured_credential_survives_a_cached_configuration` clears
the environment, sets the value in config alone, and asserts it reads as
configured.

## Mutation pass — 12 injected, 12 killed

| # | Regression injected | Killed by |
|---|---|---|
| M1 | the secret carries its value | no credential value in the payload |
| M2 | the secret carries a masked preview | no prefix either |
| M3 | the secret carries its length | no length field |
| M4 | whitespace counts as configured | whitespace is not a credential |
| M5 | an unknown provider reported as known | unknown storage provider |
| M6 | completeness ignores what is missing | incomplete while anything is missing |
| M7 | local storage asked for cloud credentials | local needs no credentials |
| M8 | debug mode not reported | debug mode is reported |
| M8b | presence read from the environment | survives a cached configuration |
| M9 | settings leave the administrator role | only an administrator may open it |
| M10 | the navigation offers settings to everybody | a member is not offered settings |
| M11 | every disk read as if it were s3 | each provider read from its own disk |

**M5 and M11 survived the first run, and both were real gaps.**

M5 replaced the *storage* section's `known` computation, and the suite only
tested the AI one — every section computes it for itself, so every section
needs its own test.

M11 hard-coded the `s3` disk. Nothing covered `r2` or `b2`, which are
S3-compatible and configured on their own disks: reading `s3`'s credentials for
all three would report a working b2 installation as unconfigured, and a
configured s3 disk would report an empty r2 one as ready.

## Not in this ticket

Writing configuration. A separate ticket, because writing a `.env` from a web
request needs its own review: which values may be set at all, what happens to
the file's permissions, and how the configuration cache is rebuilt afterwards.
The installer already has `EnvironmentFile`, which backs up before writing and
refuses to write without a backup — that is the piece such a ticket would build
on.
