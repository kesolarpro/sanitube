# UPL-001 — Un fichier entre dans SaniTube depuis un navigateur

Premier ticket du chemin critique identifié par l'audit de parcours produit.

---

## Ce qui manquait

L'audit a trouvé qu'**aucun `<input type="file">` n'existait dans l'intégralité
de `resources/js`**. Conséquences directes :

- Ni audio ni image ne pouvait entrer depuis un navigateur.
- L'écran d'ingestion importe depuis un préfixe de stockage — il suppose donc
  les fichiers déjà déposés par FTP ou une console S3, hors application.
- Le sélecteur de pochette d'une release ne propose que les assets `ARTWORK`
  existants. Aucun ne pouvant être créé depuis l'interface, il était vide sur
  une installation neuve, **définitivement**.

Le backend de l'upload direct existait pourtant, testé : `BeginDirectUpload`,
`DirectUploadController`, deux routes. Rien ne l'appelait.

## Le problème que la conception a dû résoudre

`LocalStorageProvider` **n'implémente pas** `SupportsDirectUpload` — seuls
S3, R2 et B2 le font. Or le stockage local est le défaut livré et la seule
option sur un hébergement sans stockage objet. Câbler uniquement le chemin
direct aurait donné une installation cPanel toujours incapable d'accepter un
fichier, ce qui contredit l'exigence de portabilité.

**Deux chemins, un écran, et l'interface dit lequel elle utilise.**

| | Stockage objet | Stockage local |
|---|---|---|
| Chemin | direct, les octets n'entrent jamais dans PHP | relayé par l'application |
| Plafond | celui de SaniTube | le plus bas entre SaniTube et PHP |

L'alternative — faire signer un PUT au stockage local — ressemblerait au chemin
direct tout en traversant PHP, et annoncerait deux gigaoctets à un hôte qui
refusera à huit mégaoctets.

**Le plafond effectif est calculé et la limite contraignante est nommée.** Un
opérateur qui a monté `SANITUBE_MAX_MASTER_BYTES` à 2 Go en laissant
`post_max_size` à 8 Mo a une installation qui refuse tous les masters ; un écran
affichant 2 Go lui mentirait au seul endroit où il regarderait.

---

## Ce qui a été construit

- `UploadAdmission` — quels genres sont déposables, quels types sont acceptés,
  quel plafond s'applique, et ce que PHP lui-même accepte. Tout en configuration.
- `RelayedUploadController` + `RelayedUploadRequest` — le chemin relayé.
- `UploadScreenQuery` + `UploadScreenController` — ce que l'écran a le droit de
  promettre, **mesuré sur l'installation**.
- `resources/js/Pages/Assets/Upload.vue` — sélection multiple, glisser-déposer,
  progression, refus par fichier, doublon signalé.
- `config/assets.php` — `accepted_upload_types` par genre.
- Six langues, plus un groupe de statuts `upload` dans `StatusBadge` : l'état
  d'un dépôt est coloré par les mêmes règles que tous les autres statuts, plutôt
  que par un badge inventé pour l'occasion.

**Séquentiel, un fichier à la fois.** Quarante masters sélectionnés sur un
hébergement mutualisé ouvriraient sinon quarante connexions simultanées, et le
premier à céder serait l'hôte. C'est aussi ce qui rend l'échec lisible : un
refus n'emporte pas le lot.

**Seuls `AUDIO_MASTER` et `ARTWORK` sont déposables.** Un dérivé, un extrait et
un stem sont *produits* par la plateforme à partir d'un master ; en accepter un
directement créerait de l'audio dont la filiation serait une affirmation plutôt
qu'un enregistrement.

## Sécurité

- **Le type est lu dans les octets**, jamais dans l'extension ni dans le
  `Content-Type` annoncé par le navigateur.
- Autorisation par le middleware de route (`can.role:catalogue`) — un MEMBER en
  lecture seule est refusé sur l'écran **et** sur le POST, testé.
- Refus **avant** enregistrement quand le fichier dépasse le plafond : le
  plafond de flux dans `AssetStorageService` l'attraperait aussi, mais après
  qu'une ligne existe pour un fichier qui n'allait jamais être conservé.
- Le nom de fichier ne touche jamais la clé d'objet — garantie existante
  d'`AssetObjectKeys`, dérivée de l'uuid.
- **Aucun chemin, disque ou empreinte ne revient au navigateur**, vérifié en
  cherchant chacun dans le corps de la réponse.
- Les refus sont des **codes**, traduits côté client ; le serveur n'envoie
  jamais de phrase, parce que ses phrases nomment des clés de stockage.

## §1 — les deux preuves

**A. PREUVE DE COMPOSANT.** `tests/Feature/Assets/BrowserUploadTest.php`,
14 tests / 63 assertions.

**B. PREUVE DE CHEMIN DE PRODUCTION.** Tous les tests passent **par la route
HTTP**, pas par le service. C'est tout l'enjeu du ticket : le backend existait
déjà et était testé, et rien ne l'appelait — un test sur
`AssetStorageService` serait passé avant ce ticket aussi.

## Le piège de fixture, et il allait dans le mauvais sens

`UploadedFile::fake()->createWithContent('master.wav', 'this is not audio')`
rapporte **`audio/wav`** : `Illuminate\Http\Testing\File::getMimeType()` déduit
le type du *nom de fichier*.

Un test bâti dessus serait passé contre une implémentation qui fait confiance à
l'extension — c'est-à-dire exactement le défaut que ce fichier doit attraper.
Mesuré plutôt que supposé :

| | `getMimeType()` |
|---|---|
| `UploadedFile::fake()->createWithContent('master.wav', 'this is not audio')` | `audio/wav` |
| Vrai `UploadedFile` sur le même contenu | `text/plain` |

Tous les tests où le type compte utilisent donc de vrais `UploadedFile`, avec
un véritable en-tête RIFF pour l'audio et un JPEG réellement encodé.

C'est le motif que le projet avait déjà rencontré avec `width => 3000` dans la
factory d'assets : une fixture qui fournit la réponse que le code était censé
produire.

## §2 — mutations

Dix mutations. **Les dix tuées.**

| # | Mutation | Verdict |
|---|---|---|
| U1 | le type n'est plus vérifié | tuée |
| U2 | `getMimeType()` → `getClientMimeType()` | **tuée** |
| U3 | tout genre devient déposable | tuée |
| U4 | le plafond n'est plus appliqué | tuée |
| U5 | l'asset n'est plus vérifié après stockage | tuée |
| U6 | tous les genres deviennent déposables | tuée |
| U7 | tout type est accepté | tuée |
| U8 | le plafond effectif ignore la limite PHP | tuée |
| U9 | liste vide = tout refuser | tuée |
| U10 | l'écran annonce toujours le chemin direct | tuée |

**U2 est celle qui compte.** Elle remplace la lecture des octets par la lecture
du `Content-Type` envoyé par le client. Avec `UploadedFile::fake()` elle aurait
survécu ; avec un vrai upload elle meurt. C'est la mutation qui prouve que le
test discrimine réellement.

**U5 est la seconde.** Sans vérification après stockage, l'asset resterait à
`STORED` — et l'analyse, la mesure d'artwork et la déduplication se déclenchent
toutes sur `AssetVerified`. Le fichier serait entré et n'aurait plus jamais
bougé.

Aucune mutation retirée.

## Ce que ce ticket ne fait pas

- **Pas de reprise après interruption.** Un dépôt coupé à mi-parcours est repris
  depuis le début. Une reprise réelle demande un upload en parties, donc un
  protocole côté fournisseur — son propre ticket.
- **Pas d'import en masse depuis cet écran.** Le lot séquentiel convient à
  quelques dizaines de fichiers ; 900 titres restent le domaine de l'import par
  préfixe, qui existe.
- **Pas de rattachement automatique à un candidat ou une release.** Un master
  déposé apparaît au catalogue et suit le pipeline existant ; le raccorder à un
  morceau reste l'étape suivante du parcours.
- **Rien n'a été cliqué dans un navigateur.** Les tests traversent la route
  HTTP réelle ; ils ne remplacent pas un essai manuel.
