# UI-004b — Candidate review actions

## What this delivers

The review queue can now be worked. Three decisions, each reachable from the
candidate detail screen:

| Action | Route | Service it calls |
| --- | --- | --- |
| Add to the catalogue | `POST ingestion/candidates/{uuid}/promote` | `PromoteTrackCandidate` |
| Decline | `POST ingestion/candidates/{uuid}/reject` | `RejectTrackCandidate` |
| Correct the title | `PATCH ingestion/candidates/{uuid}` | `ReviseTrackCandidate` |

**No new domain logic.** Every service is CAT-001's, merged and unchanged. This
ticket is the surface: a confirmation flow, an override-reason flow, the role
guard on the route, and the translation of refusals into sentences a reviewer
can act on.

## Nothing here writes a status

`$candidate->update(['status' => 'PROMOTED'])` would look like the same thing
and would skip: the guarded UPDATE that makes double promotion impossible under
a race, the duplicate-master check that follows the duplicate chain, the asset
verification check, and the requirement that overruling the machine be
justified in writing.

A test proves it rather than a comment claiming it. Replacing the reject
service call with a direct `forceFill` of the status turns
`a_promoted_proposal_cannot_be_declined_afterwards` red — because the domain
refuses to "reject" something already in the catalogue, and an assignment does
not.

## Authorisation lives on the route

`can.role:catalogue`, beside `auth` and `active`. A **MEMBER may read the
review queue and decide nothing in it** — asserted on all three actions.

The `actions` block the read model now returns — `can_promote`,
`can_promote_with_override`, `can_reject`, `can_revise` — is **presentation,
never authorisation**. It exists so the interface can draw a disabled button
with an explanation instead of a button that fails.

One test makes that separation load-bearing rather than asserted: it takes a
`PENDING` candidate, confirms the payload offers no promote button, then posts
the promotion anyway and watches the domain refuse it. Removing every flag in
the block would change what the screen looks like and change nothing about what
a request is allowed to do.

The status predicates come from `TrackCandidateStatus` itself — `isPromotable()`,
`isPromotableWithOverride()`, `isRevisable()` — not from a second copy. If one
ever changes meaning, this changes with it.

## The override flow

`READY` promotes outright. `NEEDS_REVIEW` and `DUPLICATE` require an explicit
override **and a stated reason**, and the note box only appears when the domain
would demand it. Showing an override box on a READY candidate would teach
reviewers to fill one in every time, which is how an override stops meaning
anything.

The pairing is enforced in `PromoteTrackCandidate` and deliberately **not**
restated in the form request. It is a property of the decision, not of the HTTP
request that carried it, and a second copy in a form is a second copy that can
drift. A test posts `override: true` with no note and watches the domain refuse
it with `OVERRIDE_NEEDS_NOTE`.

## Two corrections to what already existed

**The reviewer is now recorded.** The API's promotion call leaves `reviewerId`
null; this one passes the signed-in user. A decision that changed the catalogue
and names nobody is a decision nobody can be asked about later. Same for
rejection.

**Revision touches only the title.** `ReviseTrackCandidate` accepts a
`metadata` array and merges it, and the interface deliberately does not expose
that. A candidate's metadata is where the importer's evidence lives — what the
file said, what the manifest claimed, what the platform noticed — and a
free-form editor over it would let a reviewer rewrite the evidence their own
decision is supposed to rest on. A test asserts the manifest survives a title
correction intact.

## Refusals

Every `CandidateReviewException` carries a machine-readable reason. The
controller returns the **code** via `withErrors`, and the interface translates
it into one of seven sentences. The domain's English is never rendered — it is
written for a developer reading a log, the same reason a storage driver's
message is withheld from the ingestion screens.

Seven codes translated in six languages: `NOT_PROMOTABLE`,
`OVERRIDE_NEEDS_NOTE`, `ALREADY_PROMOTED`, `ALREADY_DECIDED`,
`ASSET_NOT_VERIFIED`, `MASTER_ALREADY_IN_CATALOGUE`, `TITLE_REQUIRED`.

## Confirmation, and where the buttons sit

Promote and decline are `ConfirmDialog`s — promote because it is the one action
that writes to the catalogue, decline because it is destructive in the sense
that matters. Revision has no confirmation: correcting a guess before anybody
acts on it is the cheapest thing here to undo.

The action card sits **last on the page, after the evidence**. A decision is
taken after reading, and a promote button above the analysis is one people
press before they have looked.

The promote dialog says what promotion is and is not: it creates a draft, it
publishes nothing, and it assigns no ISRC.

## Guardrails proven

Six regressions injected; **every one turned a test red**:

| Injected regression | Caught by |
| --- | --- |
| role guard dropped from the review routes | a member may read the queue and decide nothing in it |
| controller assigns a status instead of calling the service | a promoted proposal cannot be declined afterwards |
| `override` forced true, so the note requirement never bites | 2 tests |
| the reviewer is no longer recorded | promoting a ready candidate creates exactly one draft track |
| revision replaces the metadata instead of only the title | correcting the suggested title leaves the evidence alone |
| the actions block claims a member may review | a member is not offered the actions either |

## Tests

21 new tests. **819 PHP tests / 3470 assertions**, 1 skipped (the real ffprobe
run), plus 16 component tests. PHPStan level 6 clean, no baseline. Pint clean.
vue-tsc clean. Frontend build clean. Strings in `en/fr/es/it/pt/de` with the
completeness gate passing both directions.

Covered: unauthenticated refused, deactivated account refused, MEMBER refused on
all three actions, double promotion refused with one Track surviving, unverified
master refused, override without a note refused, held candidate without an
override refused, one recording cannot enter the catalogue twice, decline
without a reason refused, promoted candidate cannot be declined afterwards,
decided candidate cannot be revised, empty title refused rather than erasing the
suggestion.

## Architecture amendment

**None.** No migration, no new table, no invariant touched, no domain service
changed. Three routes, one controller, three form requests, one read-model
addition, one page extended.

## Review

Not `REVIEW_REQUIRED` under the standing policy: ordinary UI over
already-approved domain services. It changes no authorization semantics — it
consumes SEC-001's existing `can.role:catalogue` middleware — introduces no
invariant, and every refusal it can produce was already produced by the API
surface merged in CAT-001.
