# ART-002 — Generated artwork, and the refusal that comes before the spending

An image provider, written against the published OpenAI specification, plus the
check that stops it being used pointlessly.

---

## The finding that shaped the ticket

Reading the specification before writing anything — §5's rule — turned up a
mismatch a generator built on assumption would have discovered by paying for it.

**This platform's default artwork requirement is a 3000px shortest side**
(ART-001). The published `CreateImageRequest` schema lists, for the GPT image
models, the standard sizes `1024x1024`, `1536x1024` and `1024x1536`. The only
square among them is 1024.

Generate first and validate afterwards, and **every** cover is billed and then
rejected by the platform's own validator.

So `ArtworkFeasibility` compares the two configurations *before* a request is
sent, and `GenerateArtwork` refuses with `REQUIREMENTS_UNREACHABLE` carrying the
numbers that disagree. Both sides are settings, so an operator has two honest
ways out — lower the requirement, or declare a larger size their account and
model actually support.

**The shipped configuration therefore refuses out of the box, and that is
deliberate.** `config/artwork.php` says so in the comment beside the setting,
and a test asserts the two numbers still disagree — so if they ever stop
disagreeing, the comment explaining why they do not is caught as wrong.

## What the specification actually says

Read from `openai/openai-openapi` — the `createImage` operation at
`POST /images/generations`, `CreateImageRequest`, `ImagesResponse` and `Image`.
Two details shape the adapter, and both are the kind an assumption gets wrong:

- **`response_format` is not a GPT-image parameter.** The specification scopes
  it to `dall-e-2` and `dall-e-3` and says the GPT image models "always return
  base64-encoded images". Sending it to one sends a parameter it does not take.
  A test asserts the key is **absent** from the request body.
- **A `url` is only produced by the dall-e models and is valid for 60 minutes.**
  That is a bearer credential with an expiry. This adapter never returns one: a
  response carrying only a URL is treated as unreadable rather than followed.
  Nothing downstream holds a provider address, and nothing here fetches one on
  the platform's behalf.

**Sizes are declared in configuration, never inferred.** The specification lists
different allowed sizes per model, describes arbitrary sizes for one family
under divisibility and aspect constraints, and marks the largest as
experimental. Deriving from a model name what a given account may request is
exactly the guessing ADR-0018 and §5 forbid.

## What was built

`ImageSize`, `ImageCapabilities`, `ImageRequest`, `GeneratedImage`,
`ImageProvider` (contract), `OpenAiImageProvider`, `UnavailableImageProvider`,
a shipped `FakeImageProvider`, `ArtworkRefusal`,
`ArtworkGenerationException`, `ArtworkFeasibility`, `GenerateArtwork`, and a
`providers` block in `config/artwork.php`.

**A generated cover becomes an ordinary asset, not a special case.** It is
registered as `ARTWORK`, stored through the same service every upload uses,
checksummed and verified — so ART-001's listener measures it and the release
validator judges it on that measurement. A generated cover gets no more trust
than an uploaded one, and the provider's claim about what it produced is never
what the platform reports.

## §1 — the two proofs

**A. COMPONENT PROOF.** `tests/Feature/Artwork/ArtworkGenerationTest.php`,
20 tests / 51 assertions.

The headline test is not that generation works. It is that when the two
configurations disagree, **nothing is sent at all** — asserted on the fake
provider's own record of what it was asked (`$provider->requests === []`), not
on the outcome. "It failed" and "it never asked" look identical from the return
value and are not the same thing when one of them costs money.

**B. PRODUCTION-PATH PROOF — who calls this in production?**

- **`GenerateArtwork`** registers, stores and **verifies**, and the test asserts
  `MeasureArtworkJob` was queued — proving the ART-001 listener fired, rather
  than measuring by hand.
- **The container binding.** Everything else builds providers by hand, which
  proves an adapter works without proving a configured installation gets one.
  Two tests: the named driver resolves, and a differently-named entry
  (`openai-eu`) resolves by its `driver` key.

## Three things caught during the ticket

**1. The generated cover would never have been measured.** `store()` leaves an
asset at `STORED`; verification is a separate step, and ART-001's listener fires
on `AssetVerified`. Without it the cover sits unverified for ever and the
release validator reports it unmeasured for the rest of its life. Caught by an
assertion that failed on the status, then fixed by verifying inside
`GenerateArtwork` — the same thing `ProcessIngestionItem` and
`SelectMusicGenerationResult` already do after storing bytes.

**2. The portability guardrail caught a hardcoded domain.** I gave
`base_url` a default of `https://api.openai.com/v1`. The existing convention is
**no default at all** — `config/ai.php` and `config/transcription.php` both read
it purely from the environment — and the standing constraint is that nothing
hardcodes a domain. `no_domain_is_hard_coded_in_application_code` failed, which
is exactly what it is for. An installation that has set no base URL now has no
image provider, which is the correct state for one that has not configured one.

**3. PHPStan caught dead code dressed as intent.** I had written a `note()`
method that redacted an exception message and then discarded it, with a docblock
explaining why. `void.pure` flagged that it has no side effects. It was removed:
the `catch` now says plainly that the message is not captured, and that
redacting it would not make it safe — redaction masks this installation's
credential and cannot mask the prompt the client quotes back.

### B11 — the right answer for the wrong reason

Removing `if (! $response->successful())` survived, because a 401 body carries
no `data` and `firstImage()` returns null anyway. The guard was behaviourally
redundant *against that fixture*.

The discriminating case is a **non-2xx carrying a well-formed body** — a stale
cache, an echoing gateway. Reading the body and ignoring the status would hand
back an image this request did not generate. That is a real contract statement,
not an implementation detail: the same principle the distribution module already
holds, that an outage is decided by code and never by what the message happens
to contain. The test added asserts a 502 with a valid images payload returns
nothing.

### B16 — the binding had no test

Every other test built a provider by hand, so removing the `openai` branch from
the container binding left everything green. **A working adapter and a working
feature are different claims**, and this is now the fourth ticket in a row where
mutation found precisely that gap. Two tests added, and the second (`openai-eu`)
also kills B17.

No mutation was withdrawn.

## What this ticket did not do

- **No screen and no route.** Generation is reachable from `GenerateArtwork` and
  nothing calls it yet. A button that spends money needs its own confirmation
  surface and its own authorization ticket — SET-002's reasoning.
- **No spend ceiling for images.** GEN-004 built one for music. Images need the
  same, against the asset ledger rather than `music_generations`, and it is not
  silently covered by this.
- **No edit or variation endpoints.** `/images/edits` and `/images/variations`
  exist in the specification and are not implemented.
- **Nothing certified against the real endpoint.** No key in CI. The adapter has
  never spoken to OpenAI, and `AI-002` covers it.
