# INS-002 — Installing SaniTube from a browser

## The gap

INS-001 built `sanitube:install` as a service with a terminal in front of it,
and said so: *"the service is the installer so INS-002 can reuse it."* What it
could not do is help the operator it was designed for. A cPanel account
frequently has no SSH at all — File Manager and phpMyAdmin, and nothing that
runs `php artisan`.

It also assumed somebody had already edited `.env` with working database
credentials, which on that host is the hard part rather than the easy one.

## The problem a web installer has and no other screen does

**Before installation there are no accounts, so there is nobody to
authenticate.** Roles, the active check, the session — every guard the platform
has depends on the thing being set up.

An `/install` page guarded only by "available while uninstalled" is a page where
whoever reaches the URL first becomes the owner of somebody else's catalogue,
and on shared hosting the window between uploading files and finishing setup is
measured in minutes.

### The token

A random 64-character value is written to `storage/installer/token` at 0600 on
the first visit and **shown nowhere**. To proceed, the operator copies it out of
that file.

That converts *"anybody who found the URL"* into *"somebody who can read a file
on this server"* — which is exactly the person who should be installing it, and
on cPanel is a thirty-second job in File Manager while `php artisan` is often
not available at all.

It is not a password and is not treated as one: single-purpose, regenerated per
installation, compared with `hash_equals`, and deleted the moment the installer
locks. Leaving a usable credential on disk for a door that is already shut would
give it exactly one remaining function — being found.

### Two guards, not one

`EnsureInstallable` asks both:

- **Is the lock absent?** The file written when the installer finishes.
- **Is the installation incomplete?** Asked of the *installation* — key,
  database, schema, active owner — not of the lock.

Both, because a lock file can be deleted by anybody with the access the token
demands, and an installation with a live owner must refuse regardless of what
any file says.

A refusal is **404, not 403**. A 403 confirms a SaniTube installer once lived
here, which is an invitation to come back and look for the lock file.

## The finding that made the installer possible at all

SaniTube ships `SESSION_DRIVER=database` and `CACHE_STORE=database`. Those are
right for a running installation and impossible for the one screen that runs
*before* the schema exists:

> the install page renders → Laravel stores the session that carries the CSRF
> token → there is no `sessions` table → the form cannot be submitted

on precisely the host the web installer exists for.

So the installer's routes run their session and cache on the filesystem. This
forced a second decision: `StartSession` reads the driver from configuration as
it runs, and route middleware runs *after* a group's — so joining the `web`
group would put the swap too late to matter. The installer declares its own
middleware stack, in order, with `UseFilesystemState` first and
`EnsureInstallable` last.

## Not one stage is reimplemented

Every stage is `InstallationService`'s, unchanged and in the same order the
console command runs them. A web installer with its own copy of the stages is
the one that misses a fix — that regenerates `APP_KEY` on a re-run, creates a
second owner, or writes `.env` without a backup. The service already refuses all
three and this controller does not get an opinion.

What the controller adds is the three things a browser needs and a terminal does
not: the token, somewhere to type the database settings, and the lock.

### Writing configuration

An **allowlist** of seven keys, never "whatever was posted". A form that can set
an arbitrary `.env` key can set `APP_DEBUG`, `APP_KEY` or the mail credentials —
and this one runs before anybody has authenticated.

An absent optional field leaves the existing line alone rather than writing an
empty string, so the installer cannot erase a value nobody asked it to change.
Everything goes through `EnvironmentFile`, which refuses to write without taking
a backup first — asserted, so the installer cannot quietly go around it.

Reconnecting after the write happens **only when something changed**. Purging a
connection that is already correct throws away a working handle to open an
identical one, and on a re-run it drops the connection the previous stages just
proved was good.

## A real defect, found by a surviving mutation

M5 restored `->withInput()` on the refusal path, and the test stayed green — so
the test was asserting the wrong thing. It checked the rendered HTML, and today's
template reads `old()` for nothing sensitive.

Rewriting it to assert on the **session** immediately failed *without any
mutation*, which is how the actual defect surfaced:

> Laravel's validation redirect flashes the request input, and its default
> exclusion list is `current_password`, `password`, `password_confirmation` —
> every secret the framework can guess the name of, and not every secret this
> platform has. **`db_password` was being flashed into the session on every
> validation failure.**

Nothing rendered it today. The next person to add `value="{{ old('db_password') }}"`
— an entirely reasonable edit — would have rendered a database password into
HTML from a template that did nothing wrong.

Fixed in `bootstrap/app.php` by adding `db_password` and `token` to
`dontFlash`, application-wide: `token` is both the installer's filesystem
credential and a password-reset token, and neither should ever be flashed
anywhere.

**Flashing a secret is the defect. Rendering it is the consequence.**

## Mutation testing

Six injected, six killed.

| # | Mutation | Killed by |
|---|---|---|
| M1 | Removed the lock check from the middleware | `a_locked_installer_is_gone_rather_than_forbidden` |
| M2 | Removed the completeness check, leaving only the lock | `a_complete_installation_refuses_even_with_no_lock_file` |
| M3 | Made an absent token accept anything | `the_token_is_refused_when_there_is_none_at_all` |
| M4 | Never wrote the lock after installing | `a_valid_token_installs_and_the_door_closes_behind_it` |
| M5 | Restored `->withInput()` on the refusal path | `a_refusal_does_not_flash_what_was_typed_into_the_session` (after the test was corrected) |
| M6 | Left the token on disk after locking | `a_valid_token_installs_and_the_door_closes_behind_it` |

M5 is the one worth reading: it survived, the test was fixed to assert what it
names, and fixing it exposed a defect in the application's exception
configuration rather than in the installer at all.

## Not covered

- **Rate limiting on the token field.** Deliberately absent. The token is 256
  bits of entropy compared with `hash_equals`; a throttle would add a cache
  dependency to the one screen that must work before the cache is configured,
  in exchange for slowing an attack that is not feasible to begin with.
- **A real cPanel installation.** Everything here is proved against the test
  suite. `CPANEL_CERTIFICATION` remains a thing somebody has to perform on a
  real host, and this report does not claim otherwise.
- **Resuming a part-finished install** works by re-running: every stage is
  idempotent and reports `SKIPPED` with its reason. There is no stored
  wizard state, deliberately — state about a half-finished install is one more
  thing that can be wrong.
