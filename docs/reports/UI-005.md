# UI-005 — The studio screens

## What this delivers

Five read-only screens over GEN-001:

| Screen | What it answers |
| --- | --- |
| `/studio` | Can this install generate at all, and what has it generated |
| `/studio/projects` | Which campaigns exist |
| `/studio/projects/{uuid}` | One campaign, its defaults, and its generations |
| `/studio/generations` | Every request made to a provider |
| `/studio/generations/{uuid}` | What was asked for, and what came back |

Plus the read models, filter and cursor validation, six locales, and the
navigation entry that makes the studio reachable at all — it has been a
disabled item in the sidebar since UI-001.

**Nothing here writes.** Starting a generation calls a supplier and costs
money, and the surface that does it needs a confirmation flow and a provider
cost surface of its own. Recorded as **UI-005b**.

## The provider banner is the point of the overview

GEN-001 ships one real capability — a fake provider — and no credentials for
anything else. On most installs the honest thing for the studio to say is
**"no generation provider is configured"**, and to say it plainly. A screen
that offered a generate button regardless would produce a failure the operator
could only diagnose by reading logs.

Three states, kept genuinely distinct:

- **Not configured** (`none`, the disabled provider). Nothing is wrong.
  Generation is optional and SaniTube runs fully without it, which the banner
  says out loud so nobody goes looking for the broken part.
- **Configured but unavailable.** A provider is named and reports it cannot
  accept work — missing credentials, unaccepted terms — or is named and cannot
  be resolved at all. Something is wrong and it is fixable. An operator who
  typed a provider name wrong needs to see that, not an empty studio.
- **Available.** It will accept work.

`isAvailable()` is asked of the provider object, never of the network. No
outbound request happens on a page load — the rule UI-002's review settled for
every provider surface, and it applies here for the same reason: a screen that
probes a vendor is as slow and as unreliable as the slowest supplier.

## Commercial rights get their own place

`CommercialRightsStatus` defaults to `UNKNOWN` and **nothing in SaniTube ever
sets it from the fact of a successful generation**. So a count of UNKNOWN
generations is a count of recordings nobody has established may be sold, and
it belongs on the front page rather than buried on a detail view.

On the detail screen the rights answer is shown on its own rather than beside
the status, because "the audio arrived" and "the audio may be sold" are
different questions and only one of them has been answered. A generation with
`UNKNOWN` rights gets a warning banner saying so.

## What must not leak, and does not

| Withheld | Why |
| --- | --- |
| `music_generations.provider_job_id` | the handle the provider's own API uses for this job |
| `music_generation_results.source_reference` | where the provider serves the audio from — routinely a time-limited signed URL, so a bearer credential in a column |
| `music_generation_results.raw` | the provider's whole response, containing both of the above |

What replaces the reference is `has_audio`: whether there is anything to
import, without saying where from. That distinction matters on its own terms —
a completed generation with **no** audio is a provider fault rather than an
empty recording, and a reviewer needs to be able to tell those apart.

A result that has been imported links to its asset and its candidate by uuid.
That is where the audio is actually listened to, under the preview rules
UI-003d settled: minted on demand, short-lived, never on a page load.

`failure_reason` **is** kept, and the asymmetry is deliberate. Unlike a storage
driver's message it is a sentence the provider wrote about its own service,
naming nothing about this server — and it is the only thing distinguishing
"your prompt was refused" from "the provider was down".

## Honest values

`target_track_count` is nullable and stays nullable to the screen: a project
with no target renders "no target set", never `0`, because 0 says somebody set
a target of nothing.

Every generation state gets a count including the ones at zero, for the same
reason the ingestion screens do.

A project detail counts only its own generations, asserted by test — a project
that counted the whole studio would make "how many did that campaign produce"
unanswerable, which is the one question a campaign exists to answer.

## Guardrails proven

Five regressions injected; **every one turned a test red**:

| Injected regression | Caught by |
| --- | --- |
| the audio reference reaches the browser | 2 tests |
| the provider job id reaches the browser | 2 tests |
| an unconfigured provider reads as configured | a studio with no provider says it is not configured |
| an unresolvable provider is swallowed as unconfigured | a configured provider that cannot run is not reported as ready |
| project scoping dropped from the generation list | a project detail shows only its own generations |

## Tests

15 new tests. **798 PHP tests / 3364 assertions**, 1 skipped (the real ffprobe
run), plus 16 component tests. PHPStan level 6 clean, no baseline. Pint clean.
vue-tsc clean. Frontend build clean. Strings in `en/fr/es/it/pt/de` with the
completeness gate passing both directions.

Four commercial-rights labels — `ALLOWED`, `RESTRICTED`, `PROHIBITED`,
`REVIEW_REQUIRED` — were added to the shared generic status map rather than
being written into a template.

## GAP recorded, not filled

Creating a generation, cancelling one, and selecting a result are all supported
by the domain (`StartMusicGeneration`, `SelectMusicGenerationResult`) and none
appears on these screens. Each calls a supplier or moves audio into the
catalogue, so each needs a confirmation surface rather than a button. Recorded
as **UI-005b**.

No real music generation provider exists to activate. GEN-002 stays
`BLOCKED_EXTERNAL`: no official API, no credentials, and this ticket does not
invent one.

## Architecture amendment

**None.** No migration, no new table, no invariant touched, no existing
behaviour changed. Four read models that only read, five controllers, two form
requests, five pages.

## Review

Not `REVIEW_REQUIRED` under the standing policy: read-only UI over an
already-approved domain, no authorization semantics, no provider activation, no
external action, no write of any kind.
