# ING-001 — Music File Ingestion Pipeline

**Status:** delivered
**Base:** `7575e93` (main, after AST-001)
**Branch:** `claude/ing-001-ingestion-pipeline`

---

## What this ticket is actually about

Getting roughly 900 existing recordings into the platform without any of them
becoming a Track.

That negative is the whole design. An import is a bulk, unattended, partially
failing operation run by a job queue; the catalogue is the source of truth. If
those two are allowed to touch, the source of truth becomes whatever a batch
job guessed from a filename at three in the morning. So ingestion produces
**candidates** — proposals — and CAT-001 is where a human turns one into a
Track.

```
Source → IngestionBatch → IngestionItem → Asset (AST-001) → VERIFIED
       → TrackCandidate → review
```

## The entities

| Table | Holds |
| --- | --- |
| `ingestion_batches` | One import operation. Status, source, timestamps. |
| `ingestion_items` | One source inside a batch, and the idempotency boundary. |
| `track_candidates` | A proposal that a Track could exist. |

**No counters are stored on a batch.** Every count a progress display needs is
derivable from the items, and a denormalised counter that drifts makes a batch
look finished while work is still in flight. `itemCounts()` is a `GROUP BY`.

Everything on a candidate that resembles catalogue data is named
`suggested_*` or `matched_*`, and that naming is load-bearing. A guess stored
under an authoritative name is a guess that will eventually be read as fact —
including across the API, where `suggested_title` keeps its name.

`metadata` is JSON, unindexed, and holds only the incidental. A business rule
living in a JSON blob is a rule no database can help you keep.

## Idempotency

Three separate mechanisms, because there are three separate ways the same work
can arrive twice.

**1. The same *intent*, submitted twice.** `ingestion_key` is a SHA-256 of
`source | reference`. The unique index is on `(ingestion_key, active_marker)`,
where `active_marker` is `1` while the item is PENDING or PROCESSING and NULL
once terminal. Every engine in the matrix treats NULLs as distinct inside a
unique index, so unlimited finished attempts coexist while **at most one can be
in flight** — enforced by the database, not by the service remembering to look.

This is the same trick that carries "one active ISRC per track" in ARCH-002,
used again for the same reason: no partial index, no `CHECK`, no
engine-specific syntax.

A resubmission while the first is in flight is recorded as `SKIPPED` with
`ALREADY_IN_FLIGHT`, not dropped — the batch still accounts for every reference
the caller named.

**2. The same *job*, delivered twice.** Every at-least-once queue eventually
does this. `ProcessIngestionItem` returns immediately if the item is already
terminal, and the job carries the item's **uuid rather than the model** — a
serialised model is a snapshot of a row taken when the job was queued, and by
the time a worker picks it up that snapshot can be a lie.

**3. A crash *mid-upload*.** This is the one that shapes the code. The asset is
registered and `item.asset_id` is written **before** any bytes move. AST-001
derives an asset's object key from its UUID, so an asset that exists has exactly
one address; the retry re-uploads to that same address and overwrites the
partial write. Had the id been recorded after the upload, every attempt would
register a *new* asset and orphan the previous one's bytes.

A test kills the provider mid-upload, recovers it, retries, and asserts the
asset id is unchanged and exactly one asset exists.

## Duplicate bytes

Distinct from duplicate intent. The same master legitimately arrives twice —
under two names, from two folders — and AST-001 already detects it by SHA-256.
The item becomes `DUPLICATE`, the candidate becomes `DUPLICATE` with
`matched_asset_id` set, and both are kept for review. An import that errors
because a file is already known has lost the fact that it happened.

## Cloud import safety

A cloud import may not be pointed at the prefixes SaniTube writes to itself.
`AssetObjectKeys::managedPrefixes()` names them; `CloudImportReader` refuses
them.

Without this, "import everything" re-ingests every master as new material, and
running it twice produces duplicates of the duplicates. It is not a
hypothetical — it is the obvious first thing to try.

An empty prefix is refused for the same reason. When a prefix legitimately
contains a mix, the managed objects are filtered out rather than failing the
whole request.

`MANUAL_UPLOAD` references must live under the reserved `inbox/` prefix.
Otherwise "import this object" would be a way to name any object in the store,
including a master.

## Batches and the queue

`SANITUBE_INGESTION_MAX_BATCH`, default 500. The initial catalogue does not fit
in one batch on purpose: a batch is a unit someone has to be able to inspect
when it half-fails, and two batches of 500 that partly failed are diagnosable
where one wall of 900 rows is not.

The POST carries **references, never payloads**. Bytes arrive through the
storage pipeline; nine hundred files will not survive one HTTP request, and one
that tried would fail at a different point every time.

Work is bounded: N item jobs, plus a finalise dispatched only when an item
finds nothing else outstanding. Under a race two workers can both believe they
were last, which is why finalising is idempotent.

Runs on `QUEUE_CONNECTION=database`. Redis remains optional.

## What a batch's outcome means

`COMPLETED_WITH_ERRORS` is deliberately distinct from both neighbours.
Importing 900 files and losing four is neither a success nor a failure, and a
status that can only say one of those is a status that hides the four. Nothing
getting in at all is `FAILED`.

## API

```
POST /api/v1/ingestion/batches        → 202, references not payloads
GET  /api/v1/ingestion/batches
GET  /api/v1/ingestion/batches/{uuid}
GET  /api/v1/ingestion/candidates
GET  /api/v1/ingestion/candidates/{uuid}
```

Behind the internal token. `202` rather than `201`: the batch exists, the work
does not.

This is the first write in v1, and it writes to the staging side of the
platform rather than the catalogue — nothing here can create a Track, so
exposing it before the Identity module exists does not hand a shared token the
ability to mutate the catalogue.

Nothing published carries `disk`, `path`, `bucket`, `provider`,
`source_reference`, `ingestion_key`, `sha256` or an internal id. A test walks
every key of every response recursively to keep that true.

## Decisions worth challenging

- **A candidate is created `READY` on successful verification.** Today nothing
  else has to happen first. MED-001 inserts technical analysis into that
  transition — `PENDING → PROCESSING → READY`, or `WAITING_CAPABILITY` when the
  server has no FFmpeg — and `TrackCandidateStatus` already carries that case
  so MED-001 extends rather than rewrites. Stated here because it means ING-001
  alone marks candidates ready on a weaker basis than the finished system will.

- **Ingestion imports as `AUDIO_MASTER`.** ING-001 is music file ingestion. A
  later ticket importing artwork or documents will need the kind to come from
  the request.

- **Nothing deletes the source.** A `CLOUD_IMPORT` reference belongs to whoever
  owns that storage, and an import that removes its own input is one nobody
  dares run twice. The consequence is that `inbox/` accumulates: manual uploads
  stay after import. Inbox cleanup is a follow-up — the staging sweep
  deliberately touches only `staging/`.

- **`created_by` is nullable.** Identity does not exist yet. Declared now
  because backfilling provenance onto rows already imported is guesswork, and
  the initial catalogue is imported once.

## No architecture amendment

Nothing in ING-001 changes a decision from ARCH-001/002/003 or AST-001. The
schema is additive: three new tables, no column altered, no invariant relaxed.
`AssetObjectKeys` gained `managedPrefixes()`, which is a new read-only method.
