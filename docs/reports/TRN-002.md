# TRN-002 — speech to text through OpenAI

## Where this sits

TRN-001 shipped the transcription contract, the storage and the refusals, and
said so plainly: *"`none` is the only driver that ships today."* This ticket
ships the first real one, and wires it so that naming it in configuration is
the whole of what an operator has to do.

Nothing in the catalogue learned a vendor's name. `TranscribeAsset` still asks
the manager for "whatever this installation transcribes with", and the manager
is the only place that knows OpenAI exists.

## The specification, and what it does not say

**Written against `openai/openai-openapi`, the `/audio/transcriptions` path**,
because the brief said not to guess and both documentation domains are egress
blocked from this environment. The official machine-readable contract was
reachable and is what the adapter is built on:

- `POST /v1/audio/transcriptions`, `multipart/form-data`
- `file` and `model` required; `language`, `prompt`, `response_format`,
  `temperature`, `timestamp_granularities`, `stream`, `chunking_strategy` and
  `include` optional
- models include `whisper-1`, `gpt-4o-transcribe`, `gpt-4o-transcribe-diarize`
  and `gpt-4o-mini-transcribe`
- `response_format` ∈ `json`, `diarized_json`, `verbose_json`
- `verbose_json` returns `task`, `language`, `duration`, `text`, `words`,
  `segments`; a segment carries `id`, `seek`, `start`, `end`, `text`, `tokens`,
  `temperature`, `avg_logprob`, `compression_ratio`, `no_speech_prob`
- **`start` and `end` are numbers in seconds**

Two things are widely repeated in secondary sources and are **not present in
the official specification**: a list of accepted audio formats, and a maximum
upload size. Neither is asserted here. The size ceiling this adapter enforces
is therefore documented, in code and in `.env.example`, as *configured local
policy* — a decision about what an installation is willing to pay to upload —
and not as a restatement of somebody else's rule. The service's own refusal
remains the authority.

The default model is `whisper-1` for the same reason: it is the model whose
`verbose_json` segment structure the specification actually pins. The newer
transcription models are configurable. Defaulting to one on the assumption that
it returns the same segments would have been exactly the guess the brief
forbade.

## Seconds there, milliseconds here

The single most consequential line in the adapter. The response is in seconds
and this platform stores milliseconds, so an unconverted reading puts every
segment a thousand times too early — and nothing downstream would notice until
somebody opened a timeline. Mutation M1 removes the `* 1000` and the test dies.

A segment missing `start`, `end` or `text` is **skipped, not defaulted**. Zero
is a real position: coercing a missing start would place that text at the
beginning of the recording, where it would look entirely plausible.

## Configured is not certified

`ProviderCertification` (new, in `Foundation`) makes checkable the vocabulary
`docs/production-readiness.md` has used in prose: `NOT_CONFIGURED`,
`CONFIGURED_UNCERTIFIED`, `CERTIFIED`, `BLOCKED_EXTERNAL`, `UNAVAILABLE`.

This adapter **never returns `CERTIFIED` from configuration alone**, and does
not make a call in order to answer the question — a status check that costs
money is a status check nobody runs. A pasted key says somebody pasted a key.
It does not say the account exists, the model is permitted, or the quota is
unspent.

So its state today is **`CONFIGURED_UNCERTIFIED`**: complete on this side,
never proven against the real service from here. That is an honest ceiling, not
a defect, and the enum's docblock records the distinction that matters —
`BLOCKED_EXTERNAL` is not "not built".

## Two ways a key leaks, both closed

A transcription call carries a bearer token and a customer's audio.

**The error body is never carried out of the adapter.** A vendor's 4xx
routinely echoes the request back; there is no reading of that body which is
safe to keep, so a failed response raises `TRANSCRIPTION_CALL_FAILED` carrying
the provider's *name* and nothing else. The test asserts the key, the vendor
error code and the vendor error text are all absent from the message.

**A transport failure is redacted.** The HTTP client quotes the request it
sent, and that request had an `Authorization` header on it — and a failing call
is precisely the output somebody pastes into a support thread. `CredentialRedactor`
masks the configured key before the exception is raised.

No secret appears in any test fixture that is not a synthetic one, and none is
written to a transcript row.

## WHO CALLS THIS IN PRODUCTION?

`TranscribeAsset` does, resolved from the container, reaching this adapter only
through `TranscriptionManager` and only because configuration named it.

`the_domain_service_reaches_the_real_adapter_through_configuration` proves that
whole chain rather than the adapter alone: it sets `transcription.provider` to
`openai`, makes `TranscribeAsset` from the container, substitutes **no**
provider, and asserts a real HTTP request left for the documented endpoint with
the documented fields — then that the stored transcript records provider,
provider version, model, detected language and two segments.

`a_second_pass_over_the_same_asset_does_not_pay_twice` asserts idempotence **on
the wire**, not in the database: a cached row that still made the call would
look identical from a row count, and that is the shape of an accidental
re-billing of a whole catalogue.

**Honest limit, and the next ticket.** `TranscribeAsset` itself still has no
upstream caller — no event, no job, no command, no controller invokes it. That
is TRN-003 (§48.3, transcription production wiring) and it is deliberately not
smuggled in here. What this ticket proves is that the link from the domain
service to the vendor is real; the link from ingestion to the domain service is
not yet built, and this report says so rather than letting a green suite imply
otherwise.

## The pipeline test that was a probe

`DirectUploadTest::a_direct_upload_enters_the_deduplication_pipeline` is
promoted from the throwaway probe written during the §48.1 audit. A direct
upload never passes through the ingestion service the other routes use, so
nothing about it being analysed followed from those tests. What makes it work
is that `AssetObserver` raises `AssetStored` on the row itself, whichever code
wrote it — a claim that stays true right up until somebody moves the event into
the service where it looks like it belongs.

## Portability

Nothing hardcoded. The endpoint comes from the environment with no default in
PHP, exactly as the AI providers and the object stores do, so an installation
behind a corporate gateway or pointed at a self-hosted OpenAI-compatible
service changes a value rather than a file. The name in `providers` maps to a
driver, so a second endpoint for the same vendor is a configuration entry and
not a class.

The OpenAI credentials fall back to the `SANITUBE_OPENAI_*` values the AI
module already reads, because they are the same account and pasting a key twice
is how the two copies drift apart. An installation wanting a separate project
or budget sets the transcription-specific variables and the fallback never
applies.

`SANITUBE_TRANSCRIPTION_PROVIDER=none` remains the shipped default, and
`a_fresh_install_still_transcribes_with_nobody` reads that value out of
`.env.example` and asserts it resolves — the test shape AI-001 learned the hard
way, when `null` in a dotenv file turned every AI test red in CI while passing
locally.
