# ADR-0006 — BIGINT storage key plus a UUID v7 public identity

- **Status:** Accepted
- **Date:** 2026-08-14
- **Ticket:** ARCH-002

## Context

Every public aggregate needs an identifier that can appear in a URL, an API
payload and an export. Three options were live:

1. **BIGINT only.** Cheapest, but the id is then the public identity: it leaks
   catalogue size and creation order, and it is guessable. `/tracks/1041`
   invites `/tracks/1042`.
2. **UUID as primary key.** Opaque, but a 36-byte clustered key on every index
   and every foreign key. On a catalogue heading for hundreds of thousands of
   rows — running on shared hosting, where the buffer pool is small and not
   ours to tune — that is a real cost paid on every join.
3. **Both.**

Version matters too. UUID v4 is random, so as a lookup key it scatters across
the index and every read touches a different page. UUID v7 is time-ordered and
clusters, without being sequential enough to enumerate.

## Decision

Both, with the roles kept strictly apart:

- `id` — `BIGINT UNSIGNED AUTO_INCREMENT`. The storage key. Used for joins and
  foreign keys, never serialised.
- `uuid` — `CHAR(36)`, UUID v7, unique. The public identity, generated by the
  application (`Str::uuid7()`), not by a database default: a
  `DEFAULT(uuid())` would be engine-specific and is banned by the portability
  rules.

`getRouteKeyName()` returns `uuid` for every aggregate, so route binding
resolves on it.

## Consequences

**Accepted:**

- Joins stay on a 8-byte key; indexes stay narrow.
- Nothing external can infer catalogue size, ordering or the existence of a
  neighbouring record.
- An internal id appearing in a URL is structurally impossible rather than a
  review item — a test asserts that `/artists/{id}` 404s while
  `/artists/{uuid}` resolves.

**Costs:**

- Two identifiers per row, and everyone has to know which one they hold. The
  naming (`id` vs `uuid`) and the API layer carry that.
- One extra unique index per table.
- Cursor pagination encodes the primary key inside the opaque cursor. That is
  accepted: the cursor is a pagination token, not business data, and the tests
  assert only that no id appears in the payload itself.

## Revisit when

- The catalogue is distributed across systems that must mint ids without
  coordinating — then the UUID may need to become the primary key, and the
  join cost is worth paying.
- Not for aesthetics. One identifier would be tidier and would cost either
  performance or opacity.
